## Breaking changes

### ESM-only packages

Every `@rjsf/*` package now ships only ESM: per-file modules and declarations in `lib/`.
The CommonJS (`dist/index.cjs`), bundled ESM (`dist/<name>.esm.js`) and UMD (`dist/<name>.umd.js`) builds are gone, along with the `./dist` and `./dist/*.cjs` export paths.

- `import` from any bundler or from Node works as before; `require()` also keeps working on every supported Node version, which can load ESM packages natively.
- Deep imports through `@rjsf/<package>/lib/<file>.js` are unchanged.
- If you loaded a UMD bundle from a CDN with a `<script>` tag, switch to an ESM CDN (for example `import Form from 'https://esm.sh/@rjsf/core'`) or a bundler.

### Theme removals

#### @rjsf/semantic-ui

This theme has been removed as it does not support React 19 and has become unmaintained.

### Theme version support changes

#### @rjsf/mantine

Version 7 is dropping official support for `mantine` version 8. You must upgrade to version 9, which requires React 19.2 or later.

Mantine 9 also renamed `Grid`'s `gutter` prop to `gap`. `GridTemplate` maps a `gutter` value from `ui:row`/`ui:col` options to Mantine's `gap` prop for backward compatibility (an explicit `gap` wins if both are provided), but existing `ui:row`/`ui:col` options that use `gutter` should be renamed to `gap` going forward.

### Node support

Version 7 supports only the active Node.js LTS lines: `^22.18.0 || ^24.11.0 || >=26.0.0`.
Node 20, Node 23, Node 25, and Node 24 releases before 24.11.0 are no longer supported, as they are not [maintained versions](https://nodejs.org/en/about/releases/).
Node 22.18.0 is the floor because it is the first release to enable native TypeScript type stripping by default.

All PR and branch builds are running against Node 22, 24 and 26

Dropping Node 20 also let us upgrade `pnpm` past version 10, which had been pinned because pnpm 11+ requires Node >=22.13. We're now on the latest pnpm release (12).

### React version

RJSF is no longer actively supporting React version < 19.x.
React 19 is officially supported on all the themes.

### Removal of `defaultProps` support on widgets BREAKING CHANGE

`getWidget()` no longer merges a widget component's (deprecated) `defaultProps.options` into the `options` it renders with. React 19 removed `defaultProps` support for function components, so this merging behavior was already broken for function widgets there and only ever worked for `forwardRef`/`memo`-wrapped ones.

If you relied on `defaultProps` to supply default `options` for a custom widget, apply the defaults inside the widget itself instead, e.g. via destructuring defaults: `const { color = 'red' } = options;`. See [Custom widget options](../advanced-customization/custom-widgets-fields.md#custom-widget-options).

### `Widget` type BREAKING CHANGE

The `Widget<T, S, F>` type in `@rjsf/utils` is now a plain `ComponentType<WidgetProps<T, S, F>>` alias. It no longer carries the optional `MergedWidget` property, which `getWidget()` used to stamp onto a widget component to cache the wrapper it created for merging `defaultProps.options` (see above). That caching is gone along with the merging behavior it supported.

This is only a breaking change if you referenced `Widget['MergedWidget']` directly, or otherwise depended on the `Widget` type being an intersection type rather than a plain component type.

### `withTheme()` BREAKING CHANGE

`withTheme()` now returns a plain function component instead of a `forwardRef`-wrapped one, now that React 19 supports passing `ref` as a regular prop to function components.

This is a breaking change if you pass the return value of `withTheme()` directly to `useState()` or a state setter, e.g. `useState(withTheme(theme))` or `setFormComponent(withTheme(theme))`. React treats a bare function passed to either as a lazy initializer/updater and calls it immediately with no arguments, which throws (a `forwardRef` object isn't a function, so this pattern happened to work before).
Wrap it in a lazy initializer instead: `useState(() => withTheme(theme))`.

### `FormProps['onSubmit']` event type BREAKING CHANGE

The `event` parameter passed to `onSubmit` is now typed as `SubmitEvent<any>` instead of the deprecated `FormEvent<any>` (both from `react`; `FormEvent` doesn't correspond to a real event type and is annotated `@deprecated` in `@types/react` in favor of `SubmitEvent`, `ChangeEvent`, `InputEvent`, or `SyntheticEvent`). This is only a breaking change if you referenced `FormEvent` directly for your `onSubmit` handler's event parameter type.

`SubmitEvent` was added to `@types/react` in version 19.2.18; earlier 19.2.x patches don't have it and will fail to compile against `@rjsf/core`'s published types with `TS2305: Module 'react' has no exported member 'SubmitEvent'`. Make sure your project's `@types/react` is at least `19.2.18`.

### `ObjectFieldTemplatePropertyType` BREAKING CHANGE

`ObjectFieldTemplatePropertyType` in `@rjsf/utils` is now generic (`<T, S, F>`, defaulted like every other RJSF generic type), and its `content` field is typed as `ReactElement<Pick<FieldProps<T, S, F>, 'schema' | 'uiSchema'>>` instead of a bare `ReactElement`. `ObjectFieldTemplateProps['properties']` threads its own `<T, S, F>` through to it.

This is only a breaking change if you referenced `ObjectFieldTemplatePropertyType` with explicit (non-default) generic arguments, or relied on `content.props` being typed as `any`.
