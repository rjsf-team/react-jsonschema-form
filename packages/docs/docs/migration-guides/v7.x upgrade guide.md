# 7.x Upgrade Guide

## New deprecations

### Reading `Form` internals through a `ref`

The `Form` ref now has a documented contract: the `FormHandle` type, exported from `@rjsf/core`.
Its members are unchanged and stay supported. Anything else on the instance is an implementation detail and will break in a later 7.x release, so stop using it now:

| Stop using                            | Use instead                                                                                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `.state.formData`                     | `.getFormData()`, new in this release (see New Features)                                                                                         |
| `.state.errorSchema`, `.state.errors` | `event.errorSchema`, `event.errors` in your `onChange`/`onSubmit` handler                                                                        |
| `.state.schemaUtils`                  | build one with `createSchemaUtils({ validator }, schema)`, or use the `registry.schemaUtils` a field, widget or template receives                |
| `.state.registry`                     | build one with `buildRegistry(props, schemaUtils.getRootSchema(), schemaUtils)`, or use the `registry` prop a field, widget or template receives |
| `.setState(...)`                      | `.setFieldValue(path, value)`, or pass a new `formData`                                                                                          |
| `.formElement`                        | `.reset()` for a form reset; direct DOM access has no replacement                                                                                |

```diff
-const data = formRef.current.state.formData;
+const data = formRef.current.getFormData();

-const { errorSchema } = formRef.current.state;
+const onChange = (event) => setErrorSchema(event.errorSchema);
```

Still supported and unchanged: `submit()`, `reset()`, `setFieldValue()`, `validateForm()`, `validateFormWithFormData()` and `focusOnError()`.

`validate()` is still supported, but it now takes only the data to validate; see [`FormHandle.validate()` takes only the data](#formhandlevalidate-takes-only-the-data-breaking-change).

These `state` members carry no `@deprecated` tag yet, so the only notice is this guide. `IChangeEvent` is derived from `FormState`, so tagging `state.formData` or `state.errorSchema` would also mark `event.formData` and `event.errorSchema` — the replacements — as deprecated.
The tags follow once the event type stops deriving from the state type.

**Typing the ref.** Keep `useRef<Form>()`.
TSX types a class element's `ref` by its instance, so `useRef<FormHandle>()` is rejected on `<Form ref>` for as long as `Form` is a class.
Narrow to `FormHandle` where you use the ref instead; the compiler then keeps you on the supported members, and nothing changes for you when the ref prop itself becomes `Ref<FormHandle>`:

```tsx
import { useRef } from 'react';
import type { FormHandle } from '@rjsf/core';
import Form from '@rjsf/core';

function Editor({ id, record }) {
  const formRef = useRef<Form>(null);

  function save() {
    const form: FormHandle | null = formRef.current;
    api.patch(id, form?.getFormData());
  }

  return <Form ref={formRef} schema={schema} validator={validator} initialFormData={record} />;
}
```

**Why.** With one owner per form (see [Form data has one owner](#form-data-has-one-owner-breaking-change)) there is no internal copy to read: `getFormData()` returns what the form renders in either mode, and `FormHandle` is the ref contract that survives the later move to a function-component `Form`.

## Breaking changes

### Form data has one owner BREAKING CHANGE

`Form` now follows the `<input>` rule, decided once at mount:

- **`formData`: you own the value**, like `value`. The form renders exactly what you pass and proposes each edit through `onChange`; nothing changes until you pass the new value back.
- **`initialFormData`, or neither: the form owns the value**, like `defaultValue`.

Only `undefined` means "not passed": `formData={null}` is a value you own, unlike `<input value={null}>`. A form that mounts with `formData` stays yours if it later becomes `undefined`.

Find your case below.

**Your `onChange` doesn't store the value back** (it logs, validates, or there is none). With `formData` the form now shows none of the user's edits. Switch to `initialFormData`:

```diff
-<Form schema={schema} validator={validator} formData={record} onChange={log} />
+<Form schema={schema} validator={validator} initialFormData={record} onChange={log} />
```

If a form is meant to be fixed, keep `formData` and add `readonly`.

**You control the data** (`onChange={(e) => setData(e.formData)}`). This keeps working as long as the handler updates the state synchronously; updating from a Transition, `useDeferredValue`, a timeout or after an `await` is not supported. Three things differ:

- **No defaults are generated for you**, whether on mount, after a schema change or when you replace the data. Seed them yourself:

  ```tsx
  const schemaUtils = createSchemaUtils({ validator, customMergeAllOf, defaultFormStateBehavior }, schema);
  const [data, setData] = useState(() => schemaUtils.getDefaultFormState(schema, record));
  ```

  Pass the same `customMergeAllOf` and `defaultFormStateBehavior` the form gets: computing defaults merges `allOf`s, so a context missing either one seeds data the form itself would not produce.

  Defaults added by an edit, such as a new array item or a `oneOf` switch, are still proposed.

- **`onChange` fires for edits only**: user input, `setFieldValue()`, and blur validation or omission. It no longer fires on mount or when a prop changes.
- **`reset()` clears only the form's own errors.** It leaves the data alone and doesn't call `onChange`. To reset the data, pass the value you want as `formData` (and call `reset()` to clear the errors), or remount with a new `key`.

**Your data loads after mount.** A form that mounts with `formData={undefined}` owns its data for good: when the record arrives, the form ignores it and logs a development warning. Mount once the data is there:

```tsx
if (!record) {
  return <Spinner />;
}
return <Form key={recordId} schema={schema} validator={validator} formData={record} onChange={onChange} />;
```

Or pass a fallback for the root type, such as `formData={record ?? {}}`. Only do this when the form can't be edited before the record arrives.

**You read defaults from `onChange` or `state.formData`.** A form that owns its data no longer calls `onChange` for defaults it adds to `initialFormData` on mount or after a schema or uiSchema change. A form you control no longer keeps `state.formData`. In both cases, read `getFormData()`.

**Also note:**

- With `omitExtraData`, a form you control still passes the data with extra fields removed to `onSubmit`, but no longer stores that copy.
- In development, the `formData` passed to `onChange` is deep-frozen, so mutating it throws instead of silently corrupting your state. Only plain objects and arrays are frozen.
- Development warnings flag three cases:
  - `formData` arriving after the form mounted without it.
  - `formData` passed together with `initialFormData`.
  - A form you control with no `onChange` that is neither `readonly` nor `disabled`.

**Why.** Before this release the form kept a private copy of your data so it could reconcile the two owners. That copy is why a declined edit stayed visible, a `oneOf` switch snapped back, and every prop change re-ran default generation. With one owner there is nothing to reconcile.

### ESM-only packages

Every `@rjsf/*` package now ships only ESM: per-file modules and declarations in `lib/`.
The CommonJS (`dist/index.cjs`), bundled ESM (`dist/<name>.esm.js`) and UMD (`dist/<name>.umd.js`) builds are gone, along with the `./dist` and `./dist/*.cjs` export paths.

- `import` from any bundler or from Node works as before; `require()` also keeps working on every supported Node version, which can load ESM packages natively.
- Deep imports through `@rjsf/<package>/lib/<file>.js` are unchanged, except `@rjsf/mantine`'s `lib/templates/ButtonTemplates/index.js`, which was removed.
- If you loaded a UMD bundle from a CDN with a `<script>` tag, switch to an ESM CDN (for example `import Form from 'https://esm.sh/@rjsf/core'`) or a bundler.

### `@rjsf/shadcn` no longer ships prebuilt stylesheets BREAKING CHANGE

The compiled `dist/<theme>.css` files (`default`, `amethyst-haze`, `caffeine`, `claude`, `clean-slate`, `neo-brutalism`, `pastel-dreams`, `soft-pop`, `twitter`, `vercel`) are gone, and so is the `src/css` directory they were built from.
Each was a full Tailwind build — preflight reset included — for one fixed set of design tokens, which is the wrong shape for a library: importing one restyled the whole page and could not follow your own shadcn theme.

`@rjsf/shadcn` is now styled the way shadcn components are, by the application's Tailwind build.
Add the package to your Tailwind sources:

```css
@import 'tailwindcss';
@source "../node_modules/@rjsf/shadcn/lib";
```

The form then picks up the CSS variables from your `shadcn init` setup.
If you were importing a prebuilt theme for its colors, generate the equivalent variables with [tweakcn](https://tweakcn.com/editor/theme) into your global CSS; the playground's [theme sources](https://github.com/rjsf-team/react-jsonschema-form/tree/main/packages/playground/src/themes/shadcn) hold the token sets the old stylesheets were built from.

### `getDefaultRegistry()` removed BREAKING CHANGE

`getDefaultRegistry()` bundled the core fields, widgets and templates together with placeholder `rootSchema`, `formContext`, `translateString` and `globalFormOptions` values that the `Form` overwrote anyway. Use `generateTheme()` for all three dictionaries, or the individual generator for the one you need:

```diff
-import { getDefaultRegistry } from '@rjsf/core';
+import { generateTheme } from '@rjsf/core';

-const { fields, widgets, templates } = getDefaultRegistry();
+const { fields, widgets, templates } = generateTheme();
```

```diff
-import { getDefaultRegistry } from '@rjsf/core';
+import { generateFields } from '@rjsf/core';

-const { StringField } = getDefaultRegistry().fields;
+const { StringField } = generateFields();
```

To reuse a single component, import it directly instead — `import { StringField } from '@rjsf/core'` — so the rest of the core components stay out of your bundle.

### `Form.getRegistry()` is now the `buildRegistry()` export BREAKING CHANGE

`getRegistry()` was a `static` on the `Form` class. It is now a standalone `buildRegistry()` export from `@rjsf/core`, taking the same arguments:

```diff
-import Form from '@rjsf/core';
+import { buildRegistry } from '@rjsf/core';

-const registry = Form.getRegistry(props, schema, schemaUtils);
+const registry = buildRegistry(props, schema, schemaUtils);
```

Most code never needs it. Inside a field, widget or template, use the `registry` prop you already receive — it is the registry the `Form` actually rendered with, including its real `schemaUtils`.
To build one for a test, use `getTestRegistry()` from `@rjsf/core/testing`.
For the core component dictionaries on their own, use `generateTheme()`.

### `_internalFormWrapper` removed BREAKING CHANGE

The private `_internalFormWrapper` prop, and its entry in the `ThemeProps` a theme passes to `withTheme()`, have been removed.
It existed so `@rjsf/semantic-ui` could wrap the `<form>` element in that library's own `Form` component, and it was the only theme that ever used it.
Use the public `tagName` prop to render a different element in place of `<form>`.

### `getTestRegistry()` moved to `@rjsf/core/testing` BREAKING CHANGE

Update the import and add `@rjsf/validator-ajv8` to your dev dependencies:

```diff
-import { getTestRegistry } from '@rjsf/core';
+import { getTestRegistry } from '@rjsf/core/testing';
```

```bash
npm install --save-dev @rjsf/validator-ajv8
```

`@rjsf/validator-ajv8` is now an optional peer dependency of `@rjsf/core` that only this entry point needs, so it no longer ships as a transitive dependency of the main entry.
The arguments are unchanged: `getTestRegistry(schema, {}, templates)` still works.

### `Registry` members are read-only BREAKING CHANGE

Every member of the `Registry` type in `@rjsf/utils` is now `readonly`.
The registry is the plumbing `Form` builds from its props and hands down to fields, widgets and templates; nothing is supposed to write back into it, and now nothing can.

This is only a breaking change if you assigned into a registry you received, e.g. `registry.globalUiOptions = {...}` or `registry.formContext = {...}`.
Build a modified copy instead and pass that down:

```diff
-registry.globalUiOptions = { enableMarkdownInHelp: true };
+const registry = { ...baseRegistry, globalUiOptions: { enableMarkdownInHelp: true } };
```

Only the registry's own members are read-only.
The component maps it holds are not deeply read-only, so `registry.widgets.MyWidget = ...` still compiles; override widgets, fields and templates through the `Form` props or `withTheme()` rather than by writing into the maps.

The registry that `getTestRegistry()` returns is additionally frozen at runtime, along with its `fields`, `templates` and `widgets` maps and the nested `ButtonTemplates`, so a test that mutates it throws instead of silently affecting later assertions.
The freeze is shallow by design: a deep freeze would reach objects the caller owns, such as `formContext`, `rootSchema` and the validator's internal caches.

### `schema`, `uiSchema` and `registry` props are read-only BREAKING CHANGE

`schema`, `uiSchema` and `registry` are now `readonly` on `RJSFBaseProps`, which every field, widget and template props type extends, and on `SubmitButtonProps`, which declares its own.
These are values the form builds and passes down; writing back into them never reached the form and now fails to compile.

This is only a breaking change if you assigned into the props your custom component received, e.g. `props.schema = modifiedSchema`.
Spread a copy and use that instead, which also drops the modifiers:

```diff
-props.schema = { ...props.schema, title: 'Custom' };
+const schema = { ...props.schema, title: 'Custom' };
```

Note that these props are read-only, not deeply immutable.
The objects behind them are shared with the form, so mutating `props.schema.title` in place is still a bug even though it compiles.

### Markdown is an opt-in template

`markdown-to-jsx` is no longer part of the `@rjsf/core` bundle (it was a third of it) and is now an optional peer dependency instead of a dependency, so `@rjsf/core` no longer installs it.
Markdown is rendered through the `MarkdownTemplate`, whose core default is plain text; `@rjsf/core/markdown` provides the `markdown-to-jsx` implementation. Install `markdown-to-jsx` and register it:

```tsx
import Form from '@rjsf/core';
import MarkdownTemplate from '@rjsf/core/markdown';

<Form
  schema={schema}
  validator={validator}
  templates={{ MarkdownTemplate }}
  uiSchema={{ 'ui:enableMarkdownInDescription': true }}
/>;
```

The `ui:enableMarkdownInDescription` and `ui:enableMarkdownInHelp` options remain independent, default to `false`, and can still be set through `ui:globalOptions`.
Translatable strings that allow markdown go through `RichDescription`, so they also need `ui:enableMarkdownInDescription`.
`RichDescription.TEST_IDS` and `RichHelp.TEST_IDS` no longer exist, since neither component renders markdown itself any more; the markdown test id lives on the renderer as `MarkdownTemplate.TEST_IDS.markdown` from `@rjsf/core/markdown`.
Raw HTML is never parsed, including in `FileWidget`'s file information, which used to allow it.

The English `InvalidObjectField`, `UnsupportedField*` and `FilesInfo` translatable strings no longer use markdown syntax.
`FileWidget`'s file information used to render through `markdown-to-jsx` unconditionally, which is what made the file name bold; it now goes through `RichDescription` like every other translatable string, so it is plain text unless you register a `MarkdownTemplate`, set `ui:enableMarkdownInDescription`, and supply a `translateString` that marks the name up.
A custom `translateString` that returns markdown keeps working when the template is registered and `ui:enableMarkdownInDescription` is enabled.

### Removal of `defaultProps` support on widgets BREAKING CHANGE

`getWidget()` no longer merges a widget component's (deprecated) `defaultProps.options` into the `options` it renders with.
React 19 removed `defaultProps` support for function components, so this merging behavior was already broken for function widgets there and only ever worked for `forwardRef`/`memo`-wrapped ones.

If you relied on `defaultProps` to supply default `options` for a custom widget, apply the defaults inside the widget itself instead, e.g. via destructuring defaults: `const { color = 'red' } = options;`.
See [Custom widget options](../advanced-customization/custom-widgets-fields.md#custom-widget-options).

### `Widget` type BREAKING CHANGE

The `Widget<T, S, F>` type in `@rjsf/utils` is now `SlotComponent<WidgetProps<T, S, F>>`, the slot type `Field` and every `TemplatesType` entry share: any function or class component taking those props, including one annotated as a React `ComponentType` or `FunctionComponent`.
It no longer carries the optional `MergedWidget` property, which `getWidget()` used to stamp onto a widget component to cache the wrapper it created for merging `defaultProps.options` (see above).
That caching is gone along with the merging behavior it supported.

This breaks code that referenced `Widget['MergedWidget']` directly, and code that assigns a `Widget` to a React `ComponentType` annotation, which a `SlotComponent` does not satisfy; annotate such a value as `Widget` instead. Passing your own `ComponentType` into `widgets` is unaffected.

### `withTheme()` BREAKING CHANGE

`withTheme()` now returns a plain function component instead of a `forwardRef`-wrapped one, now that React 19 supports passing `ref` as a regular prop to function components.

This is a breaking change if you pass the return value of `withTheme()` directly to `useState()` or a state setter, e.g. `useState(withTheme(theme))` or `setFormComponent(withTheme(theme))`.
React treats a bare function passed to either as a lazy initializer/updater and calls it immediately with no arguments, which throws (a `forwardRef` object isn't a function, so this pattern happened to work before).
Wrap it in a lazy initializer instead: `useState(() => withTheme(theme))`.

Its return type changed too; see [`withTheme()` returns a `ThemedForm`](#withtheme-returns-a-themedform-breaking-change).

### `FormProps['onSubmit']` event type BREAKING CHANGE

The `event` parameter passed to `onSubmit` is now typed as `SubmitEvent<any>` instead of the deprecated `FormEvent<any>` (both from `react`; `FormEvent` doesn't correspond to a real event type and is annotated `@deprecated` in `@types/react` in favor of `SubmitEvent`, `ChangeEvent`, `InputEvent`, or `SyntheticEvent`).
This is only a breaking change if you referenced `FormEvent` directly for your `onSubmit` handler's event parameter type.

`SubmitEvent` was added to `@types/react` in version 19.2.18; earlier 19.2.x patches don't have it and will fail to compile against `@rjsf/core`'s published types with `TS2305: Module 'react' has no exported member 'SubmitEvent'`.
Make sure your project's `@types/react` is at least `19.2.18`.

### `ObjectFieldTemplatePropertyType` BREAKING CHANGE

`ObjectFieldTemplatePropertyType` in `@rjsf/utils` is now generic (`<T, S, F>`, defaulted like every other RJSF generic type), and its `content` field is typed as `ReactElement<Pick<FieldProps<T, S, F>, 'schema' | 'uiSchema'>>` instead of a bare `ReactElement`. `ObjectFieldTemplateProps['properties']` threads its own `<T, S, F>` through to it.

This is only a breaking change if you referenced `ObjectFieldTemplatePropertyType` with explicit (non-default) generic arguments, or relied on `content.props` being typed as `any`.

### Removal of deprecated APIs BREAKING CHANGE

The following APIs, deprecated in prior releases, have been removed:

- **`UiSchema['ui:rootFieldId']`**: use the `Form.idPrefix` prop instead.
- **`Form.getUsedFormData()` and `Form.getFieldNames()`** instance methods, and the underlying `getUsedFormData`/`getFieldNames` exports from `@rjsf/utils`: there is no direct replacement.
- **`Form.omitExtraData()`** instance method: use `SchemaUtils.omitExtraData(schema, formData)` instead (build one with `createSchemaUtils`, or use the `registry.schemaUtils` your fields, widgets and templates already receive).
- **`FormProps.removeEmptyOptionalObjects`**: this prop had already stopped doing anything; use `omitExtraData` instead, which now prunes empty optional objects as part of its filtering.
- **`removeOptionalEmptyObjects()`** exported from `@rjsf/utils`: use `omitExtraData` instead, which has the equivalent pruning built in.
- **`toPathSchema()`** exported from `@rjsf/utils`, and `SchemaUtils.toPathSchema()`: there is no direct replacement.
- **`PathSchema` type** exported from `@rjsf/utils`: there is no direct replacement.
- **The `boolean` options for `FormProps.liveValidate` and `FormProps.liveOmit`**: use `'onChange'` in place of `true`, or omit the prop (or pass `undefined`) in place of `false`.

### Generic defaults are `unknown` instead of `any` BREAKING CHANGE

The RJSF generics are `<T, S, F>`: the form data, the schema, and the form context. `T` and `F` used to default to `any`, so anything read out of `formData` was unchecked and stayed unchecked however far it travelled. They now default to `unknown` and `FormContextType`.

Only the `T` change has teeth. `FormContextType` is still an alias for `GenericObjectType`, which is `Record<string, any>`, so reading `formContext.anything` gives you `any` exactly as before. The `F` default is a rename that makes the future retyping of `FormContextType` a one-line change; that retyping is a separate breaking change and is not part of this one.

Passing your own type is still the way to get typed form data: `Form<MyData>`, `FieldProps<MyData>` and `IChangeEvent<MyData>` behave as before (apart from `IChangeEvent.formData`, described below), and `Form` infers `T` from `formData` when you pass it, so `<Form formData={data} onChange={…} />` types the handler with no type argument at all. The validators and the theme exports were retyped so they keep working with a typed form; see [`ValidatorType` and `customizeValidator()` take the schema as their first type argument](#validatortype-and-customizevalidator-take-the-schema-as-their-first-type-argument-breaking-change) and [`withTheme()` returns a `ThemedForm`](#withtheme-returns-a-themedform-breaking-change) below.

Values annotated without a type argument still fit a typed form. A `const uiSchema: UiSchema = …`, a `CustomValidator` or `ErrorTransformer`, a handler taking a bare `IChangeEvent`, and a widget, field or template written against the bare props (`function MyWidget(props: WidgetProps)`, class components included) all go into a `Form<MyData>`. Passed next to `formData` they do not change what `Form` infers either: `T` comes from `formData`/`initialFormData`, and from the other props only when no data is passed, so a typed `onSubmit` handler still types a form that has no `formData`. Component slots check their props bivariantly, the way React checks event handlers, which is what lets a component written for `unknown` data fit a slot typed for `MyData`.

The exception is a `ref`: an unannotated `createRef<Form>()` next to typed `formData` makes `T` `unknown`. Give it the type, `createRef<Form<MyData>>()`; a `FormHandle`-typed ref does not fit the `ref` prop, so narrow to `FormHandle<MyData>` where you read it, as described under [Reading `Form` internals through a `ref`](#reading-form-internals-through-a-ref).

The reverse does not hold: a typed handler does not fit a bare `FormProps`, since `FormProps` means `FormProps<unknown>`. A props object or a wrapper component that takes typed handlers (`customValidate: (formData: MyData | undefined, …)`, `onSubmit: (e: IChangeEvent<MyData>) => …`) fails with `TS2322`; type it `FormProps<MyData>`, as in `function MyForm(props: FormProps<MyData>) { return <Form {...props} />; }`.

`IChangeEvent.formData` and `FormHandle.getFormData()` are typed `EventFormData<T>`: `T` itself when the data is an object or array, since no change below the root replaces such a root with `undefined`, and `T | undefined` for a scalar, which is `undefined` once its field is cleared. A write at the root itself can empty an object root: `setFieldValue('', undefined)`, or a root-level custom field or widget calling `onChange(undefined, ROOT_FIELD_PATH)`. The type does not reflect that, and the event reaches `onChange` either way, so allow for `undefined` in the handler's state if your form does either. So `const [data, setData] = useState(initial)` with `onChange={({ formData }) => setData(formData)}` needs no annotation for an object form. For a scalar root the state has to allow `undefined`:

```diff
-const [theme, setTheme] = useState('light');
+const [theme, setTheme] = useState<string | undefined>('light');
 <Form schema={{ type: 'string' }} formData={theme} onChange={({ formData }) => setTheme(formData)} … />
```

Beyond those, what changes is code that relied on the `any` default. The form data now arrives as `unknown`, so you either name its type or narrow it.

**Name the type** — preferred, and what the default is there to encourage:

```diff
-const onChange = ({ formData }: IChangeEvent) => save(formData.name);
+const onChange = ({ formData }: IChangeEvent<MyData>) => save(formData.name);
```

**Or narrow it**, when the data really is unknown at that point:

```diff
-function MyField({ formData }: FieldProps) {
-  return <input value={formData} />;
+function MyField({ formData }: FieldProps) {
+  return <input value={typeof formData === 'string' ? formData : ''} />;
 }
```

A custom validator receives `unknown` for the same reason:

```diff
-const customValidate = ({ pass1, pass2 }, errors) => {
+const customValidate: CustomValidator<MyData> = (formData, errors) => {
+  const { pass1, pass2 } = formData ?? {};
   if (pass1 !== pass2) {
     errors.pass2?.addError("Passwords don't match");
   }
   return errors;
 };
```

One declaration changed along with the defaults: `Registry.schemaUtils` is `SchemaUtilsType<T, S, F>` rather than `SchemaUtilsType<T, S>`. The omitted `F` was a latent bug that the `any` default had been hiding; it only matters if you wrote the type out by hand.

### `ValidatorType` and `customizeValidator()` take the schema as their first type argument BREAKING CHANGE

`ValidatorType<S, F>` puts the form data type on `validateFormData<T>()`, since a validator checks data of any shape against a schema. `import validator from '@rjsf/validator-ajv8'` (and the same export from `@rjsf/validator-ata` and `@rjsf/validator-cfworker`) fits every `Form`, and `customizeValidator()` takes only `<S, F>`:

```diff
-const validator = customizeValidator<MyData>();
+const validator = customizeValidator();

 <Form<MyData> schema={schema} validator={validator} />
```

The first type argument is now the schema type, so a leftover `customizeValidator<MyData>()` or `ValidatorType<MyData>` does not always fail where it is declared. If `MyData` shares no keys with `JSONSchema7`, the declaration is the error (`TS2559: Type 'MyData' has no properties in common with type 'JSONSchema7'`). A shared key of a conflicting type fails at the declaration too (`TS2344: Type 'MyData' does not satisfy the constraint 'JSONSchema7'`). Otherwise (a `title: string`, say) the declaration compiles with the schema typed as `MyData`: a `Form` that infers its types from it reports the mismatch on its `schema` prop (`TS2322: Type 'RJSFSchema' is not assignable to type …`, or `TS2741: Property '…' is missing in type 'RJSFSchema'` when `MyData` also has a required key that `JSONSchema7` lacks), and a `Form<MyData>` may not report it at all, since the validator's methods are checked bivariantly. In every case, drop the type argument.

### `withTheme()` returns a `ThemedForm` BREAKING CHANGE

`withTheme()` returns the new `ThemedForm<T, S, F>` rather than `ComponentType<FormProps<T, S, F>>`: a function component that is generic over the form data like `Form`, so a theme's default `Form` export infers `T` from `formData` or takes it as `<Form<MyData> />`. The `Theme`, `Templates` and `Widgets` exports keep each component's own generic type, so `withTheme<MyData>(Theme)` and `{ ...Templates, FieldTemplate: MyFieldTemplate }` typecheck for any `T`. `generateForm<T, S, F>()` and `generateTheme<T, S, F>()` still exist for pinning the types up front. An existing `ComponentType<FormProps<…>>` annotation of the return value still compiles, but it fixes `T` again; drop it to keep the per-use inference. Since `ThemedForm` is a plain generic function type, setting or reading component statics such as `displayName` on the return value no longer type-checks.

### `ErrorSchema<T>` and `FormValidation<T>` node shapes BREAKING CHANGE

`ErrorSchema<T>` and `FormValidation<T>` now describe the tree that `toErrorSchema()` and `createErrorHandler()` actually build. Previously they resolved to the wrong shape for anything but a plain object: a leaf field's node resolved to that field's own type, an array's node to an array rather than a node keyed by index, and `ErrorSchema<any>` to an index signature that no concrete error schema was assignable to. In practice a typed error schema never type-checked.

There are two things to do.

**Drop the casts you used to work around the old shapes.** The value type-checks on its own now:

```diff
-const extraErrors = { name: { __errors: ['too short'] } } as unknown as ErrorSchema;
+const extraErrors: ErrorSchema<FormData> = { name: { __errors: ['too short'] } };
```

**Reach into nodes with `?.`.** Every node is optional, because the tree only contains the fields that actually have errors:

```diff
-errors.address.city.addError('unknown city');
+errors.address?.city?.addError('unknown city');
```

For reference, this is the shape a typed error schema now accepts — a node per field, keyed by index for arrays, with no children below a leaf:

```ts
type FormData = { name: string; address?: { city: string }; tags: string[] };

const errors: ErrorSchema<FormData> = {
  __errors: ['form-level problem'],
  name: { __errors: ['too short'] },
  address: { city: { __errors: ['unknown city'] } },
  tags: { 0: { __errors: ['not allowed'] } },
};
```

A field whose type is a union — what a `oneOf`/`anyOf` property gives you — accepts the children of every member it can hold, since which one is present depends on the current value:

```ts
type FormData = { thing: string | { city: string } };

const errors: ErrorSchema<FormData> = { thing: { city: { __errors: ['unknown city'] } } };
```

`FormValidation<T>`, the tree a `customValidate` function receives, is the same tree with `addError()` on every node.

In full, the children a node accepts are decided by the type of the data it describes:

| Field's type                                | Children of its error node                            |
| ------------------------------------------- | ----------------------------------------------------- |
| An object                                   | A node per property                                   |
| An array                                    | A node per index, keyed as `0`, `1`, …                |
| A tuple                                     | A node per position, each of that position's own type |
| A tuple with a rest element                 | Its declared positions as above, the rest as an array |
| A primitive (`string`, `number`, `boolean`) | None — a leaf holds only `__errors`                   |
| `Date` or `File`                            | None — an object holding no form fields               |
| A union                                     | The children of every member                          |
| `any` or `unknown`                          | Unconstrained                                         |

An optional property is described by the type it holds, so `address?: { city: string }` gets the same node as `address: { city: string }`.
Any other class instance used as a field value (a `Money` or `LatLng` value object, say) is treated as an object, so its properties are accepted as children even though nothing produces errors for them.

If you leave `T` at its default (`unknown`) and never annotate an error schema, nothing changes for you.

### `extraErrors` now blocks submission by default BREAKING CHANGE

`FormProps.extraErrorsBlockSubmit` has been replaced with `FormProps.extraErrorsAreWarnings`, and the default behavior is inverted: `extraErrors` now block form submission by default, the same as JSON Schema validation errors.

If you were relying on the old default (`extraErrors` displayed but non-blocking), set `extraErrorsAreWarnings` to `true`.
If you were setting `extraErrorsBlockSubmit` to `true` to get blocking behavior, remove the prop entirely — that is now the default.

If your app sets `extraErrors` from a failed server response (the async validation pattern above) and leaves it populated afterward, resubmitting the form will now re-block on those same stale errors and call `onError` again, since every submit re-merges whatever `extraErrors` is currently set to.
Clear `extraErrors` (e.g. back to `{}`) when the user edits the form or before they resubmit, the same way you'd clear a schema validation error.

### Removal of the `experimental_`/`Experimental_` prefix BREAKING CHANGE

The features below were marked experimental while their API stabilized. They are no longer experimental in v7, and the prefix has been dropped from their names:

| Old name                                                      | New name                             |
| ------------------------------------------------------------- | ------------------------------------ |
| `FormProps.experimental_defaultFormStateBehavior`             | `FormProps.defaultFormStateBehavior` |
| `FormProps.experimental_customMergeAllOf`                     | `FormProps.customMergeAllOf`         |
| `Experimental_DefaultFormStateBehavior` (type, `@rjsf/utils`) | `DefaultFormStateBehavior`           |
| `Experimental_ArrayMinItems` (type, `@rjsf/utils`)            | `ArrayMinItems`                      |
| `Experimental_CustomMergeAllOf` (type, `@rjsf/utils`)         | `CustomMergeAllOf`                   |

The corresponding `experimental_defaultFormStateBehavior`/`experimental_customMergeAllOf` parameters on the `@rjsf/utils` schema functions (e.g. `getDefaultFormState`, `retrieveSchema`, `createSchemaUtils`, and others) were renamed the same way, and are now members of the `SchemaContext` those functions take; see [`@rjsf/utils` schema functions take a `SchemaContext` in place of the `validator`](#rjsfutils-schema-functions-take-a-schemacontext-in-place-of-the-validator-breaking-change). Update any code that names these props, types, or parameters explicitly.

### `time`/`date-time` formats now require a timezone offset BREAKING CHANGE

`@rjsf/validator-ajv8` now depends on `ajv-formats` 3.x instead of 2.x. Per [RFC 3339](https://datatracker.ietf.org/doc/html/rfc3339#section-5.6), `ajv-formats` 3 requires the JSON Schema `time` format to include a timezone offset (`Z`, or `+HH:MM`/`-HH:MM`); previously the offset was optional for `time` alone. `date-time` already required an offset in `ajv-formats` 2.x, so it's unaffected by this change.
This closes [#3930](https://github.com/rjsf-team/react-jsonschema-form/issues/3930), where `format: "time"` values produced by RJSF were not spec-compliant.

- **`@rjsf/core`'s `TimeWidget`** (used for `format: "time"`, and the equivalent `TimeWidget` in `@rjsf/daisyui` and `@rjsf/mantine`) now appends the browser's local UTC offset to the value whenever it's changed, e.g. `14:30:00-04:00` instead of `14:30:00`. The offset is stripped back off when displaying a value in the native time input. `format: "date-time"`/`alt-datetime` were already emitting `Z`-suffixed UTC strings and are unaffected.
- If you have previously-stored `formData` for a `format: "time"` field that lacks a timezone offset, it will now fail validation. Options:
  - Let the widget resave the value the next time a user edits that field — it will pick up the offset automatically. Note this reinterprets the wall-clock value in the browser's _current_ local offset, so if the stored value already carried a different offset (e.g. entered in another timezone), resaving it will represent a different instant rather than preserving the original one.
  - Backfill stored data with an explicit offset (e.g. treat legacy values as UTC and append `Z`).
  - If you need to keep accepting offset-less values for a given field, change that field's schema to `format: "iso-time"`/`format: "iso-date-time"` instead of `format: "time"`/`format: "date-time"` — `ajv-formats` 3 added these as an explicit, optional-timezone escape hatch for validation. RJSF maps both to the same widget used for `time`/`date-time` (`TimeWidget`/`DateTimeWidget`, including the dedicated `DateTimeWidget`s in `@rjsf/antd` and `@rjsf/daisyui`), and doesn't add a timezone offset for those formats, so committed values keep behaving like `format: "time"`/`format: "date-time"` did before this release. A stored value that happens to carry an offset anyway is still stripped for display, since the underlying date/time picker can't render one either way.

### `UiSchema<T>` checks field names BREAKING CHANGE

`UiSchema<T>` used to intersect `GenericObjectType` (`Record<string, any>`), so any string key was accepted. The per-field entries are now a mapped type over `T`, which means a field name that isn't in the form data is a compile error:

```ts
type FormData = { firstName: string; address: { city: string } };

const uiSchema: UiSchema<FormData> = {
  firstName: { 'ui:widget': 'textarea' },
  address: { city: { 'ui:placeholder': 'City' } },
  lastName: { 'ui:widget': 'text' }, // error: `lastName` is not a field of FormData
};
```

`FormProps` already infers `T` from `formData`, so a form with typed form data gets this without naming the type anywhere.

What has _not_ changed:

- **Untyped uiSchemas.** `UiSchema` with no type argument, or with `any` form data, accepts exactly what it accepted before — arbitrary nesting included.
- **The `ui:` namespace.** Any `ui:`-prefixed key is still accepted at every level, so theme-specific and application-specific directives keep working.
- **`oneOf`/`anyOf` fields.** A union-typed field accepts the keys of every branch, since which branch is present depends on the current value.

What to fix, if any of it affects you:

- **A uiSchema that names a field absent from `T`** — a property added by a `dependencies` subschema, or an `additionalProperties` key when `T` has no index signature. Give `T` an index signature (`{ [key: string]: unknown }` on the relevant object), or nest the entry under the `additionalProperties` key described below.
- **Keys the old index signature accepted silently** are now declared, with types: `additionalProperties` (a uiSchema for the data the index signature of `T` holds, unconstrained when `T` has none), `additionalItems` (a uiSchema for the array's element type), `anyOf` and `oneOf` (positional lists, one uiSchema per subschema), and the legacy unprefixed `classNames` (a string; `ui:classNames` is the prefixed spelling of the same thing). If you passed an object where a positional list is expected — `oneOf: { 'ui:title': '...' }` — it was already ignored at runtime, with a console warning; it is now also a type error.
- **A form data field named `classNames`, `anyOf` or `oneOf`** cannot be given a per-field entry, because the entry's type is intersected with the declared key's type and a string or a list has nothing in common with a uiSchema. This makes a runtime limitation visible rather than adding one: `SchemaField` consumes and deletes `classNames` from every uiSchema it receives, and `anyOf`/`oneOf` are read as positional lists wherever the schema has that keyword, so such a field's uiSchema was never reliably delivered. Rename the field, or configure it through `ui:options` on the parent. A field named `items`, `additionalItems` or `additionalProperties` is fine: those keys hold a uiSchema, so the intersection accepts the per-field entry.
- **A self-referential form data type** (`type TreeNode = { children: TreeNode[] }`) nested far enough in one uiSchema literal can exhaust the type checker (`Excessive stack depth comparing types`), since the per-field entries recurse with the data. Annotate the deep sub-entry as plain `UiSchema` to stop the recursion there.
- **A uiSchema typed by an `interface` you declared** is rejected, because an interface has no index signature and `UiSchema` requires one for its `ui:` keys. This is not new — the `ui:${string}` signature predates this change — but the field-name checking makes it easier to hit. Use a `type` alias, or annotate the literal with `UiSchema<T>` directly.

### `UiSchemaDefinitions` drops its `T` parameter BREAKING CHANGE

`UiSchemaDefinitions<S, F>` no longer takes the form data type, and types every entry as `UiSchema<unknown, S, F>`. `UiSchema`'s own `ui:definitions` key uses the same type. A definition applies to whichever field references it, so typing it by the root form's data rejected the nested keys of the field it describes.

```diff
-const definitions: UiSchemaDefinitions<MyFormData, RJSFSchema, MyContext> = { ... };
+const definitions: UiSchemaDefinitions<RJSFSchema, MyContext> = { ... };
```

A leftover three-argument `UiSchemaDefinitions<MyFormData, RJSFSchema, MyContext>` fails with `TS2707` (too many type arguments). A one- or two-argument `UiSchemaDefinitions<MyFormData>` or `UiSchemaDefinitions<MyFormData, RJSFSchema>` binds `MyFormData` to the schema type `S`: it may compile, or fail with a `TS2559` that doesn't mention the dropped parameter. Drop the form data argument in every case.

### `@rjsf/mantine`'s `onChangeOverride` now receives the change event BREAKING CHANGE

`@rjsf/mantine`'s `BaseInputTemplate` routed `onChange` and `onChangeOverride` through a single variable and handed the value to both, so an `onChangeOverride` received the input's string value. Every other theme, and `@rjsf/core`'s own `BaseInputTemplate`, pass it the raw `ChangeEvent` — which is also what `WidgetProps['onChangeOverride']` has always declared.

`onChangeOverride` now receives the `ChangeEvent` with this theme too. If you pass one to a `@rjsf/mantine` widget, read the value off the event:

```tsx
// Before
const onChangeOverride = (value: string) => setSomething(value);

// After
const onChangeOverride = (event: ChangeEvent<HTMLInputElement>) => setSomething(event.target.value);
```

A numeric field with an `onChangeOverride` now renders Mantine's `TextInput` rather than its `NumberInput`, which reports only the parsed value and never an event.
The input keeps `type="number"` (`@rjsf/core`'s `<input>` no longer does, see below); the override is what handles the input in that case, so the stepper controls and number formatting it replaces have nothing to drive.

Note that `@rjsf/core` applies `ui:emptyValue` for you when the input is cleared; an `onChangeOverride` bypasses `onChange` entirely, so handle an empty string yourself if you need that behaviour.

### `@rjsf/antd`'s `onChangeOverride` is now called for a numeric field BREAKING CHANGE

`@rjsf/antd`'s `BaseInputTemplate` wired its `InputNumber` branch straight to `onChange`.
`InputNumber` reports only the parsed value and never an event, so an `onChangeOverride` on a numeric field was never called at all.

A numeric field with an `onChangeOverride` now renders the `Input` branch (still `type="number"`) so the override receives the `ChangeEvent`, as `WidgetProps['onChangeOverride']` declares and as every other theme does. That field loses `InputNumber`'s stepper controls and formatting, which the override replaces anyway; a numeric field without an `onChangeOverride` still renders `InputNumber` as before.

### Field identity is a `FieldPath` string instead of a `FieldPathId` object BREAKING CHANGE

Every field, template and widget used to receive a `fieldPathId` prop, an object `{ $id, path, name? }` rebuilt on every render.
Because it was a new object each time, it defeated `React.memo` at every level and forced deep comparison of props to compensate.
Field identity is now two primitive strings:

- `fieldPath`: a `FieldPath` such as `friends[0].firstName`, telling **where the data lives**. It drives `onChange` writes. Property names are separated by `.`, array indexes are bracketed, and `\ . [ ]` inside a property name are backslash-escaped, so it stays unambiguous when property names contain dots or brackets. The root form is the empty string, exported as `ROOT_FIELD_PATH`.
- `id`: the DOM id such as `root_friends_0_firstName`, telling **what the element is called**. It drives `htmlFor`, focus and accessibility attributes. Ids are byte-identical to v6, including the `XxxOf` suffixes used to disambiguate `oneOf`/`anyOf` option fields, with one exception: the optional-data controls (`enableOptionalDataFieldForType`) of an object or array whose schema is itself an `oneOf`/`anyOf` take the `XxxOf`-suffixed id of the field that renders them. v6 gave those controls and the selected option's controls the same DOM id. A schema property named `''` is a second such exception: v6 dropped an empty path segment at every level, so the property took its parent's id and the two collided; it now gets a trailing separator of its own (`root_obj_`).

`FieldProps` and `FieldTemplateProps` receive both. Every other template that received `fieldPathId` (`ArrayFieldTemplate`, `ArrayFieldTitleTemplate`, `ArrayFieldDescriptionTemplate`, `ArrayFieldItemButtonsTemplate`, `CyclicSchemaExpandTemplate`, `FieldErrorTemplate`, `FieldHelpTemplate`, `ObjectFieldTemplate`, `UnsupportedFieldTemplate`) now receives `id` instead.
The `childFieldPathId` prop on `ObjectField`/`ArrayField` is gone, since `fieldPath` is always a truthful data address.
`IChangeEvent` and `FormState` no longer carry `fieldPathId` either, so an `onChange(e)`/`onSubmit(e)` handler that read `e.fieldPathId` must derive what it needs some other way — the root form's id is `idPrefix`, and `e.schemaUtils`, `e.formData` and `e.errorSchema` are unchanged.

```diff
-const { fieldPathId } = props;
-<label htmlFor={fieldPathId.$id}>
-<h2 id={titleId(fieldPathId)}>
+const { id } = props;
+<label htmlFor={id}>
+<h2 id={titleId(id)}>
```

The id helpers `titleId()`, `descriptionId()`, `helpId()`, `errorId()`, `examplesId()`, `buttonId()`, `optionalControlsId()` and `ariaDescribedByIds()` accept only a `string` id.

`FieldProps['onChange']` carries the `FieldPath` string instead of a `FieldPathList`; fields forward the `fieldPath` prop they already hold:

```diff
-onChange(newValue, fieldPathId.path, errorSchema, fieldPathId.$id);
+onChange(newValue, fieldPath, errorSchema, id);
```

`toFieldPathId()` and the `FieldPathId` type are removed.
Build paths with `toFieldPath(segment, parentPath?)` and derive what you need from them:

| Was                                    | Now                                               |
| -------------------------------------- | ------------------------------------------------- |
| `toFieldPathId(name, options, parent)` | `toFieldPath(name, parentFieldPath)`              |
| `fieldPathId.$id`                      | `id` prop, or `fieldPathToId(fieldPath, options)` |
| `fieldPathId.path`                     | `fieldPathToList(fieldPath)`                      |
| `fieldPathId.name`                     | `fieldPathToName(fieldPath, options, isMulti)`    |

`FieldPath` is a branded `string`, so a plain string (a DOM id, for example) is rejected by the compiler where a `FieldPath` is expected.
A `FieldPath` is still assignable wherever a `string` is accepted.

The `useDeepCompareMemo()` hook is removed.
It existed to hand out a stable `fieldPathId` object across renders; with two primitive strings there is nothing to stabilize.
A custom field or widget that used it for its own props can use `useMemo()`, or compare the values it cares about directly.

### `IChangeEvent` members are read-only BREAKING CHANGE

`IChangeEvent`, the event `onChange` and `onSubmit` receive, is now declared on its own instead of as a `Pick` of the `Form`'s internal state, and every member is `readonly`.
The members and their types are unchanged, except two. `formData` is now `EventFormData<T>`; see [Generic defaults are `unknown` instead of `any`](#generic-defaults-are-unknown-instead-of-any-breaking-change). And `edit` is gone: with ownership decided at mount it only restated the props you passed (whether `formData` is defined, or whether `initialFormData` was passed), so check those instead.
Readonly modifiers do not affect assignability, so a handler that reads the event or passes it on compiles as before; only code that assigns into the event breaks:

```tsx
// Before: compiled, and wrote into data the form shares with its parent
onChange={(event) => { event.formData = normalize(event.formData); setData(event.formData); }}

// After: copy out of the event into your own state
onChange={(event) => setData(normalize(event.formData))}
```

The modifier is shallow: it stops `event.formData = ...`, not a write inside `formData`.
Treat the whole event as immutable, as the guide says for received form data above.

### `ui:emptyValue` extended scope BREAKING CHANGE

`ui:emptyValue` used to only supply a value when a user actively cleared a field's widget.
It now applies whenever the field is blank for any reason — on initial render, after a form reset, or when cleared — since `getDefaultFormState()` threads `uiSchema` through its defaults pipeline (`computeDefaults()`/`getObjectDefaults()`) to pick it up.

If a field has no `formData` and no `schema.default`, and you set `ui:emptyValue` for it, that field's `formData` will now be populated with the `ui:emptyValue` on first render and after a reset, instead of staying `undefined` (and being omitted from `formData` entirely) until the user clears it once.
See [`ui:emptyValue`](../api-reference/uiSchema.md#emptyvalue).

### Shallow comparison replaces `experimental_componentUpdateStrategy` BREAKING CHANGE

`Form` and `SchemaField` now compare their props shallowly, as `React.memo` does, and keep the references of unchanged data across changes so that comparison is enough.
The `experimental_componentUpdateStrategy` prop is removed, and with it `shouldRender()`, `shallowEquals()` and the `ComponentUpdateStrategy` type from `@rjsf/utils`.

What to change:

- Remove the `experimental_componentUpdateStrategy` prop from `<Form>` and from any `globalFormOptions` read of it.
- Give `Form` stable references for props that hold functions: `customValidate`, `transformErrors`, `translateString`, `nameGenerator`, `customMergeAllOf`, `validator`, `fields`, `widgets`, `templates`, `formContext`, and a `uiSchema` carrying components such as `ui:widget`. A value recreated on every render re-derives the form's state on every render, so wrap it in `useCallback` or `useMemo`, or define it outside the render function. A changed one now takes effect at once, where v6 ignored it until another prop changed; with `liveValidate: 'onChange'`, a changed `validator`, `customValidate`, `transformErrors`, `customMergeAllOf` or `schema` also re-validates the current data. That re-validation, and the one a replaced `formData` triggers, validates with the schema resolved for the data whenever the schema utilities are unchanged (the same `schema`, `validator`, `defaultFormStateBehavior` and `customMergeAllOf`), the way an edit is validated; a replaced value shows the same live errors typing it would, and a miss that only the root schema reports (`if`/`then`, `oneOf`) shows on submit, as it does for typed data. `uiSchema` and `formContext` take effect in rendering at once, but a change to either re-validates only on the next data change, blur or submit, which matters if `ui:required` depends on state outside the form.
- Treat the `formData` you receive from `onChange`, `onBlur`, `onSubmit` and the other callbacks as immutable. It shares unchanged subtrees with the previous value, which for a controlled form is the object you passed in, so mutating it in place corrupts your own state. Copy before changing, as with any reducer.
- Treat schemas returned by `retrieveSchema()` as immutable; it may return the same instance across calls.
- Replace `shouldRender(this, nextProps, nextState)` in a class component's `shouldComponentUpdate` by extending `PureComponent`, which is the same comparison.
- Replace `shallowEquals` with `shallowEqual` from `fast-equals`.

### A typeless `oneOf`/`anyOf` of constants now renders as a select BREAKING CHANGE

A `oneOf`/`anyOf` whose options are all constants (`const` or a single-value `enum`) used to render as an unsupported field when the schema omitted `type`, because neither a field nor a widget could be resolved without one.
`SchemaField` now infers the `type` from the constant values, so the select these schemas always described actually renders ([#4666](https://github.com/rjsf-team/react-jsonschema-form/issues/4666)):

```json
{
  "oneOf": [
    { "const": "gpl", "title": "GPL" },
    { "const": "mit", "title": "MIT" }
  ]
}
```

That includes object and array constants, which render through a select whose options are labelled with their `title`, or with their JSON when they have none, whether the schema omits `type` or declares `type: 'object'`/`'array'` ([#5317](https://github.com/rjsf-team/react-jsonschema-form/issues/5317)).
Object and array constants are given the type `object`/`array`, and a declared type is kept as declared, so custom fields, templates and widgets see the type of the value they choose.
The select is rendered by `StringField`, which renders every other select, rather than by `ObjectField`/`ArrayField`, which edit a value's contents.
An empty `oneOf: []`/`anyOf: []` offers nothing to choose, so a typed object or array with one is still edited through `ObjectField`/`ArrayField`.
`getDefaultFormState()` fills such a select as a whole too, the way it fills a primitive select: a required `oneOf`/`anyOf` select defaults to the constant its own `default` names, or else its first, honoring `constAsDefaults` (including `skipOneOf`), a required `enum` select is left unfilled, and a value already picked is kept as it is. An ancestor's `default` naming one of its constants picks that one, and `ui:initialValue`/`ui:emptyValue` apply to it as they do to a primitive select. Both used to get an empty `{}`/`[]` that no option allows, and a picked object could be blended with the select's `default`.
A typed `object`/`array` whose constants are spelled as an `enum` (`{ "type": "object", "enum": [{ "a": 1 }, { "a": 2 }] }`) renders the same select, where it used to render an `ObjectField` with no control or an `ArrayField` list editor.
`omitExtraData()`, `sanitizeDataForNewSchema()` and the `ui:required` check treat such a select's value as one constant rather than a container, so `omitExtraData`/`liveOmit` keep the picked object or array whole instead of pruning it to nothing, and switching to a schema whose select doesn't offer it clears it. Picking one sanitizes the data a condition on it controls, as picking a primitive option does, where it used to leave data only the old branch allowed.
An array select offers the `radio` alias as well as `select` and `hidden`, and no longer the `checkboxes` or `files` aliases, which read the picked array as a list of selections; a multi-select array still has no `radio`.
A select, spelled as an `enum` or a `oneOf`/`anyOf` of constants, whose `type` list names more than one non-`null` type renders through `StringField`, which keeps each option's value as it is, instead of through the field for the first listed type, which rendered `NullField` for a list starting with `null` and cast every option's value to a number for a list starting with `number` (so a `true` option wrote `1`).

Most forms only gain the field they were already asking for.
Three narrower shapes change behavior, and each is worth checking:

**A schema with both `anyOf` and `oneOf`.** `optionsList()` and the option selector read `anyOf` before `oneOf`, but `isSelect()`, `sanitizeDataForNewSchema()`, `BooleanField`, the `LayoutGridField` path (`findFieldInSchema()`, `LayoutMultiSchemaField`), the defaults `getDefaultFormState()` computes, the `ui:required` check, `retrieveSchema()`'s option resolution and `getClosestMatchingOption()`'s scoring of nested properties read `oneOf` first, so a schema carrying both keywords could render one list while deciding it was a select from the other — or throw `schema cannot be inferred as a constant` during render ([#5309](https://github.com/rjsf-team/react-jsonschema-form/issues/5309)).
Every one of them now reads `anyOf` first, through the new `getXxxOfKey()` utility (an empty `anyOf: []` gives way to a non-empty `oneOf`), so a constant default comes from the `anyOf` options on screen and a `ui:required` field inside the rendered `anyOf` option is reported. The option selector follows: its `id` suffix is `__anyof_select`, where it used to say `__oneof_select` whenever a `oneOf` was present, and its options take their labels and per-option `uiSchema` from `uiSchema.anyOf`, where they used to come from `uiSchema.oneOf`.
A schema with constant options under _both_ keywords renders the `anyOf` options, and one whose `anyOf` options aren't all constants renders that `anyOf`'s option selector, where it used to render a select of the `oneOf` constants.
A schema with only one of the two keywords is unaffected.

_What to change:_ give the two keywords the same options, or drop the redundant one.

**A `type: 'boolean'` with labelled constant options.** A checkbox shows no option labels, so a boolean whose `oneOf`/`anyOf` has more than one constant option, at least one of them labelled by its `title` or a `ui:title` in the matching `uiSchema.oneOf`/`uiSchema.anyOf` entry, now defaults to a select, the same widget its typeless spelling gets ([#5309](https://github.com/rjsf-team/react-jsonschema-form/issues/5309)):

```json
{
  "type": "boolean",
  "oneOf": [
    { "const": true, "title": "Yes" },
    { "const": false, "title": "No" }
  ]
}
```

The same goes for a nullable boolean (`"type": ["boolean", "null"]`) whose options include a `null` constant, which a checkbox has no state for, labelled or not.
A single option, the usual way to spell a checkbox that must be checked, and unlabelled `true`/`false` options keep the checkbox.
A custom field chosen by `ui:field` isn't handed that default: the `uiSchema` it receives has no `ui:widget` unless the caller set one. `ui:field: 'BooleanField'` still gets the select, and so does a field registered under the schema's `$id`, which keeps its label that way.

_What to change:_ set `"ui:widget": "checkbox"` to keep the checkbox.

**A typeless falsy `const` with `constAsDefaults: 'never'`.** `getSchemaType()` returned `undefined` for a typeless schema whose `const` was falsy (`0`, `false`, `''` or `null`), which is what rendered those as unsupported fields.
A typeless `{ "const": null }` now resolves to `null` and renders through `NullField`, exactly like an explicit `{ "type": "null" }`.

At the default `constAsDefaults` setting nothing changes in the emitted data: such a property already contributed its constant as its own default.
With `defaultFormStateBehavior.constAsDefaults` set to `'never'`, which suppresses that default, a typeless `{ "const": null }` and a _required_ typeless `{ "const": false }` now write `null` and `false` into the form data on mount where nothing was written before — the first from `NullField`, the second from the required-boolean default.
Each matches what the explicit `type` spelling already did. Required `{ "const": 0 }` and `{ "const": "" }` are unaffected.

_What to change:_ nothing, if you want the two spellings to agree.
If a form relied on those keys staying absent, drop the property from the schema instead of relying on it not rendering.

### A boolean `enum` labels its values Yes/No BREAKING CHANGE

A `type: 'boolean'` field labels every `true` and `false` in its `enum` that `ui:enumNames` doesn't name with the translated Yes/No, as it already labels untitled boolean constants ([#5319](https://github.com/rjsf-team/react-jsonschema-form/issues/5319)).
The labels are in the `enumOptions` it passes to whatever widget renders it, so a select, radios or a custom widget that reads `options.enumOptions` shows them.
Only an unnamed two-value `enum` of `true` and `false` read Yes/No before, so `"enum": [true]` and a nullable `"enum": [true, false, null]` now read Yes, No and `null` where they read `true`, `false` and `null`.
`ui:enumOrder` now orders a boolean's Yes/No options, those of a two-value `enum` and the implicit `true` and `false` of a plain `{ "type": "boolean" }`, where it used to ignore them unless `ui:enumNames` was also set.
As it does for any `enum`, the order drops a value it doesn't list unless it has `'*'`, so `"ui:enumOrder": [true]` now leaves only Yes where it showed Yes and No, and an empty `"ui:enumOrder": []` leaves no options at all.
A constant option whose `title` is empty (`"title": ""`) now has an empty label where it read Yes or No, since `BooleanField` reads its options through `optionsList()`, which keeps an empty title for every other type ([#4448](https://github.com/rjsf-team/react-jsonschema-form/issues/4448)).

_What to change:_ name the values with `ui:enumNames` to keep other labels, list both values or add `'*'` to a `ui:enumOrder` meant only to put one first, drop an empty `ui:enumOrder`, and drop an empty `title` to keep Yes or No. Update tests or DOM snapshots that match the option text `true`/`false`.

### `number`/`integer` fields no longer render a native `<input type="number">` by default BREAKING CHANGE

`getInputProps()` now defaults a `number`/`integer` field to `<input type="text" inputMode="decimal|numeric" pattern="...">` instead of `<input type="number">`, avoiding the cross-browser keystroke-filtering, scroll-wheel, and locale decimal-separator quirks of a native number input.
The `pattern` still blocks a non-numeric submission the same way `required` already does, and accepts the exponent notation JavaScript renders very small and very large numbers with.
A `number` accepts either sign of exponent (`1e-7`, `1e+21`); an `integer` is only ever rendered that way from `1e21` up and always with a `+`, so a negative exponent is rejected there rather than admitting `1e-7` where `0.0000001` is refused.
The `integer` pattern accepts every spelling of a whole number the field itself produces while you type — a trailing separator and zeros (`5.`, `5.00`), and the fractional mantissa of the exponent form (`String(2 ** 70)` is `1.1805916207174113e+21`) — while still refusing an actual fraction such as `1.5`.
Set `ui:options.inputType: 'number'`, or use the `updown` widget, to keep a native number input for a field. See [#4038](https://github.com/rjsf-team/react-jsonschema-form/issues/4038).

A schema whose `type` is an array counts as a `number`/`integer` field when exactly one of its entries isn't `"null"`, so `["number", "null"]` and `["number"]` both render the numeric text input — `SchemaField` already rendered them through `NumberField`, and they used to come back as a plain text input carrying `min`/`max`/`step`.
A union of more than one non-null type, such as `["number", "string"]`, keeps the plain text input it had before.
A schema with no `type` at all but a numeric `const` counts the same way, since that is the type `SchemaField` picks its field by.

`step`, `min` and `max` only constrain a native number input, so `getInputProps()` no longer returns them for these fields, and the browser no longer range- or step-checks the value before submit.
`minimum`, `maximum` and `multipleOf` are still enforced by RJSF's own validation, which reports them as form errors.
They are still returned when the field renders a native number input, through `ui:options.inputType: 'number'` or the `updown` widget, along with `step="any"` for a `number` field with no `multipleOf` so decimals are accepted (the `updown` widget did not get that `step` before).

Because the value lives in a text input with a `pattern`, native constraint validation can now block a submit whose value doesn't match, such as legacy server data like `'yo'` loaded into a number field. When that happens `onSubmit` and `onError` never fire, and the browser shows its own message on the field instead of an RJSF error.
If you want RJSF's validation to be the only validator, set `noHtml5Validate` on the `Form`.

A `pattern` the value fails is reported by the browser as a bare "Please match the requested format", which says nothing on a field that now looks like a plain text box, so RJSF sets a `title` on the input for the browser to append to that message.
The two strings go through `translateString` as `TranslatableString.NumberInputTitle` ("Enter a number") and `TranslatableString.IntegerInputTitle` ("Enter a whole number"); translate them as you do the rest.
A `pattern` of your own replaces the derived one and takes the derived `title` with it, since that title describes a rule no longer in force: pass it as a widget prop in `core`, through `extraProps` in `shadcn` and `react-bootstrap`, or through `slotProps.htmlInput` in `mui`.
`chakra-ui`, `daisyui` and `fluentui-rc` render a fixed set of props, so a `pattern` or `title` of your own doesn't reach the input in those themes at all.

That `title` is set whenever the `pattern` is, not only when the value fails it, which has two visible consequences.
The browser shows it as a tooltip when the pointer rests on any `number`/`integer` field, and because `title` is the last fallback in accessible-name computation, a numeric field rendered with no label at all (`ui:options: { label: false }`, or a layout that hides it) is now announced by that title instead of going unnamed — the same name for every such field on the page.
Give those fields a `ui:title` or an `aria-label` if either matters, or, in the themes listed above that forward them, your own `title` or `pattern`.

A text input also lets a value that isn't a number reach `formData`: `asNumber()` keeps the raw string when `Number()` can't parse it, so a half-typed `1.2.3` or a lone `-` stays in the `number` slot, where a native number input reported an empty value instead.
Code reading `formData` from `onChange`, from `getFormData()`, or through `liveValidate` errors should expect a string there while a field is being edited.
RJSF's validation reports it as a type error, and the `pattern` blocks submitting it.

The numeric virtual keyboards that `inputMode="decimal"` and `"numeric"` request are also digit-only on some platforms: the iOS ones have no minus key, so a field that accepts negative values can't have one typed on an iPhone or iPad.
RJSF doesn't switch `inputMode` by the schema's `minimum`, because most number fields have none and would lose the numeric keyboard.
For a field that needs negative values on iOS, set `ui:options.inputType: 'number'` (or use the `updown` widget), whose keyboard does have a minus key.

Accessibility changes with the element. A native `<input type="number">` is exposed as a `spinbutton`, and `min` and `max` give it `aria-valuemin`/`aria-valuemax`, so a screen reader announces a `{ "type": "integer", "minimum": 1, "maximum": 10 }` field as "spin button, 1 to 10".
A text input with `inputMode` is a `textbox`, and `inputMode` is only a virtual-keyboard hint that assistive technology doesn't see, so the range is no longer announced.
RJSF doesn't add `role="spinbutton"` or `aria-valuemin`/`aria-valuemax` to compensate: the role promises arrow-key stepping that a text input doesn't implement, and those attributes aren't valid on a `textbox`.
For a field where the range matters to the user, state it in `ui:description` or `ui:help`, which the input is already linked to through `aria-describedby`, or set `ui:options.inputType: 'number'` (or use the `updown` widget) to keep the native semantics.

This only affects themes whose `BaseInputTemplate` renders a plain native `<input>`; `@rjsf/antd` and `@rjsf/mantine` already render their own `InputNumber`/`NumberInput` component and are unaffected, except that the plain input they fall back to when a widget supplies an `onChangeOverride` is still `type="number"`.
If your code selects the widget by its DOM `type` (`input[type="number"]`, `getByRole('spinbutton')`), select on `inputMode` (`input[inputmode="decimal"]`) or your own field/id instead.

### `getInputProps()`'s fourth parameter is now `plainNativeInput` BREAKING CHANGE

The fourth parameter of `getInputProps()` was `autoDefaultStepAny`, which only decided whether a `number` field got `step="any"`. It is now `plainNativeInput`, and it decides whether the theme renders a plain native `<input>` for numbers. It is positional and still defaults to `true`, so a call that passes it needs no edit, but its meaning changed:

- `true` (the default): a `number`/`integer` field with no `defaultType` comes back as `type: 'text'` with `inputMode` and `pattern` and without `step`, `min` or `max`, as described above. A native `number` input, whether from an explicit `ui:options.inputType` of `'number'` or a widget's `defaultType` of `'number'` (as the `updown` widget passes), returns `type: 'number'` and now also `step: 'any'` for a `number` with no `multipleOf`, so decimals are accepted.
- `false`: for a theme with its own numeric widget, such as `@rjsf/antd` and `@rjsf/mantine`. The result is what it was before: `type: 'number'` (with `step: 1` for an `integer`, or `type: 'text'` for a `number` in a locale whose decimal separator isn't `.`), never `step: 'any'`, `inputMode` or `pattern`.

`InputPropsType` gained optional `inputMode` and `pattern` members.
If your own `BaseInputTemplate` spreads the result of `getInputProps()` onto an `<input>`, they reach it automatically.
If it hands them to a component that doesn't forward unknown props to the native `<input>`, pull `inputMode` and `pattern` out and pass them to it explicitly, as `@rjsf/mui` does through `slotProps.htmlInput`; without them the field renders as a plain text input with no numeric keyboard or `pattern`.

`@rjsf/mui` now applies the `getInputProps()` attributes before `slotProps.htmlInput`, so a `step`, `min`, `max` or `accept` you pass through `slotProps.htmlInput` or `ui:options.mui.slotProps.htmlInput` takes precedence instead of being overwritten by the derived value.
If you added one of those to work around the old clobbering — a `{ "type": "integer", "multipleOf": 5 }` field given `slotProps={{ htmlInput: { step: 1 } }}`, say — it now takes effect, and the browser step-checks against your value rather than the schema's.
`BaseInputTemplateMuiProps['slotProps']['htmlInput']` is typed as `InputHTMLAttributes<HTMLInputElement | HTMLTextAreaElement>` so those `<input>`-only attributes are accepted.

### `FieldTemplateProps` gains a required `keyName` BREAKING CHANGE

`FieldTemplateProps` has a new required `keyName: string` member, the name of the field's property in its parent object, and `WrapIfAdditionalTemplateProps` picks it up too.
It carries none of the decoration `label` may have picked up — a `ui:title`, or the `(deprecated)` marker the default `deprecatedHandling` appends — so an `additionalProperties` key is read and renamed from the real key rather than from what is displayed.
Rendering a `FieldTemplate` does not change; only code that constructs `FieldTemplateProps` itself is affected, and that code fails to compile with `TS2741` until it supplies `keyName`.

A **custom `WrapIfAdditionalTemplate`** should take the key control's value from `keyName` instead of `label`, keeping `label` for the control's own label:

```tsx
const keyLabel = translateString(TranslatableString.KeyLabel, [label]);
// ...
<input type='text' id={`${id}-key`} onBlur={onKeyRenameBlur} defaultValue={keyName} />;
```

Without it, a `deprecated` additional property keyed `foo` shows `foo (deprecated)` in its key input and renames itself to that string on blur.

### `ui:hideError` now suppresses the theme's error styling BREAKING CHANGE

`ui:hideError` was only ever half honored by the themes.
It suppressed the error messages RJSF renders, but the input underneath kept whatever the theme uses to signal invalid — MUI's `Mui-error`, Bootstrap's `is-invalid`, Chakra's `invalid` flag, Fluent's `validationState`, shadcn's `border-destructive` — so a field with hidden errors still rendered a red outline with nothing explaining it ([#3684](https://github.com/rjsf-team/react-jsonschema-form/issues/3684)).
`@rjsf/mantine` went further: its widgets handed the messages to Mantine's own `error` prop, and its `AltDateWidget` and `RangeWidget` rendered an `Input.Error` apiece, so a Mantine user saw the error text itself under a directive asking for it to be hidden.
Every theme's widgets now respect the directive, so a form using `ui:hideError` loses that outline — and, on Mantine, the error text that came with it.
The directive also reaches components that were never handed it: the `oneOf`/`anyOf` selector `MultiSchemaField` renders, the widget `ArrayField` renders for a multi-select array or an array of files, and the `ArrayFieldTemplate` and `ObjectFieldTemplate`, whose `hideError` prop was declared but never set.

`@rjsf/chakra-ui`'s `CheckboxesWidget` changes in two more ways, since it had a second, unrelated source of error styling:

- It no longer flags a required field while it is still empty.
  Its inner `CheckboxGroup` was marked invalid whenever the field was required and had nothing selected, before validation had found anything wrong and whatever `ui:hideError` said, so every checkbox carried `aria-invalid="true"` and `data-invalid` from the first render.
  That state is now derived from the field's visible errors like every other error state, and there is no option to bring the old behavior back; a required checkboxes field is flagged once validation reports an error for it, as any other field is.
- Once the field does have visible errors, every checkbox is marked invalid (`aria-invalid="true"` and `data-invalid`), where a field that was not required used to mark only the surrounding fieldset.

This changes nothing about what `rawErrors` contains.
Fields and widgets are still handed the full list while errors are hidden, which is what lets a custom widget render them its own way — that is the whole point of the directive.
What changed is that the built-in widgets no longer treat a non-empty `rawErrors` as reason enough to style themselves as invalid.

If you maintain a custom theme or widget, derive your error state with the new [`getVisibleErrors()`](#new-non-validator-utility-functions), or its boolean form `hasVisibleErrors()`, rather than reading `rawErrors` directly:

```tsx
// Before: renders an error state even when `ui:hideError` is set
const hasError = rawErrors.length > 0;

// After
const hasError = hasVisibleErrors(props);
```

A custom `FieldTemplate` needs no such change.
`SchemaField` withholds `rawErrors` from the `FieldTemplate` while the errors are hidden, as it always has, and `LayoutMultiSchemaField` now passes both props on those same terms.
`LayoutMultiSchemaField` also passes the `classNames` and `style` it never did, so that same wrapper now carries `rjsf-field-error` while the field has errors to show; see [`LayoutMultiSchemaField` styles its wrapper like every other field](#layoutmultischemafield-styles-its-wrapper-like-every-other-field-breaking-change).
What a `FieldTemplate` gains is `errorSchema`, which `ArrayFieldTemplateProps` and `ObjectFieldTemplateProps` already declared: it carries every error whatever `hideError` says, so a template that renders the errors itself can reach the ones the directive withholds, which blanking `rawErrors` had left it no way to do.
A template that spreads its leftover props onto a DOM node should destructure `errorSchema` out along with the rest, or React will warn about an unknown `errorschema` attribute.

The form-level error list is unaffected; it is controlled separately by [`showErrorList`](../api-reference/form-props.md#showerrorlist).

### `LayoutMultiSchemaField` styles its wrapper like every other field BREAKING CHANGE

A discriminated `oneOf`/`anyOf` rendered through a `LayoutGridField` is rendered by `LayoutMultiSchemaField`, which builds its own `FieldTemplate` props rather than going through `SchemaField`.
It passed that template neither `classNames` nor `style`, so such a cell was the one field in a form that no `rjsf-field*` rule and no `ui:classNames` ever reached ([#5327](https://github.com/rjsf-team/react-jsonschema-form/issues/5327)).
It now passes both, built the same way `SchemaField` builds them.

Four things change for a form that already renders one of these cells:

- A CSS rule matching `.rjsf-field`, `.rjsf-field-<type>` or `.rjsf-field-error` now matches the cell's wrapper, where it never did.
  A rule written to style every field will start applying to these cells; a rule written to exclude them has to say so.
- `ui:classNames` and `ui:style` on the cell are applied by the `FieldTemplate` wrapper, and are kept out of both the options and the `uiSchema` handed to the selector widget, the way `SchemaField` has always kept them from its children (see [#439](https://github.com/rjsf-team/react-jsonschema-form/issues/439)).
  A custom selector widget that styled itself from `options.classNames`/`options.style`, or from `getUiOptions(props.uiSchema)`, no longer receives them.
  Read them from `ui:options` under a name of your own if the widget, rather than the wrapper, is what should carry them.
- The field also passes the `hidden`, `formData`, `description` and `rawDescription` props it never set.
  A `ui:widget: 'hidden'` on such a cell now hides it, where the widget used to render inside the full wrapper, and a `ui:description` or `schema.description` on it now renders.
- `ui:disabled` and a `deprecated` schema are resolved the way `SchemaField` resolves them, where the cell ignored both.
  `ui:disabled` now disables the cell and its selector widget, and re-enables them when it is `false` on a form or a grid that disables everything.
  A deprecated cell is hidden by `ui:deprecatedHandling: 'hide'`, disabled by `'disable'`, and by the `'label'` default has the deprecation marker appended to the label its `FieldTemplate` receives — not to the label the selector widget receives, which names the widget's own control, as in every other field.
  A cell with no title is left unlabelled rather than given the marker as its whole label, which is where this parts from `SchemaField`: that falls back to the property name, so only a root field reaches a label of `(deprecated)` alone, while a typeless discriminated cell is commonly titleless.

The `rjsf-field-<type>` class is `rjsf-field-undefined` for the usual discriminated schema — `{ discriminator, oneOf: [{ $ref }, ...] }` declares no top-level `type`, and `getSchemaType()` has nothing to infer one from.
That is what `SchemaField` has spelled for any typeless schema since 6.x, so the two agree, which is the only thing this change promises about it.
It is not a spelling to key a rule off: a later release may drop the type class for a schema it cannot type, or derive it from the selected option, in `getFieldClassNames()` for both fields at once.
Key off `.rjsf-field`, which every field carries whatever its schema says.

A custom field that renders its own `FieldTemplate` should build these props with the three new `@rjsf/utils` helpers rather than by hand, so it keeps carrying whatever the contract gains next:

```tsx
import {
  ERRORS_KEY,
  getDeprecatedHandling,
  getFieldClassNames,
  getUiOptions,
  getVisibleErrors,
  omitConsumedStyling,
} from '@rjsf/utils';

const uiOptions = getUiOptions(uiSchema, registry.globalUiOptions);
// A field resolves `ui:hideError` itself, in either direction, falling back to the prop, which carries the parent's
// value rather than this field's; and its errors arrive in `errorSchema`, not in the `rawErrors` a widget is handed,
// so `hasVisibleErrors(props)` is not the answer here the way it is inside a widget or a template
const hideError = uiOptions.hideError === undefined ? props.hideError : Boolean(uiOptions.hideError);
const hasErrors = getVisibleErrors({ rawErrors: errorSchema?.[ERRORS_KEY], hideError }).length > 0;
const classNames = getFieldClassNames(schema, hasErrors, uiOptions.classNames);
// `hide` means the `hidden` prop, `disable` means the `disabled` one, and `label` decorates the label handed to the
// template — but not the one handed to the widget below it
const deprecatedHandling = getDeprecatedHandling(schema, uiOptions);
// What to hand the children, with the styling this template consumed removed
const childUiSchema = omitConsumedStyling(uiSchema);
```

Pass `rawErrors` on the same terms `SchemaField` does — the full list while the errors are shown, `undefined` while they are hidden — and pass `errorSchema` through unchanged, so a template rendering the errors itself can still reach the hidden ones.

### `EnumOptionsType.value` is `unknown` BREAKING CHANGE

An enum option's `value` is typed `unknown` instead of `any`, since it can be any JSON value an `enum`, `const` or `examples` entry holds.
The helpers typed by it follow: `enumOptionsSelectValue()`, `enumOptionsDeselectValue()` and `enumOptionsValueForIndex()` return `unknown` values, and `enumOptionSelectedValue()` takes `value` as `unknown` and returns a `string` (a `string[]` when `multiple`) or its `emptyValue` (`undefined` when it is omitted) instead of `any`.
Its second type parameter is the type of `emptyValue` and defaults to `undefined`, so a call that passes `<S>` explicitly along with an `emptyValue`, as the v6 themes did, no longer compiles: drop the type arguments and let them be inferred, or pass `<S, typeof emptyValue>`.
`UIOptionsType.emptyValue` is `unknown` as well, as is every `ui:options` value read through the type's index signature, so an `emptyValue` taken from `options` and returned by `enumOptionSelectedValue()` is `unknown` until it is narrowed.
Nothing changes at runtime; only code that used a value as a narrower type stops compiling.
Compare values with `===` rather than `includes()`, which no longer accepts an `unknown` argument, and render an option's `label` rather than its value.
An `unknown` value no longer fits a `value` attribute either, and `String()` would turn every object or array value into `"[object Object]"` or a comma-joined list.
Encode the options with `enumOptionsDomValues()` instead, reading each option's DOM value at its index, and decode the attribute in the change handler with `enumOptionValueDecoder()`, which is what the built-in select widgets do; the two must use the same format, which `getOptionValueFormat(options)` reads from `ui:optionValueFormat`:

```tsx
// Before
<select value={value} onChange={(event) => onChange(event.target.value)}>
  {enumOptions.map((option) => (
    <option key={option.value} value={option.value} disabled={enumDisabled.includes(option.value)}>
      {option.value}
    </option>
  ))}
</select>

// After
const { enumOptions = [], enumDisabled = [], emptyValue } = options;
const optionValueFormat = getOptionValueFormat(options);
const domValues = enumOptionsDomValues(enumOptions, optionValueFormat);
<select
  value={enumOptionSelectedValue(value, enumOptions, false, optionValueFormat, '')}
  onChange={(event) => onChange(enumOptionValueDecoder(event.target.value, enumOptions, optionValueFormat, emptyValue))}
>
  {enumOptions.map((option, index) => (
    <option
      key={domValues[index]}
      value={domValues[index]}
      disabled={enumDisabled.some((disabledValue) => disabledValue === option.value)}
    >
      {option.label}
    </option>
  ))}
</select>
```

### `FieldTemplateProps.rawHelp` carries an element `ui:help` BREAKING CHANGE

`rawHelp` is `string | ReactElement` and carries whatever `ui:help` resolved to, where it used to be `string` and silently `undefined` for a `ui:help` given as a React element.
It is now a reliable answer to whether a field has any help at all, which is what a `FieldTemplate` gating on it wants:

```tsx
// Before: renders nothing for `'ui:help': <strong>…</strong>`, since `rawHelp` was `undefined`
{rawHelp && help}

// After: renders the element too, with no change to the code
{rawHelp && help}
```

A string `ui:help` is unaffected, whether it comes from the field's own uiSchema or from `ui:globalOptions`: `rawHelp` already carried it, because `SchemaField` has always resolved help with the globals included.
Only the element form was lost.
`@rjsf/antd`'s `FieldTemplate` gated on `rawHelp` this way and so dropped an element `ui:help` along with the field's errors; every theme and every custom `FieldTemplate` doing the same is fixed by this change.

Two things to check in code that reads `rawHelp` as a string:

- A template using it where a `string` is required — `rawHelp.length`, a template literal, or a `string`-typed prop — no longer compiles.
  Narrow it first (`typeof rawHelp === 'string' ? rawHelp : undefined`) to recover exactly the old value.
- A template that spreads its leftover props onto a DOM node should destructure `rawHelp` out along with the rest.
  React warns about the unrecognized prop either way, but an element value renders as `rawhelp="[object Object]"` where a string used to render as itself.

### Clearing a custom error now also clears it from the error list BREAKING CHANGE

A field, widget or template can raise its own error by passing an `errorSchema` as the third argument of `onChange`:

```tsx
onChange(value, fieldPath, { __errors: ['must be a company address'] });
```

Clearing it again — calling `onChange` for the same path with no `errorSchema` — used to remove the message from the field but leave it in the list the `ErrorListTemplate` renders, until the next validation replaced the list wholesale. Both now drop the entry at the same time.

This was an aliasing accident rather than a design: when the validator's own error schema is empty, `validationDataMerge()` returns the additional schema _by reference_, so the form's committed `errorSchema` and the custom-error builder were the same object. Clearing mutated it in place, which the field saw when it re-rendered, while the top-level `errors` array was never rebuilt. The form no longer mutates committed state, so the list is recomputed instead.

If you have a test asserting that a cleared custom error is still listed at the top of the form, it will now fail; the error is gone from both places.

### `noValidate` now turns off live validation on blur BREAKING CHANGE

`noValidate` disables validation everywhere else — on change, on submit, and when props change — but `liveValidate='onBlur'` ran and displayed schema errors regardless of it. It is now honored there too.

If you combined `noValidate` with `liveValidate='onBlur'` and depended on blurring a field to produce errors, drop `noValidate`:

```diff
-<Form noValidate liveValidate='onBlur' ... />
+<Form liveValidate='onBlur' ... />
```

### `FormHandle.validate()` takes only the data BREAKING CHANGE

`validate()` now takes only the data to validate: `validate(formData)`. Its `schema`, `altSchemaUtils` and `retrievedSchema` parameters are gone. They existed for the form's own validation passes, which call the internal pipeline directly. Nothing on the handle is typed by the schema or the form context any more, so the type is `FormHandle<T>` rather than `FormHandle<T, S, F>`.

To validate against another schema or validator, build the utilities for it and call its validator yourself, passing the form's `customValidate`, `transformErrors` and `uiSchema` as `validate()` did:

```diff
-const { errors } = formRef.current.validate(data, otherSchema, otherSchemaUtils);
+const { errors } = otherSchemaUtils
+  .getValidator()
+  .validateFormData(data, otherSchema, customValidate, transformErrors, uiSchema);
```

To hand `customValidate` the same defaults the form would, pass the trailing `getCustomValidateFormData`: `() => otherSchemaUtils.getDefaultFormState(otherSchema, data, true, undefined, uiSchema)`.

`validate()` also added the errors of `ui:required` fields on top. For those, merge `otherSchemaUtils.getUiRequiredErrorSchema(uiSchema, data)` into the result with `validationDataMerge()`.

### `@rjsf/daisyui` applies `ui:classNames` and `ui:style` on the field wrapper BREAKING CHANGE

`@rjsf/daisyui`'s `FieldTemplate` applied `ui:classNames` twice — once on the `WrapIfAdditionalTemplate` wrapper it renders every field in, and again on its own inner `field-template` div — while applying `ui:style` to that inner div alone ([#5327](https://github.com/rjsf-team/react-jsonschema-form/issues/5327)).
A `ui:classNames` declaring a border or padding drew it twice, one nested inside the other, and a `ui:style` written to go with those classes landed on a different element than they did.
Both now go to the wrapper, the way `@rjsf/core` and every other theme applies them.

`ui:options.daisy`'s own `className`, `style` and `theme` are unaffected.
They are this theme's per-field theming of that inner div, which is what they are for.

Two things to check:

- A CSS rule or a test that reached `ui:classNames` on `.field-template`, or read `ui:style` off it, has to look at the wrapper above it instead.
- A custom `WrapIfAdditionalTemplate` registered for this theme is now what applies both, so one that renders `<div className={classNames}>` and ignores `style` silently drops every `ui:style` on upgrading, where ignoring it was harmless before.
  Apply `style` alongside `classNames` on the element you return, in the plain branch as well as the additional-property one.

### `@rjsf/mantine` widgets reference rjsf's ids for labels and descriptions BREAKING CHANGE

Most `@rjsf/mantine` widgets passed `aria-describedby` to a Mantine component that discarded it, and the checkbox and radio groups pointed `aria-labelledby` at a Mantine label that was never rendered ([#5332](https://github.com/rjsf-team/react-jsonschema-form/issues/5332)).
Every widget now references the ids the other themes use: an input is described by the field's error, description and help ids (`root__error root__description root__help`), and a checkbox or radio group is labelled by the field's title id (`root__title`).
Accessibility is all that changes, apart from a few places where the markup your code or tests may select on is different:

- `RadioWidget`'s label has the field's title id (`root__title`) instead of the id Mantine generated for it (`root-label`).
  `CheckboxesWidget`'s label keeps that id, but `Checkbox.Group` now renders it, as a `<div class="mantine-CheckboxGroup-label">` inside the group's wrapper, where it used to be a `<label>` before the group.
  Both groups are labelled by it, where before the checkbox group had no accessible name.
  When the label is hidden (`ui:label: false`) or left out of `inputWrapperOrder`, it is still rendered with that id, `hidden`, so the group keeps its name; when the field has no label, neither group has an `aria-labelledby`.
  Select the label by `#root__title`, or better, the group by its accessible name:

  ```diff
  -container.querySelector('#root-label');
  +screen.getByRole('radiogroup', { name: 'My field' });
  ```

- `CheckboxesWidget` and `RadioWidget` apply `labelProps` to their label, except an `id`, since the label's id has to match the group's `aria-labelledby`.
  As in Mantine's groups, `labelProps` comes from `ui:options` or the Mantine theme's `CheckboxGroup`/`RadioGroup` `defaultProps`, then `ui:options.wrapperProps`, then the theme's `InputWrapper` `defaultProps`, so a theme group default wins over `ui:options.wrapperProps`.
  `CheckboxesWidget` used to ignore `labelProps` entirely.
- `RangeWidget` and `AltDateWidget` render their title, description and errors inside Mantine's `Input.Wrapper` (`.mantine-InputWrapper-root`), where they used to render them as siblings of the slider or the date parts.
  The `InputWrapper` options apply to them as to Mantine's inputs: an option in `wrapperProps`, from `ui:options` or else the Mantine theme's `Input` and `InputWrapper` `defaultProps`, wins over the same option set top-level, from `ui:options` or else the theme.
  So a theme's `wrapperProps` value beats a top-level `ui:options` one, and an option set to `undefined` in `wrapperProps` falls back to the theme's `InputWrapper` `defaultProps`.
  `inputWrapperOrder` orders or leaves out the title, description and errors, and `labelProps`, `descriptionProps`, `errorProps`, `withAsterisk`, `labelElement` and `size` style them; on `AltDateWidget`, `size` doesn't reach the date parts.
  The theme's `Input` styling props (`classNames`, `styles`, `className`, `style`, `variant` and the like) reach the wrapper too, as they do an input's.
  On `AltDateWidget`, the root element props from the theme's `Input` and `InputWrapper` `defaultProps` (`className`, `style`, `mod`, style props such as `mt`, and the `root` entry of `classNames`, `styles` and `attributes`) stay on each date part's own wrapper and aren't applied again around them all; set them in `ui:options.wrapperProps` to style the field's wrapper.
  The title keeps the field's title id (`root__title`) whatever `labelProps` says, has no `for`, and when it is hidden or left out of `inputWrapperOrder` it is rendered `hidden`, so the inputs keep their name.
  Their errors render in Mantine's single error element instead of one element per message.
  `AltDateWidget` applies an `inputContainer` around each date part rather than around them all, resolved as for a `Select`. Only the `inputContainer` of a `ui:options.wrapperProps` reaches the parts, over the theme's `Select` `wrapperProps` rather than replacing them, since the field's own wrapper applies the rest.
  Set these options on `InputWrapper` in the theme, not on `Slider`: Mantine's `Slider` spreads its own `defaultProps` on its root element.
- `RangeWidget` renders its description by the same rules as the other widgets: it shows `schema.description`, which it used to leave out, and hides the description under `ui:label: false`, where it used to show `ui:options.description` regardless.
- `RangeWidget` no longer passes Mantine input props that `Slider` doesn't take (`leftSection`, `withErrorStyles`, `loading` and the like) or the `InputWrapper` options from `ui:options` on to the slider's root element, where they became unknown attributes.
- `RangeWidget`, `PasswordWidget`, `TimeWidget`, `ColorWidget`, `FileWidget` and `DateTimeInput` name their input by the `nameGenerator`, which they ignored.
  Without one, they, `TextareaWidget` and `CheckboxWidget` name their input by the field's id (`root_address_city`), as the other widgets do, where they used the bare property name (`city`, or `""` at the root).
  Update any selector or form-data parsing that relied on the old `name`.
- Every widget that renders a description, except `CheckboxWidget`, applies `descriptionProps` from `ui:options`, `ui:options.wrapperProps` or the Mantine theme's `defaultProps`, resolved as Mantine resolves them, where only `ui:options.wrapperProps.descriptionProps` used to reach it. The description is always rendered in a `div`, including under a `wrapperProps.descriptionProps`, which used to turn it back into Mantine's default `<p>`.
- Mantine's error element has the field's error id (`root__error`) instead of the id Mantine generated for it (`root-error`), whatever `errorProps.id` says.
  `FieldErrorTemplate` still renders a hidden copy of the errors, but gives it that id only when no other element has it, so beside Mantine's error element the copy has no id.
  `ObjectFieldTemplate` and `ArrayFieldTemplate` show the object's or array's own errors with that id, below its fields, where they used to be hidden, except those a `oneOf`/`anyOf` selector already shows.
  A custom `ObjectFieldTemplate` or `ArrayFieldTemplate` renders them only if it reads `rawErrors` itself.
  Inputs are now described by the error they show, including a `oneOf`/`anyOf` selector, which had no error to reference, and a checkbox's error is read once rather than twice.
  The widget of a `oneOf`/`anyOf` option no longer shows the errors its selector shows as well, nor is it marked invalid by them.
  `CheckboxWidget` renders its error below the checkbox, where Mantine's `Checkbox` rendered it below the label, and ignores `errorProps`, as before.
  A custom `FieldErrorTemplate` still renders, alongside Mantine's error. If it gives its element the field's `errorId(id)`, as `@rjsf/core`'s does, that id is then on two elements, so give it another id, or leave `'error'` out of `inputWrapperOrder` so that Mantine renders none.
  A custom widget or `ui:field` that describes its input by `ariaDescribedByIds(id)` still reaches that hidden copy, as does `@rjsf/core`'s `RatingWidget`, which has no Mantine counterpart, and a widget whose `inputWrapperOrder` leaves out `'error'`, whose errors are announced but not shown.
  Select an error by `#root__error`, or better, the input by its accessible description:

  ```diff
  -container.querySelector('#root-error');
  +expect(screen.getByRole('textbox')).toHaveAccessibleDescription(/must be string/);
  ```

- Mantine's success message, rendered for a `success` option, has the id from `successProps.id`, else `root-success`, even when `wrapperProps` has an `id`, and inputs are described by it when it is shown.
  `RangeWidget` and `AltDateWidget` render it once, on the field's wrapper, and describe the slider thumb or each date part by it; a date part no longer renders one of its own, even from the theme's `Select` `defaultProps`.
  `CheckboxesWidget` and `RadioWidget` describe each option by it, rather than the group, like the field's other ids.
- Each `AltDateWidget` date part is labelled by the field's label followed by the part, so a query by the part alone no longer matches when the field has a label, which falls back to its property name when there is no `title`:

  ```diff
  -screen.getByRole('combobox', { name: 'year' });
  +screen.getByRole('combobox', { name: 'My field year' });
  ```

Snapshot tests of Mantine forms will change too, as inputs gain the rjsf ids in `aria-describedby` and the hidden copy of the errors loses its id beside Mantine's error element.
An assertion on an input's accessible description (`toHaveAccessibleDescription()`) now includes the field's help text and errors along with its description.
`RangeWidget`'s `aria-describedby` moves from the slider's root element to its focusable `role="slider"` thumb.

### `getDisplayLabel()` reads a boolean's widget from the reduced ui options BREAKING CHANGE

A `boolean` field left to its default widget is a checkbox, which draws its own label, so `getDisplayLabel()` reports `false` for it and the theme's `FieldTemplate` renders none.
It decided that from the `ui:widget` key alone, and `ui:options: { widget: 'radio' }` is the same choice spelled the other way, so a `boolean` naming its widget that way was treated as having no widget at all: the template suppressed the label, leaving a radio group or a select with nothing above it ([#5318](https://github.com/rjsf-team/react-jsonschema-form/issues/5318)).

`FieldTemplateProps.displayLabel` is now `true` for that spelling, in every theme.
A `FieldTemplate` of your own needs no change; a snapshot of a form with a `boolean` field whose widget is set through `ui:options.widget` gains that field's label.

Naming the checkbox a `boolean` already resolves to, by the `CheckboxWidget` key it is registered under, now counts as naming no other widget and reports `false`.
A checkbox renders the field's label itself after its input, so `ui:widget: 'CheckboxWidget'` had every theme render a second label beside the widget's own; that field now carries one label again.
The `checkbox` alias still reports `true`, since that is the spelling a `FieldTemplate` matches to lay a checkbox field out itself, taking over the field's description along with its label.
A widget registered under some other key, or passed to `ui:widget` as a component, cannot be recognized by name and still reports `true`, so a self-labelling widget of your own set that way renders a label twice — see [#5389](https://github.com/rjsf-team/react-jsonschema-form/issues/5389).

### `@rjsf/daisyui`'s date and label markup changed BREAKING CHANGE

`@rjsf/daisyui` rendered its field label from the schema type rather than from the widget, and rendered it whether or not the field had a title, so several kinds of field were labelled wrongly or not at all; its `DateWidget` mangled a `format: 'date'` value at both ends ([#5318](https://github.com/rjsf-team/react-jsonschema-form/issues/5318)).
The theme's API only gained exports, so the migration is limited to snapshot tests of a daisyui form, stylesheets targeting these elements, and anything that stored what its date widget committed.

**What a `format: 'date'` field commits** is now `YYYY-MM-DD`, the shape `@rjsf/core`'s native date input and every other theme produce, where it was a full UTC date-time such as `2020-05-03T00:00:00.000Z` — not a `date`, so `ajv-formats` rejected the value the user had just picked.
Closing the picker with no day chosen commits `ui:emptyValue` (`undefined` by default) rather than `''`, which failed that format the same way.
A stored value carrying a time names the day its own text spells, whatever separator, time and zone follow it, so a `2020-05-03T00:00:00.000Z` or a `2020-05-03T12:00:00Z` reads as 3 May.
The exception is an instant with no zone of its own landing on local midnight, which is what the widget writes for a field declaring a date-time — the day the user picked, in the zone they picked it in — and so names that local day.
A value stamped with an offset of its own came from somewhere else and is read as its text reads, however that offset resolves for the reader.

Exactly twelve hours ahead of UTC those two rules describe one value.
A day picked there is stored as the midday UTC instant of the day _before_ — the same instant, and the same text but for the milliseconds `toISOString()` always emits, as a backend's own midday-UTC value for that earlier day.
A midday value therefore reads as the local day its instant begins, 4 May rather than 3 May, because reading the text first instead would move every day this widget itself stored in a zone ahead of UTC.
Deciding the reading from the format the field declares, rather than from the value's shape, is [#5395](https://github.com/rjsf-team/react-jsonschema-form/issues/5395).
Anything asserting on the committed shape sees `2020-05-03` where it saw a date-time.
A value the widget cannot read at all is now left alone when the picker is dismissed, where it used to be replaced by the empty value.

**Neither picker stores anything unless the user chose a date.** Opening a picker and dismissing it used to commit whatever it was holding, so a `format: 'date'` field holding a date-time had the day the widget read out of it written back over the value — data the user never touched, rewritten by a glance at the calendar.
A `format: 'date-time'` or `iso-date-time` field is left alone the same way, including the seconds neither picker can set.
Picking a day is still the request to store one, and still rewrites a date-time in a `date` field as the date that field's format requires.

**Either picker commits the shape the field's `format` declares**, rather than the one its own name suggests: a date for `format: 'date'`, a UTC ISO string for `date-time`, and a naive local date-time for `iso-date-time`.
`widgetMap` resolves `ui:widget: 'date'` and `ui:widget: 'date-time'` on any `string` schema, whatever `format` it declares, so `{ 'ui:widget': 'date' }` on a `format: 'date-time'` field used to commit a value that field's own format rejects, and `{ 'ui:widget': 'date-time' }` on a `format: 'date'` field likewise.

**What the markup looks like:**

- A field with no title renders no `<label>` at all, where an empty one used to take up space — every root field and array item, along with the lone required `*` on an untitled array item.
- A `boolean` rendered through anything other than a checkbox or toggle now has a label, where it had none.
  Those two widgets render their own after the input, and so does the description.
  Which widget renders the label is decided from the registry, so a widget you register as `CheckboxWidget` or `toggle` — a wrapper around the theme's own, or a replacement — is the one that renders it.
  A widget registered under any other key gets the template's label as well as its own.
- A widget rendering a _group_ of controls marks it with `role='radiogroup'`/`role='group'`, carries the field's `id`, and names itself from the label through `aria-labelledby` (a `__label` id suffix, since `TitleFieldTemplate` claims `titleId()`). `AltDateWidget`'s year/month/day labels reach their selects through the new [dateElementId()](#new-non-validator-utility-functions).
- A `hidden` field renders only its children, as in `@rjsf/core`.
  An `additionalProperties` entry hidden with `ui:widget: 'hidden'` therefore loses its key input and remove button, and a field hidden by `deprecatedHandling: 'hide'` — the other thing `SchemaField` reports through that prop — is hidden rather than rendered in full.
- `ToggleWidget` renders the field's label beside the switch, where it rendered `ui:options.label` — a flag, not text, so that label was always empty.
  It shares one input component with `CheckboxWidget`, which wraps the input in a `<span>` where both used a `<div>` a `<label>` does not permit, and makes the checkbox honor `ui:autofocus`.
  Both take the input's `required` attribute from `schemaRequiresTrueValue()`, as the `*` beside it already did: HTML5 constraint validation refuses an unchecked required box, so a boolean a parent merely lists as `required` — whose `false` the schema accepts, and which RJSF fills in as `false` — could not be submitted at all, with nothing on the screen to say why.
- `BaseInputTemplate` no longer renders a second, `display: none` label for its input, and the date widgets' triggers show `ui:placeholder` rather than `schema.title`.
- Both date widgets open their picker from a `<button type='button'>` where they used a `<div role='button' tabindex='0'>`, so the field's label reaches the control it names.
  A stylesheet or snapshot targeting that `div`, or its `role`/`tabindex`, needs updating.
  That label names the button through its own `htmlFor`, whichever `FieldTemplate` rendered it, and the selected value is exposed as the button's description under a `__value` id — a name from outside an element replaces its own contents, so the value would otherwise never be announced.
- Both date widgets honor `ui:disabled` and `ui:readonly`, which neither read before: the picker opened from a disabled field and committed a new value over it.
  A second press on the trigger, or on the label pointing at it, now closes the picker and commits, where it closed and reopened in one gesture.
  Escape discards the date it was closed on, where the calendar kept it and the next close committed it.
- `CheckboxesWidget` no longer puts `required` on every option box, which HTML5 constraint validation read as "check all of them" and which blocked the submit of a required array outright.
  `RadioWidget` keeps the attribute, where the browser does read same-named inputs as one group.
- `CheckboxWidget`, `ToggleWidget` and both date widgets' triggers set `aria-describedby`, so the description, errors and help around them are announced with the control.
- `CheckboxWidget` and `ToggleWidget` render the `*` for a required field whose schema is not a `boolean`, which `ui:widget: 'toggle'` can be pointed at: the template's label used to carry that marker, and the widget draws one of its own only for a `boolean` that has to be `true`.
- Both date widgets' triggers show the translated `AriaDateLabel` string, "Select a date", for a field with no value, no `ui:placeholder` and no title, where the button rendered empty — blank on the screen and nameless to a screen reader.
  Escape also restores the month the stored value names, where the calendar reopened on the month the user had navigated away to and discarded.
- `getGroupProps()` and `getTriggerDescribedBy()` are exported from `@rjsf/daisyui`, which also re-exports `@rjsf/utils`' new [fieldLabelId()](#new-non-validator-utility-functions) and [triggerValueId()](#new-non-validator-utility-functions).
  A custom group widget takes its `role` and `aria-labelledby` from the first; a custom control that displays its own value and opens a popup to change it takes its `aria-describedby` from the second, which decides whether the value is referenced at all from the same predicate the built-in widgets use.
  A widget or `FieldTemplate` of your own can name itself the way the built-in ones do rather than hard-coding the id suffixes.

### `enumOptionValueEncoder()` is removed in favor of `enumOptionsDomValues()` BREAKING CHANGE

`enumOptionValueEncoder()` encoded one option at a time, but in the `realValue` format an option's DOM value now depends on the rest of the list: options whose `String()` is the same, such as `1` and `'1'` or `true` and `'true'`, used to share a DOM value, so the second of them could not be picked and picking it wrote the first one's value ([#5315](https://github.com/rjsf-team/react-jsonschema-form/issues/5315)).
The new [`enumOptionsDomValues()`](#new-non-validator-utility-functions) encodes the whole list in one pass, giving each of those options its prefixed index (`__rjsf_index:1`) instead, and `enumOptionValueDecoder()` and `enumOptionSelectedValue()` encode against the list the same way.
It also encodes an object, array, `null` or empty string option, and a string starting with the prefix, as its index prefixed with the new `ENUM_OPTION_INDEX_PREFIX` constant, where v6 encoded objects and arrays as the bare index and `null` as the empty string, so code that parses these DOM values itself needs to expect the prefix ([#5309](https://github.com/rjsf-team/react-jsonschema-form/issues/5309)).

A custom widget encodes its options once per render and reads each option's value at its position:

```tsx
// v6
value={enumOptionValueEncoder(option.value, index, optionValueFormat)}
// v7
const domValues = enumOptionsDomValues(enumOptions, optionValueFormat);
// ...
value={domValues[index]}
```

For options from `groupEnumOptions()`, read `domValues[option.index]`, since `index` is the option's position in the ungrouped list.

### `@rjsf/utils` schema functions take a `SchemaContext` in place of the `validator` BREAKING CHANGE

The validator-based schema functions in `@rjsf/utils` used to take the `customMergeAllOf` and `defaultFormStateBehavior` of a form as separate parameters.
Each of those functions had to copy them, one by one, into every schema function it called, and several calls left one out, so a `customMergeAllOf` silently stopped applying partway down a call chain ([#4383](https://github.com/rjsf-team/react-jsonschema-form/pull/4383), [#4385](https://github.com/rjsf-team/react-jsonschema-form/issues/4385)).

Those settings now travel together with the `validator` in a `SchemaContext`:

```ts
interface SchemaContext<S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType> {
  readonly validator: ValidatorType<S, F>;
  readonly customMergeAllOf?: CustomMergeAllOf<S>;
  readonly defaultFormStateBehavior?: DefaultFormStateBehavior;
}

type SchemaParserOptions<S extends StrictRJSFSchema = RJSFSchema> = Pick<SchemaContext<S>, 'customMergeAllOf'>;
```

`SchemaParserOptions` is the subset of a `SchemaContext` that decides which sub-schemas a form validates against.
It is what `schemaParser()` takes as its optional second parameter, and the `customMergeAllOf` it holds is also taken in the options of the `compileSchemaValidators()` and `compileSchemaValidatorsCode()` functions of `@rjsf/validator-ajv8` and `@rjsf/validator-ata`, so a precompiled validator can be compiled with the same `customMergeAllOf` the form uses; see [precompiled validators](../usage/validation.md#precompiled-validators).
A form's `SchemaContext` can be passed wherever `SchemaParserOptions` are expected.

Every function that took a `validator` takes a `SchemaContext` in its place, and passes it along whole to every schema function it calls, so dropping the `customMergeAllOf` would also mean dropping the `validator`.
The separate `customMergeAllOf` and `defaultFormStateBehavior` parameters are gone, and the parameters that followed them move up a position; every other parameter, `rootSchema` included, is unchanged:

```diff
-const resolvedSchema = retrieveSchema(validator, schema, rootSchema, formData, customMergeAllOf);
-const isSelectField = isSelect(validator, schema, rootSchema, customMergeAllOf);
+const context: SchemaContext = { validator, customMergeAllOf, defaultFormStateBehavior };
+const resolvedSchema = retrieveSchema(context, schema, rootSchema, formData);
+const isSelectField = isSelect(context, schema, rootSchema);
```

| Function                      | v6 parameters                                                                                       | v7 parameters                                                                                     |
| ----------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `findFieldInSchema()`         | `validator, rootSchema, schema, path, formData?, customMergeAllOf?`                                 | `context, rootSchema, schema, path, formData?`                                                    |
| `findSelectedOptionInXxxOf()` | `validator, rootSchema, schema, fallbackField, xxx, formData?, customMergeAllOf?`                   | `context, rootSchema, schema, fallbackField, xxx, formData?`                                      |
| `getClosestMatchingOption()`  | `validator, rootSchema, formData, options, selectedOption?, discriminatorField?, customMergeAllOf?` | `context, rootSchema, formData, options, selectedOption?, discriminatorField?`                    |
| `getDisplayLabel()`           | `validator, schema, uiSchema?, rootSchema?, globalOptions?, customMergeAllOf?`                      | `context, schema, uiSchema?, rootSchema?, globalOptions?`                                         |
| `getFirstMatchingOption()`    | `validator, formData, options, rootSchema, discriminatorField?`                                     | `context, formData, options, rootSchema, discriminatorField?`                                     |
| `getFromSchema()`             | `validator, rootSchema, schema, path, defaultValue, customMergeAllOf?`                              | `context, rootSchema, schema, path, defaultValue`                                                 |
| `getUiRequiredErrorSchema()`  | _new in v7_                                                                                         | `context, rootSchema, uiSchema?, formData?, uiSchemaDefinitions?, globalUiOptions?, formContext?` |
| `isFilesArray()`              | `validator, schema, uiSchema?, rootSchema?, customMergeAllOf?`                                      | `context, schema, uiSchema?, rootSchema?`                                                         |
| `isMultiSelect()`             | `validator, schema, rootSchema?, customMergeAllOf?`                                                 | `context, schema, rootSchema?`                                                                    |
| `isSelect()`                  | `validator, theSchema, rootSchema?, customMergeAllOf?`                                              | `context, theSchema, rootSchema?`                                                                 |
| `omitExtraData()`             | `validator, schema, rootSchema?, formData?, customMergeAllOf?`                                      | `context, schema, rootSchema?, formData?`                                                         |
| `retrieveSchema()`            | `validator, schema, rootSchema?, rawFormData?, customMergeAllOf?, resolveAnyOfOrOneOfRefs?`         | `context, schema, rootSchema?, rawFormData?, resolveAnyOfOrOneOfRefs?`                            |
| `sanitizeDataForNewSchema()`  | `validator, rootSchema, newSchema?, oldSchema?, data?, customMergeAllOf?`                           | `context, rootSchema, newSchema?, oldSchema?, data?`                                              |

`retrieveSchema()` is the one to double check: a v6 call passing `resolveAnyOfOrOneOfRefs` passed `customMergeAllOf` (or `undefined`) before it, so drop that argument rather than only replacing the `validator`.

`getDefaultFormState()` is the exception: it had the longest list of optional parameters, most of them easy to pass in the wrong order, so it now takes a `SchemaContext` followed by a `GetDefaultFormStateProps` object:

```diff
-getDefaultFormState(validator, schema, formData, rootSchema, false, defaultFormStateBehavior, customMergeAllOf, undefined, uiSchema);
+getDefaultFormState({ validator, customMergeAllOf, defaultFormStateBehavior }, { schema, formData, rootSchema, uiSchema });
```

Its props are `schema`, `formData?`, `rootSchema?`, `includeUndefinedValues?`, `initialDefaultsGenerated?`, `uiSchema?` and `uiSchemaDefinitions?`, with the same meanings and defaults the positional parameters had.

`createSchemaUtils()` and `SchemaUtilsType.doesSchemaUtilsDiffer()` take a `SchemaContext` and the `rootSchema`:

```diff
-const schemaUtils = createSchemaUtils(validator, rootSchema, defaultFormStateBehavior, customMergeAllOf);
+const schemaUtils = createSchemaUtils({ validator, defaultFormStateBehavior, customMergeAllOf }, rootSchema);
```

`SchemaUtilsType`'s own methods supply the context and root schema themselves, so they are unchanged.

`ValidatorType` keeps its v6 signatures: `validateFormData()`, `isValid()` and `rawValidation()` take no `SchemaContext`, so a custom validator needs no change for this release.
The context carries a `validator`, so handing one to a validator would have meant every implementation discarding the validator it was given in favor of itself; the two things a validator actually needed the settings for are supplied another way instead.

`validateFormData()` takes one new optional trailing parameter, `getCustomValidateFormData`: a function returning the form data to hand `customValidate`, with the defaults already applied.
`Form` supplies it from its own `SchemaUtils`, so those defaults honor the form's `customMergeAllOf` and `defaultFormStateBehavior`, which they never did before.
Left out, the validator computes them itself exactly as it did in v6, so a direct caller keeps working:

```diff
 validator.validateFormData(formData, schema, customValidate, transformErrors, uiSchema);
+validator.validateFormData(formData, schema, customValidate, transformErrors, uiSchema, () => schemaUtils.getDefaultFormState(schema, formData, true, undefined, uiSchema));
```

It is a function rather than the data itself for two reasons: defaults that legitimately come out `undefined` are then an answer the validator can tell apart from "nothing was supplied", and an implementation that computes the defaults its own way never makes the caller compute them as well.

A **precompiled** validator takes the form's `customMergeAllOf` at construction rather than per call, since it is tied to one root schema compiled once:

```diff
-const validator = createPrecompiledValidator(validateFns, schema);
+const validator = createPrecompiledValidator(validateFns, schema, { customMergeAllOf });
```

It is used when the validator resolves its own root schema to check the schema it is handed, which is what previously failed with "The schema associated with the precompiled validator differs from the rootSchema provided for validation" for a form with a `customMergeAllOf` and an `allOf` in its root schema.
Give the same `customMergeAllOf` to `compileSchemaValidators()` or `compileSchemaValidatorsCode()`, in their options, so the sub-schemas they record are the ones that merge produces ([#5338](https://github.com/rjsf-team/react-jsonschema-form/issues/5338)).
Compiled without it, a `customMergeAllOf` that normalizes the merged result — sorting `required`, adding a `title` — builds sub-schemas whose hashes the precompiled map does not hold, and `getValidator()` throws "No precompiled validator function was found for the given schema".

The `computeSkipPopulate()` callback of [`defaultFormStateBehavior.arrayMinItems`](../api-reference/form-props.md#arrayminitemscomputeskippopulate) receives the `SchemaContext` in effect in place of the `validator`, so any schema function it calls can be handed the form's `customMergeAllOf` too:

```diff
-computeSkipPopulate: (validator, schema, rootSchema) => !isSelect(validator, schema.items, rootSchema),
+computeSkipPopulate: (context, schema, rootSchema) => !isSelect(context, schema.items, rootSchema),
```

The helpers that are exported only through deep imports of `@rjsf/utils/lib/schema/*` follow the same rule.
`computeDefaults()`, `getObjectDefaults()`, `getArrayDefaults()`, `getDefaultBasedOnSchemaType()`, `ensureFormDataMatchingSchema()` and `calculateIndexScore()`, as well as the `retrieveSchema()` helpers such as `retrieveSchemaInternal()`, `resolveSchema()` and `resolveDependencies()`, take a `SchemaContext` in place of the `validator` and no longer take a `customMergeAllOf` or `defaultFormStateBehavior`, including as members of the props object `computeDefaults()` and its siblings take.

Four places that used to drop a setting now apply it:

- `SchemaUtilsType.omitExtraData()` never passed the form's `customMergeAllOf` on, so the `allOf`s it merged were always merged the default way.
- An `allOf` reached through a `$ref` option of a `oneOf` inside `dependencies` was always merged the default way.
- The defaults handed to `customValidate` were computed with neither the `customMergeAllOf` nor the `defaultFormStateBehavior` of the form.
- The precompiled validators of `@rjsf/validator-ajv8` and `@rjsf/validator-ata` check the schema they are handed against their root schema, resolving that root schema when it isn't an exact match. They resolved it with the default `allOf` merge, so under `liveValidate` a form with a `customMergeAllOf` and an `allOf` in its root schema failed with "The schema associated with the precompiled validator differs from the rootSchema provided for validation".
  They now resolve it with the `customMergeAllOf` they were constructed with, so the error no longer comes from `validateFormData()`, nor from a schema function scoring `oneOf`/`anyOf` options or resolving a condition against that root schema.

A form that sets either of them sees it applied in those places from now on.

With a **precompiled** validator, give the form's `customMergeAllOf` to `createPrecompiledValidator()`, as above, so the root-schema check resolves with the merge the form resolves with, and to `compileSchemaValidators()` or `compileSchemaValidatorsCode()`, so the sub-schemas the form validates against are the ones compiled.

## New Features

### `getFormData()` and the `FormHandle` type

Think of `formData` and `initialFormData` as `value` and `defaultValue` on an `<input>`.
With `initialFormData` the form owns the data, and until now the only way to see it was `onChange`, so autosave, an "unsaved changes" guard, or a submit button rendered outside the form all had to copy every change into your own state.
`getFormData()` reads it on demand:

```tsx
function Editor({ record }) {
  const formRef = useRef<Form>(null);

  useEffect(() => {
    const timer = setInterval(() => api.draft(formRef.current?.getFormData()), 30_000);
    return () => clearInterval(timer);
  }, []);

  return <Form ref={formRef} schema={schema} validator={validator} initialFormData={record} />;
}
```

Two things to know:

- **It reads committed data.** An edit or `setFieldValue()` in the same tick is not visible until React commits it, so read after the commit (in tests, after `await act(...)`).
- **It returns what the form renders.** With a `formData` prop that is the prop itself: a proposal your `onChange` handler declined is never rendered and never returned.

`FormHandle<T>` names every supported ref member and `Form` implements it. The deprecation note above shows how to type a ref against it.

### `ui:initialValue` and `ui:required`

Two new uiSchema directives complement the extended `ui:emptyValue` above, for forms that want to control a field's initial value or required-ness without editing the underlying schema:

- **`ui:initialValue`** pre-fills a field on initial render and after a form reset. It takes priority over `schema.default`, but never overrides `formData` that's already been provided. This is useful for a field — often hidden — that a particular form wants to fix to a known value, e.g. a `country` field defaulted to `'US'` for a US-only form.
- **`ui:required`** overrides a field's `required` status from the UI side only. Setting it to `true` shows the required indicator and adds the field to the effective required set used for validation, even if the schema doesn't mark it required. Setting it to `false` hides the indicator on a schema-required field, but does **not** suppress schema-level validation — pair it with `ui:initialValue` or `ui:emptyValue` so the field always has a value, or you'll get a `console.warn`. `ui:required` must be set per field; it is not honored via `ui:globalOptions`.

See [`ui:initialValue`](../api-reference/uiSchema.md#initialvalue) and [`ui:required`](../api-reference/uiSchema.md#required) for details and examples.

`ui:required` is enforced by walking the rendered form itself rather than by rewriting the schema handed to your validator, so it works the same way regardless of which validator you use — including the precompiled validators (`AJV8PrecompiledValidator` from `@rjsf/validator-ajv8` and `ATAPrecompiledValidator` from `@rjsf/validator-ata`), which enforce it too. The one difference from a schema-level required error: a `ui:required` error is built by RJSF, not your validator, so it doesn't pass through a custom `transformErrors` function and doesn't carry validator-specific fields like AJV's `params.missingProperty`. See [`ui:required`](../api-reference/uiSchema.md#required) for details.

### `ui:options.optgroups` for grouped `<select>` options

Every theme's `SelectWidget` now supports grouping enum options into labeled sections (rendered as `<optgroup>` elements, or each theme's closest equivalent — see the [`optgroups` docs](../api-reference/uiSchema.md#optgroups) for the specifics per theme) via `ui:options.optgroups`:

```tsx
const uiSchema: UiSchema = {
  'ui:options': {
    optgroups: {
      Latin: ['lorem', 'ipsum', 'dolorem'],
      Greek: ['alpha', 'beta', 'gamma'],
    },
  },
};
```

Keys are the group labels; values are arrays of enum values belonging to that group. Enum values not listed in any group render ungrouped after the groups. This is purely additive — existing forms are unaffected unless `optgroups` is set.

### `propertyNames.enum` renders the key as a dropdown

An object whose `propertyNames` enumerates the allowed key names now renders each `additionalProperties`/`patternProperties` key as a dropdown of those names rather than a free-text input, in every theme:

```tsx
const schema: RJSFSchema = {
  type: 'object',
  additionalProperties: { type: 'boolean' },
  propertyNames: { enum: ['darkMode', 'betaBanner', 'offlineCache'] },
};
```

A name another key already holds is left out of the dropdown, and the add button creates the new property under the first allowed name that is still free instead of `newKey`.
`canExpand()` hides the add button once every allowed name is taken, the way it already does at the `maxProperties` limit, so a **custom `ObjectFieldTemplate`** that calls it picks this up on its own.
A `propertyNames` without an `enum`, such as one constraining names by `pattern`, keeps the free-text input, so existing forms are unaffected.

The names reach `WrapIfAdditionalTemplate` as a new optional `propertyNamesEnum` prop on `FieldTemplateProps`/`WrapIfAdditionalTemplateProps`.
A **custom `FieldTemplate`** that lists the props it forwards to `WrapIfAdditionalTemplate` one by one, rather than spreading them, has to add `propertyNamesEnum` to that list for the dropdown to appear, and `keyName` for the key it renders to be the real one (see [`FieldTemplateProps` gains a required `keyName`](#fieldtemplateprops-gains-a-required-keyname-breaking-change)).
A **custom `WrapIfAdditionalTemplate`** renders the dropdown by handing the prop to the new `AdditionalPropertyKeySelect` component from `@rjsf/utils`, which resolves the theme's own `SelectWidget`:

```tsx
{propertyNamesEnum ? (
  <AdditionalPropertyKeySelect
    id={`${id}-key`}
    label={keyLabel}
    value={keyName}
    propertyNamesEnum={propertyNamesEnum}
    onKeyRename={onKeyRename}
    disabled={disabled}
    readonly={readonly}
    required={required}
    registry={registry}
  />
) : (
  <input type='text' id={`${id}-key`} onBlur={onKeyRenameBlur} defaultValue={keyName} />
)}
```

### Multiple types and unconstrained properties can be edited through the fallback UI

JSON Schema lets a `type` be a list of types.
v6 rendered the first type in that list and gave no way to reach the others, and it rendered a property described only by `additionalProperties: true` as a field for whatever type the data happened to hold, with the same one-way door.
Turning on the [useFallbackUiForUnsupportedType](../api-reference/form-props.md#usefallbackuiforunsupportedtype) prop now renders both through `FallbackField`, which pairs a type selector with the field for the type currently chosen:

```tsx
const schema: RJSFSchema = {
  type: 'object',
  properties: {
    // a selector offering exactly these three types
    multi: { type: ['string', 'number', 'boolean'] },
    // a selector offering every JSON Schema type, for each key added here
    anything: { type: 'object', additionalProperties: true },
  },
};

render(<Form schema={schema} validator={validator} useFallbackUiForUnsupportedType />, document.getElementById('app'));
```

Switching the type casts the value that is already there where it can (a number to its string spelling, a string to the number it reads as) and starts from an empty value where it cannot, such as an object, an array, or a number from text that reads as no number at all.
The selector also now offers `integer` and `null` alongside the five types it offered in v6, and starts on the type the current form data has.
Every other keyword of the schema still describes the value, so a union declaring `properties`, `items`, `format` or `minimum` keeps them for whichever type is in effect.

A schema pairing multiple types with an `anyOf` or `oneOf` gets both selectors: the type selector wraps the option selector, and each option renders for whichever type is currently chosen.
Every member of the union is therefore reachable from within an option, where in v6 an option could only ever be the first type in the list.

Four things are deliberately unchanged:

- **A nullable type** (`['string', 'null']`) still renders as a plain `string` field, since [getSchemaType()](../api-reference/utility-functions.md#getschematype) resolves it to that single type. Only a union of more than one non-`null` type gets a selector.
- **With the prop off** (the default), the first type in the list still wins, exactly as in v6. The selector is the opt-in fallback UI, so nothing changes for a form that hasn't enabled it. A union paired with an `anyOf` or `oneOf` stays one-way too, since the option selector alone cannot reach the other types.
- **A schema pinning its value with an `enum`, a `const`, or an `anyOf`/`oneOf` of constants** renders as the select or constant field it always has, with no type selector, since switching type would only cast a value the user picked into one the schema rejects.
- **A field whose `ui:widget` is a component** renders through that control alone, with no type selector, the same way one with a `ui:field` does.
  A control written for that schema handles the types it allows, so wrapping it would pin the schema to one of them and cast the value on every switch.
  A `ui:widget` naming a widget by string is a theme's control for a single type, which is the choice the selector is there to make, so it renders within the selector instead — and is dropped for a chosen type the theme has no implementation of.
  A schema with no usable type of its own — an unrecognized `type`, or an `additionalProperties` entry left unconstrained — still gets a selector, since it lists no types for such a control to handle, and the widget renders within it for whichever type is chosen.
  A list naming an unrecognized type alongside a recognized one offers only the recognized ones, `null` included: a `['foo', 'null']` offers `null` and nothing else.

See [Multiple types](../json-schema/single.md#multiple-types) for details.

### New types

The following new types were added to `@rjsf/utils`:

- **`MarkdownTemplateProps<T, S, F>`**: the props a `MarkdownTemplate` receives, generic over the same `<T, S, F>` as every other template's props. `children` is the markdown string to render; `uiSchema` and `registry` are picked from the form's base props, so an implementation can read `ui:options`, reach `registry.translateString`, or fall back to another template.
- **`FieldPath`**: a branded string identifying a field by the path to its data, such as `friends[0].firstName`. See [Field identity](#field-identity-is-a-fieldpath-string-instead-of-a-fieldpathid-object-breaking-change).
- **`UiOptionsCheck`**: The `{ when, then }` shape a `Checks` union is built from, each rule declaring the widget/field/option vocabulary `StrictUiSchema` allows for a given form-data type.
- **`StrictUiSchema<Checks, T, S, F>`**: the opt-in form of `UiSchema` that narrows `ui:widget`/`ui:field`/`ui:options` to a `Checks` union's vocabulary. See [Type-safe UiSchema (opt-in)](#type-safe-uischema-opt-in).
- **`CoreUiOptionsChecks`** (`@rjsf/core`): The `UiOptionsCheck` union describing `@rjsf/core`'s own built-in widgets, fields and `ui:options`. Pass it as `StrictUiSchema`'s `Checks` argument (union it with your own `Checks` to extend it further) - it isn't included automatically.
- **`IndexedEnumOptionType<S>`**, **`EnumOptionsGroupType<S>`**, **`GroupedEnumOptionsType<S>`**: the option/group shapes returned by `groupEnumOptions()`, described below.
- **`SlotComponent<P>`**: the component-slot type behind `Widget`, `Field` and every `TemplatesType` entry: a function or class component taking `P`, with its props checked bivariantly. See [`Widget` type](#widget-type-breaking-change).
- **`ThemedForm<T, S, F>`** (`@rjsf/core`): what `withTheme()` returns. See [`withTheme()` returns a `ThemedForm`](#withtheme-returns-a-themedform-breaking-change).
- **`EventFormData<T>`** (`@rjsf/core`): the type of `IChangeEvent.formData` and `FormHandle.getFormData()`. See [Generic defaults are `unknown` instead of `any`](#generic-defaults-are-unknown-instead-of-any-breaking-change).
- **`LogOnceLevel`**: `'warn' | 'error'`, the console method `logOnce()` logs through, described below.
- **`SchemaContext<S, F>`**: the `validator`, `customMergeAllOf` and `defaultFormStateBehavior` every validator-based schema function takes as its first parameter. See [`@rjsf/utils` schema functions take a `SchemaContext` in place of the `validator`](#rjsfutils-schema-functions-take-a-schemacontext-in-place-of-the-validator-breaking-change).
- **`SchemaParserOptions<S>`**: the `customMergeAllOf` that `schemaParser()` takes, so a precompiled validator can be compiled with the same `customMergeAllOf` the form uses. It is a `Pick` of `SchemaContext`, so a form's `SchemaContext` can be passed in its place.
- **`CompileValidatorOptionsType<S>`** (`@rjsf/validator-ajv8`, `@rjsf/validator-ata`): what those packages' `compileSchemaValidators()` and `compileSchemaValidatorsCode()` take, which is their `CustomValidatorOptionsType` plus the same `customMergeAllOf`.
- **`GetDefaultFormStateProps<T, S, F>`**: the props object `getDefaultFormState()` takes after the `SchemaContext`.

### Type-safe UiSchema (opt-in)

`StrictUiSchema<Checks, T, S, F>` is a new, opt-in form of `UiSchema`: pass it a `Checks` union and it narrows `ui:widget`/`ui:field`/`ui:options` to only the values valid for each field's form-data type. An inline `uiSchema` JSX literal gets this narrowing too, by checking it with TypeScript's `satisfies` operator - no wrapper component needed.

`UiSchema` is otherwise unchanged - using `StrictUiSchema` is entirely opt-in and can be done incrementally, field by field or form by form.

See [Type-safe UiSchema](../api-reference/uiSchema.md#type-safe-uischema) for the full documentation, including examples, how to extend the widget/option vocabulary via `Checks`, and the current known gaps.

### New non-validator utility functions

- **`fieldPathEndsWithIndex(fieldPath)`**: reports whether a `FieldPath` addresses an array element.
- **`fieldPathToId(fieldPath, globalFormOptions)`**: derives the DOM id from a `FieldPath` using `idPrefix` and `idSeparator`.
- **`fieldPathToList(fieldPath)`**: parses a `FieldPath` back into a `FieldPathList`, with array indexes as numbers.
- **`fieldPathToName(fieldPath, globalFormOptions, isMultiValue?)`**: derives the HTML `name` from a `FieldPath` using the configured `nameGenerator`.
- **`flattenGroupedOptions(groupedOptions)`**: flattens the list `groupEnumOptions()` returns back into a plain list of options, in render order. For widgets that need every option in one flat collection (e.g. for value lookup) while still rendering the grouped structure.
- **`getDateTimeLocalValue(schema, value)`**: reports whether `schema.format` is `iso-date-time` and, if so, strips a timezone offset from the value for display. Shared by the `DateTimeWidget`s in `@rjsf/core`, `@rjsf/antd`, `@rjsf/daisyui`, and `@rjsf/mantine`.
- **`getDeprecatedHandling<T, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType>(schema: S, uiOptions: UIOptionsType<T, S, F>): 'hide' | 'disable' | 'label' | undefined`**: resolves how a field has to render a schema marked `deprecated`: `hide` tells the `FieldTemplate` the field is hidden, `disable` disables it, and the `label` default appends the deprecation marker to the label the `FieldTemplate` receives — but not to the one the widget below it receives. `undefined` for a schema that is not deprecated, so a `ui:deprecatedHandling` cannot hide or disable a field on its own. `SchemaField` and `LayoutMultiSchemaField` both call it, and a custom field rendering its own `FieldTemplate` should call it rather than read the option directly, which is how the `label` default gets missed ([#5327](https://github.com/rjsf-team/react-jsonschema-form/issues/5327)).
- **`getFieldClassNames<S extends StrictRJSFSchema = RJSFSchema>(schema: S, hasErrors: boolean, uiClassNames?: string): string`**: builds the `classNames` string a `FieldTemplate` receives: `rjsf-field`, the `rjsf-field-<type>` class `getSchemaType()` derives, `rjsf-field-error` while the field has errors to show, and `ui:classNames` appended last. `SchemaField` and `LayoutMultiSchemaField` both call it, so the two can no longer spell the contract differently; a custom field rendering its own `FieldTemplate` should call it rather than build the list by hand. A schema with no derivable type is spelled `rjsf-field-undefined`, as it has been since 6.x; that spelling is this helper's to change, in one place for every field, and is not one to key a CSS rule off. See [`LayoutMultiSchemaField` styles its wrapper like every other field](#layoutmultischemafield-styles-its-wrapper-like-every-other-field-breaking-change) ([#5327](https://github.com/rjsf-team/react-jsonschema-form/issues/5327)).
- **`getKnownTypes<S extends StrictRJSFSchema = RJSFSchema>(schema: S): JSONSchema7TypeName[]`**: Returns the JSON Schema types a schema lists, dropping unknown names and duplicates, however many are left; an empty array for a schema whose `type` is a single name, since a name of its own is not a list to choose from. This is the list `getUnionTypes()` narrows to the schemas allowing more than one type, and the first answer `getSchemaOwnTypes()` gives, so a schema that lists only one recognized type alongside names no field can render allows that one type and renders as it
- **`getNumericInputTitle(inputProps, translateString)`**: returns the `title` for the numeric text input a `number`/`integer` field now defaults to — `TranslatableString.NumberInputTitle` ("Enter a number") or `TranslatableString.IntegerInputTitle` ("Enter a whole number"), localized through the given `translateString` — or `undefined` when `getInputProps()` set no `pattern` for the browser to reject a value against. Called by the `BaseInputTemplate` of every theme that renders a plain native `<input>`; call it from your own if you replace that template.
- **`getOptionalDataControlsType<S extends StrictRJSFSchema = RJSFSchema>(schema: S): string | string[] | undefined`**: returns the type the Optional Data Controls UI checks against `enableOptionalDataFieldForType`: an `anyOf`/`oneOf` schema's type is read from its options, any other schema's from its own `type`. `shouldRenderOptionalField()` and `OptionalDataControlsField` both use it, so they agree on it.
- **`getSchemaOwnTypes<S extends StrictRJSFSchema = RJSFSchema>(schema: S): JSONSchema7TypeName[] | undefined`**: returns the JSON Schema types a schema says its value has, taking the first answer of: the recognized names of a `type` list, as `getKnownTypes()` returns them; the types the values of a typeless `enum` or `const` have, read from the values rather than through `getSchemaType()`, which answers `string` for any typeless `enum`; and otherwise the type `getSchemaType()` resolves, so a schema that only implies its type — `properties` implying `object` — says what every other reader of it already renders it as. `undefined` for a schema that says nothing about the type: one whose only `type` is a name JSON Schema does not define, or whose type was guessed from the form data rather than named (an unconstrained `additionalProperties` entry, marked with `GUESSED_TYPE_FLAG`). The fallback UI reads it both for the types its selector offers and for whether to offer one at all, and `SchemaField` reads it to decide whether a non-select `anyOf`/`oneOf` supplies the types instead ([#5333](https://github.com/rjsf-team/react-jsonschema-form/issues/5333)).
- **`getStaticItemsUiSchema<T = unknown, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType>(uiSchema?: UiSchema<T, S, F>, index?: number): UiSchema<T, S, F> | undefined`**: Returns the static (non-function) form of `uiSchema.items` that applies at tuple position `index` — a single object applies uniformly, an array of per-position objects resolves to the entry at `index` (or `undefined` when no `index` is given), and the dynamic `(itemData, index, formContext) => UiSchema` function form always resolves to `undefined`, since callers computing array item defaults don't have an item's data, index, or form context available to call it with
- **`getTemplates<T = unknown, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType>(registry: Registry<T, S, F>, uiOptions?: UIOptionsType<T, S, F>): TemplatesType<T, S, F>`**: returns the registry's templates with each one `uiOptions` overrides resolved through `getTemplate()`, or the registry's own map when nothing is overridden. Unlike `getTemplate()`, an override for a template name the registry lacks is left out. Core and the themes destructure the templates they render from it, since React's `static-components` lint rule reports a component returned by a call during render ([#5384](https://github.com/rjsf-team/react-jsonschema-form/pull/5384)).
- **`getUiRequiredErrorSchema<T = unknown, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType>(context: SchemaContext<S, F>, rootSchema: S, uiSchema: UiSchema<T, S, F> | undefined, formData: T | undefined, uiSchemaDefinitions?: UiSchemaDefinitions<S, F>, globalUiOptions?: GlobalUISchemaOptions, formContext?: F): ErrorSchema<T>`**: Walks `rootSchema` and `formData` the same way `SchemaField` resolves each node while rendering, returning an `ErrorSchema` with a required error for every `ui:required: true` field that's missing. Also available as `SchemaUtilsType.getUiRequiredErrorSchema(uiSchema, formData, uiSchemaDefinitions, globalUiOptions, formContext)`, which supplies the first two arguments from the `SchemaUtils` instance
- **`enumOptionValueLabel(value: unknown): string`**: the label `optionsList()` gives an option with no title of its own: its value, with a plain object or array spelled as its JSON rather than `[object Object]`, and any other value, and anything nested in it that JSON can't represent, spelled as `String()` writes it.
- **`enumOptionsDomValues(enumOptions, format = 'indexed')`**: encodes every option of `enumOptions` for its DOM value attribute in one pass over the list, replacing the removed `enumOptionValueEncoder()`, so a widget reads each option's value at its position. In the `realValue` format it keeps options whose `String()` is the same, such as `1` and `'1'`, apart, and `enumOptionValueDecoder()` and `enumOptionSelectedValue()` encode against the list the same way ([#5315](https://github.com/rjsf-team/react-jsonschema-form/issues/5315)).
- **`getExampleSuggestions(schema)`**: returns the distinct strings a text input suggests from `examples` and `default`, leaving out `null`, `undefined`, object and array values. `SchemaExamples` renders no `<datalist>` when there are none, and every theme's `BaseInputTemplate` sets `list` and the examples `aria-describedby` only when there are some, passing them to `SchemaExamples` through its new optional `suggestions` prop ([#5315](https://github.com/rjsf-team/react-jsonschema-form/issues/5315)).
- **`useOptionFocusHandlers(props)`**: hook that builds a `CheckboxesWidget`'s per-option `onFocus`/`onBlur` handlers, reporting the focused option's value by its position rather than by decoding its DOM `value`. Shared by the `CheckboxesWidget`s in `@rjsf/core` and every theme ([#5315](https://github.com/rjsf-team/react-jsonschema-form/issues/5315)).
- **`getUnionTypes<S extends StrictRJSFSchema = RJSFSchema>(schema: S): JSONSchema7TypeName[] | undefined`**: Returns the types a schema allows when it allows more than one of them, i.e. its `type` is an array of two or more non-`null` type names, dropping unknown names and duplicates; `undefined` for anything `getSchemaType()` resolves to a single type, a nullable type included. Paired with the new `JSON_SCHEMA_TYPES` constant, the list of every JSON Schema type name, which is what the fallback UI offers for a schema that constrains the type not at all
- **`getVisibleErrors(props)`**: returns the errors a widget or template should surface in its own UI, given anything carrying `rawErrors` and `hideError` (its `VisibleErrorsProps` parameter type is exported too). The list is empty whenever `ui:hideError` is in effect, so a component can derive its error state from one call instead of pairing `rawErrors` with `hideError` itself. Used by every theme's widgets; see [`ui:hideError` now suppresses the theme's error styling](#uihideerror-now-suppresses-the-themes-error-styling-breaking-change).
- **`getXxxOfKey<S extends StrictRJSFSchema = RJSFSchema>(schema: S): 'anyOf' | 'oneOf' | undefined`**: returns the keyword whose options are rendered for a schema, `anyOf` when it carries both. Every reader of the options in `@rjsf/utils` and `@rjsf/core` goes through it, so a custom field that reads the options itself can too, and agree with the rest of the form on which list is on screen ([#5309](https://github.com/rjsf-team/react-jsonschema-form/issues/5309)).
- **`groupEnumOptions(enumOptions, optgroups?, enumDisabled?)`**: groups `enumOptions` according to `ui:options.optgroups`, tagging every option with its original array index (needed for index-based value encoding) and its disabled status. Powers the `optgroups` support in every theme's `SelectWidget`, described above.
- **`hasVisibleErrors(props)`**: the boolean form of `getVisibleErrors()`, for the widgets and templates that only need to decide whether to render an error state rather than render the errors themselves.
- **`isComponentType<P = never>(value: unknown): value is ComponentType<P>`**: reports whether a value is a component React can render: a function, or a `memo()`, `forwardRef()` or `lazy()` component, but not a React element such as `<MyField />` ([#5363](https://github.com/rjsf-team/react-jsonschema-form/issues/5363)).
- **`isConstantOptionList<S extends StrictRJSFSchema = RJSFSchema>(options: unknown, nonEmpty = false): options is S[]`**: reports whether an `anyOf`/`oneOf` list is made entirely of constant schemas (see `isConstant()`), the shape rendered as a select. An empty list passes, since every one of its options is vacuously a constant, unless `nonEmpty` is set for a caller that needs an option to exist.
- **`isConstantSelect<S extends StrictRJSFSchema = RJSFSchema>(schema: S, allowEmpty = false): boolean`**: reports whether a schema's value is picked from an `enum` or an `anyOf`/`oneOf` of constants (read from the keyword `getXxxOfKey()` picks), whatever its `type`. An empty list passes only with `allowEmpty`, which gives `isSelect()`'s answer without resolving the schema; otherwise an empty `enum` leaves the `anyOf`/`oneOf` to decide. An `object` or `array` schema that passes renders as one select for its whole value; see `isWholeValueSelect()`.
- **`isWholeValueSelect<S extends StrictRJSFSchema = RJSFSchema>(schema: S): boolean`**: reports whether a schema is a select over object or array constants, which holds one of them as a whole: a non-empty `isConstantSelect()` schema whose `type` is `object` or `array`, or which declares no `type` and offers an object or array constant. `getDisplayLabel()`, `getDefaultFormState()`, `omitExtraData()`, `sanitizeDataForNewSchema()`, `getWidget()` and the `ui:required` check all treat such a select's value as one constant rather than a container through it.
- **`isEnumOptionsGroup(item)`**: type guard distinguishing a group from a standalone option in the list `groupEnumOptions()` returns.
- **`localTimeToOffsetTime(time)`**: appends the browser's current local UTC offset to a bare `HH:MM`/`HH:MM:SS` time string, without altering the wall-clock value.
- **`logOnce(message: string, level: LogOnceLevel = 'warn', error?: unknown)`**: logs `message` (followed by `error`, when there is one) through `console.warn()`, or `console.error()` when `level` is `'error'`, but only the first time it is seen, so a warning raised while rendering isn't repeated on every re-render. What has been logged is remembered for the whole page. The warnings `@rjsf/utils`, `@rjsf/core` and the validators raise while rendering now go through it ([#3051](https://github.com/rjsf-team/react-jsonschema-form/issues/3051))
- **`offsetTimeToLocalTime(time)`**: strips a trailing timezone offset (`Z` or `+HH:MM`/`-HH:MM`) from a `time` string, for feeding back into a native time input.
- **`omitConsumedStyling<T = unknown, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType>(uiSchema?: UiSchema<T, S, F>): UiSchema<T, S, F> | undefined`**: returns the `uiSchema` to hand a field's children with the class names and style the field's own `FieldTemplate` consumed removed, in all four spellings (`ui:classNames`, a bare `classNames`, `ui:style`, and the `ui:options` equivalents), so a child cannot apply them a second time inside the wrapper already carrying them ([#439](https://github.com/rjsf-team/react-jsonschema-form/issues/439)). The original object comes back when there is nothing to strip, so a field memoizing it keeps the identity it had. This is the stripping `SchemaField` has always done inline, which `LayoutMultiSchemaField` now does too ([#5327](https://github.com/rjsf-team/react-jsonschema-form/issues/5327)).
- **`padTimeSeconds(value)`**: appends `:00` seconds to a bare `HH:MM` time or the time portion of a naive local date-time string that's missing them, since RFC 3339 requires seconds regardless of whether a timezone offset is present.
- **`replaceEqualDeep(prev, next)`**: returns `next` with every subtree deeply equal to `prev` replaced by the `prev` instance, so reference-based memoization sees unchanged data as unchanged. `Form` applies it to the state it builds for a change.
- **`resetLogOnce()`**: forgets what `logOnce()` has logged. What has been logged is remembered for the whole page, so if your tests assert on an RJSF warning, call this before each test (e.g. `beforeEach(resetLogOnce)` in your Vitest or Jest setup file); otherwise only the first test to trigger a warning will see it logged
- **`resolveWidget<T = unknown, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = FormContextType>(schema: RJSFSchema, widget?: Widget<T, S, F> | string, registeredWidgets?: RegistryWidgetsType<T, S, F>): { Widget: Widget<T, S, F> }`**: returns `getWidget()`'s widget as `{ Widget }`, for the same reason: a component destructured from it passes the `static-components` rule ([#5384](https://github.com/rjsf-team/react-jsonschema-form/pull/5384)).
- **`schemaKey<S extends StrictRJSFSchema = RJSFSchema>(schema: S): string`**: the key a validator caches a schema's compiled validation function under, and the key `schemaParser()` maps it into the compiled set under: the schema's `$id` when it names something, and `hashForSchema(schema)` otherwise. An empty `$id` names nothing, so a schema carrying one is keyed by its hash rather than sharing the empty key with every other such schema. `@rjsf/validator-ajv8`, `@rjsf/validator-ata`, `@rjsf/validator-cfworker` and `ParserValidator` had each spelled this rule out for themselves and had drifted apart on the empty `$id`; they all call this now. Two schemas sharing a key must validate the same way, so a schema derived from another in a way that changes its meaning carries an `$id` derived from its own content instead — if you write a validator or derive schemas to validate against, use this for the cache key rather than reading `$id` directly ([#5338](https://github.com/rjsf-team/react-jsonschema-form/issues/5338)).
- **`toFieldPath(segment, parentPath?)`**: appends a property name or array index to a parent `FieldPath`. `ROOT_FIELD_PATH` is the path of the root form.
- **`useSelectFocusHandlers(props)`**: hook that builds a select widget's `onFocus`/`onBlur` handlers, reporting its form data `value` as it is, or the `emptyValue` option when nothing is selected. Shared by the `SelectWidget`s in `@rjsf/antd`, `@rjsf/chakra-ui`, `@rjsf/daisyui`, `@rjsf/fluentui-rc`, `@rjsf/mantine`, `@rjsf/mui` and `@rjsf/shadcn`, whose focused element carries no option value to decode.
- **`useTimeWidgetProps(props)`**: hook that combines `localTimeToOffsetTime()`, `offsetTimeToLocalTime()` and `padTimeSeconds()` into a `TimeWidget`'s offset-free display value and a `computeTimeValue()` transform for its `onChange` handler. Shared by the `TimeWidget`s in `@rjsf/core`, `@rjsf/daisyui`, and `@rjsf/mantine`.
- **`withVariantId<S extends StrictRJSFSchema = RJSFSchema>(schema: S): S`**: gives a schema derived from one that carries an `$id` an `$id` of its own, `<the original's>?rjsf=<the derived schema's hash>`, and returns a schema with no `$id` as it stands. A validator caches the function it compiles under a schema's `$id`, so a derived schema that kept the original's would be validated against the original's function. The original `$id` stays the base of the derived one, so a relative `$ref` the schema left for the validator to resolve still resolves against it. The option scoring applies this to each form of an option it validates, and `MultiSchemaField` applies it to the option it retrieved before validating it — if you validate a schema you derived from one carrying an `$id`, derive the `$id` with this ([#5338](https://github.com/rjsf-team/react-jsonschema-form/issues/5338)).
- **`dateElementId(rootId, type)`**: the id `DateElement` gives each of the date element selectors an `AltDateWidget` renders, e.g. `dateElementId('root_birthday', 'year')` is `root_birthday_year`. A theme's `AltDateWidget` uses it to point a label at the year, month or day control instead of rebuilding that id itself; the separator is always `_`, independent of the form's `idSeparator`
- **`fieldLabelId(id)`**: the id for the label a theme's `FieldTemplate` renders above a field's control, e.g. `root_birthday__label`. A widget that a `label htmlFor` cannot name — a group of controls, since the association reaches a single control rather than the element wrapping them — points `aria-labelledby` at it, so its accessible name is the text on the screen. A single control, a picker's `button` included, is named by the label's `htmlFor` alone and should not point here, since `aria-labelledby` outranks that association and resolves to nothing under a `FieldTemplate` that renders no such label. It cannot be `titleId()`, which `TitleFieldTemplate` already claims for the same field
- **`triggerValueId(id)`**: the id for the element inside a picker's trigger that displays the selected value, e.g. `root_birthday__value`. A trigger that is a `button` is named by the label pointing at it, which replaces its own contents, so the value is referenced through `aria-describedby` instead — the way a native control announces its value after its name

### Changes to existing utility functions

- **Every validator-based schema function**: Takes a `SchemaContext` in place of its `validator`, and no longer takes a `customMergeAllOf` or `defaultFormStateBehavior`. See [`@rjsf/utils` schema functions take a `SchemaContext` in place of the `validator`](#rjsfutils-schema-functions-take-a-schemacontext-in-place-of-the-validator-breaking-change)
- **`getDefaultFormState()`**: Takes a `SchemaContext` followed by a `GetDefaultFormStateProps` object, and added optional `uiSchema` and `uiSchemaDefinitions` props used to apply `ui:emptyValue` and `ui:initialValue` as defaults
  - These were added as optional trailing parameters of the `SchemaUtilsType` interface's version of `getDefaultFormState()` as well
- **`getSchemaType()`**: A schema without a `type` whose `const` is falsy (`0`, `false`, `''` or `null`) now reports the constant's type instead of `undefined`. See [A typeless `oneOf`/`anyOf` of constants now renders as a select](#a-typeless-oneofanyof-of-constants-now-renders-as-a-select-breaking-change) for what this changes. A `type` list of three or more entries that starts with `null`, such as `['null', 'string', 'number']`, now resolves to its first type other than `null` rather than to `null`, as a two-entry nullable list already did, so it renders that type's field rather than `NullField` and `getDefaultFormState()` fills it in as that type ([#5331](https://github.com/rjsf-team/react-jsonschema-form/issues/5331))
- **`enumOptionSelectedValue()`**: In the `realValue` format the selected value is encoded the same way `enumOptionsDomValues()` encodes the options' values, instead of with `String()`, so a selected object or `null` value now matches its option. It also no longer reports "no selection" purely because the value equals the `emptyValue` a widget passed it, so an option carrying that widget's `null` or `''` sentinel shows as selected. An entry of a multiple selection that matches no option is left out, as the `indexed` format leaves it out
- **`enumOptionValueDecoder()`**: In the `realValue` format a string decodes to the option `enumOptionsDomValues()` encodes as that string, and no longer falls back to the option at a bare index no option encodes as. That fallback returned the wrong option whenever a number option shared its value with another option's position, e.g. `'1'` decoded to `1` rather than `5` for the options `1` and `5`. A widget that holds an option's position resolves it with `enumOptionsValueForIndex()` instead.
- **`enumOptionsIsSelected()`**: Takes an optional third `multiple` argument. A single-select widget passes `false`, so an array `selected` is compared as the whole value of an array option such as `{ "const": [2] }` rather than as a list of selections; omitted, an array is still a list. `enumOptionsIndexForValue()` prefers an option matching the whole value when not `multiple`, which fixes `enumOptionSelectedValue()` for array constants too, and the radio widgets pass `false`
- **`enumOptionsSelectValue()`**: Compares values by deep equality and accepts a `null` option, so an object option selected in a checkbox list lands in the options' order, whether or not the form data holds the option's own instance It no longer adds a value that is already selected, and keeps a selected value that matches no option after the ones that do
- **`getDisplayLabel()`**: An `object` or `array` schema whose `enum` or `anyOf`/`oneOf` is a non-empty list of constants now displays its label, since it renders as one select for the whole value rather than as the fields of its contents
- **`getWidget()`**: The `object` and `null` types now accept the `select`, `radio` and `hidden` widget names, which a select over object constants, or one whose `type` list starts with `null`, renders with, and an `array` select over whole array constants accepts `select`, `radio` and `hidden`, throwing for `checkboxes` and `files`, which read the picked array as a list of selections. A multi-select array still throws for `radio`, since a radio group would write one value in place of its list. Only the aliases are checked: a widget named by its registered name, such as `CheckboxesWidget`, renders as named. Asking for any other name for an `object` or `null` type now throws `No widget '<name>' for type '<type>'` instead of `No widget for type '<type>'`. A widget that isn't a component, such as a React element or a context's `Provider` or `Consumer`, now throws `Unsupported widget definition`
- **`isSelect()`**: Reads `anyOf` before `oneOf`, the same as `optionsList()`, so a schema carrying both keywords is judged by the list that renders ([#5309](https://github.com/rjsf-team/react-jsonschema-form/issues/5309)). `sanitizeDataForNewSchema()` and `findFieldInSchema()` read `anyOf` first too, and `omitExtraData()` checks the `oneOf`/`anyOf` list it prunes by rather than asking `isSelect()` about the parent
- **`optionsList()`**: Returns `undefined` instead of throwing when the `anyOf`/`oneOf` it reads is not made of constants and no selector field names where the values are. An option with no title of its own and an object or array value is labelled with its JSON instead of `[object Object]`
- **`retrieveSchema()`**: The stub it builds for a property described only by an `additionalProperties` with no `type` now keeps the rest of that subschema instead of discarding it, so a property constrained by an `enum`, a `format`, a length or a range renders as a field that honors it rather than as free text. Subschema keywords such as `allOf`, identifiers such as `$id`, containers such as `$defs` and `definitions`, and a `default` of another type than the data are left out. This is not gated behind `useFallbackUiForUnsupportedType`, so such a property renders as the field its constraint calls for in every form, and a value of another type than that constraint allows is as invisible in it as in any field for a schema that names a type. The stub still takes the type of the data the property holds, and is now marked with the new `GUESSED_TYPE_FLAG` symbol to record that the type was guessed rather than declared by the schema when the subschema asserts nothing about the value. When expanding every branch, `resolveAnyOrOneOfSchemas()` keeps the keyword it didn't read on each option it returns, so the schema parser also covers the `oneOf` of a schema whose `anyOf` it resolved first, which a precompiled validator otherwise threw for at runtime
- **`sanitizeDataForNewSchema()`**: A property is no longer treated as having changed schema when its type differs but both the old and the new type carry `GUESSED_TYPE_FLAG`, since those types describe the data rather than anything either schema requires. Without this, switching the type of such a property through the fallback UI discarded the value as data belonging to an old schema. A new schema that declares a type of its own is still the type the data has to satisfy. It also compares a `default` or `const` with the form data by value rather than by reference, so a `readOnly` object or array holding its default keeps it, and an untouched object default is swapped for the new schema's. An array item picked from object constants is kept when the new items schema still offers it, rather than sanitized property by property and dropped. An `anyOf`/`oneOf` with an option that is neither a `const` nor an `enum` no longer counts as a list of allowed values, so a value only that option accepts is kept rather than replaced with one of the constants. An option's `enum` counts every one of its values as allowed, where one with more than one value used to add none, so a value it allows is kept and one no option allows is cleared
