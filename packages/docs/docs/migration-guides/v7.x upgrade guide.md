# 7.x Upgrade Guide

## New deprecations

### Reading `Form` internals through a `ref`

The `Form` ref now has a documented contract: the `FormHandle` type, exported from `@rjsf/core`.
Its members are unchanged and stay supported. Anything else on the instance is an implementation detail and will break in a later 7.x release, so stop using it now:

| Stop using                            | Use instead                                                                                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `.state.formData`                     | `.getFormData()`, new in this release (see New Features)                                                                                         |
| `.state.errorSchema`, `.state.errors` | `event.errorSchema`, `event.errors` in your `onChange`/`onSubmit` handler                                                                        |
| `.state.schemaUtils`                  | build one with `createSchemaUtils(validator, schema)`, or use the `registry.schemaUtils` a field, widget or template receives                    |
| `.state.registry`                     | build one with `buildRegistry(props, schemaUtils.getRootSchema(), schemaUtils)`, or use the `registry` prop a field, widget or template receives |
| `.setState(...)`                      | `.setFieldValue(path, value)`, or pass a new `formData`                                                                                          |
| `.formElement`                        | `.reset()` for a form reset; direct DOM access has no replacement                                                                                |

```diff
-const data = formRef.current.state.formData;
+const data = formRef.current.getFormData();

-const { errorSchema } = formRef.current.state;
+const onChange = (event) => setErrorSchema(event.errorSchema);
```

Still supported and unchanged: `submit()`, `reset()`, `setFieldValue()`, `validateForm()`, `validateFormWithFormData()` and `focusOnError()`.

`validate()` is still supported, but it now takes only the data to validate; see [`FormHandle.validate()` takes only the data](#formhandlevalidate-takes-only-the-data-breaking-change).

These `state` members carry no `@deprecated` tag yet, so the only notice is this guide. `IChangeEvent` is derived from `FormState`, so tagging `state.formData` or `state.errorSchema` would also mark `event.formData` and `event.errorSchema` — the replacements — as deprecated.
The tags follow once the event type stops deriving from the state type.

**Typing the ref.** Keep `useRef<Form>()`.
TSX types a class element's `ref` by its instance, so `useRef<FormHandle>()` is rejected on `<Form ref>` for as long as `Form` is a class.
Narrow to `FormHandle` where you use the ref instead; the compiler then keeps you on the supported members, and nothing changes for you when the ref prop itself becomes `Ref<FormHandle>`:

```tsx
import { useRef } from 'react';
import type { FormHandle } from '@rjsf/core';
import Form from '@rjsf/core';

function Editor({ id, record }) {
  const formRef = useRef<Form>(null);

  function save() {
    const form: FormHandle | null = formRef.current;
    api.patch(id, form?.getFormData());
  }

  return <Form ref={formRef} schema={schema} validator={validator} initialFormData={record} />;
}
```

**Why.** `Form` is moving to the same ownership rule as an `<input>`: pass `formData` and you own the value, like `value`; pass `initialFormData` and the form owns it, like `defaultValue`.
Today `state.formData` is a copy the form keeps to reconcile those two cases on every update.
With one owner there is no copy, so `getFormData()` ships first, before the switch, as the read path that keeps working across it.
`FormHandle` is the ref contract that also survives the later move to a function-component `Form`.

## Breaking changes

### ESM-only packages

Every `@rjsf/*` package now ships only ESM: per-file modules and declarations in `lib/`.
The CommonJS (`dist/index.cjs`), bundled ESM (`dist/<name>.esm.js`) and UMD (`dist/<name>.umd.js`) builds are gone, along with the `./dist` and `./dist/*.cjs` export paths.

- `import` from any bundler or from Node works as before; `require()` also keeps working on every supported Node version, which can load ESM packages natively.
- Deep imports through `@rjsf/<package>/lib/<file>.js` are unchanged.
- If you loaded a UMD bundle from a CDN with a `<script>` tag, switch to an ESM CDN (for example `import Form from 'https://esm.sh/@rjsf/core'`) or a bundler.

### `@rjsf/shadcn` no longer ships prebuilt stylesheets BREAKING CHANGE

The compiled `dist/<theme>.css` files (`default`, `amethyst-haze`, `caffeine`, `claude`, `clean-slate`, `neo-brutalism`, `pastel-dreams`, `soft-pop`, `twitter`, `vercel`) are gone, and so is the `src/css` directory they were built from.
Each was a full Tailwind build — preflight reset included — for one fixed set of design tokens, which is the wrong shape for a library: importing one restyled the whole page and could not follow your own shadcn theme.

`@rjsf/shadcn` is now styled the way shadcn components are, by the application's Tailwind build.
Add the package to your Tailwind sources:

```css
@import 'tailwindcss';
@source "../node_modules/@rjsf/shadcn/lib";
```

The form then picks up the CSS variables from your `shadcn init` setup.
If you were importing a prebuilt theme for its colors, generate the equivalent variables with [tweakcn](https://tweakcn.com/editor/theme) into your global CSS; the playground's [theme sources](https://github.com/rjsf-team/react-jsonschema-form/tree/main/packages/playground/src/themes/shadcn) hold the token sets the old stylesheets were built from.

### `getDefaultRegistry()` removed BREAKING CHANGE

`getDefaultRegistry()` bundled the core fields, widgets and templates together with placeholder `rootSchema`, `formContext`, `translateString` and `globalFormOptions` values that the `Form` overwrote anyway. Use `generateTheme()` for all three dictionaries, or the individual generator for the one you need:

```diff
-import { getDefaultRegistry } from '@rjsf/core';
+import { generateTheme } from '@rjsf/core';

-const { fields, widgets, templates } = getDefaultRegistry();
+const { fields, widgets, templates } = generateTheme();
```

```diff
-import { getDefaultRegistry } from '@rjsf/core';
+import { generateFields } from '@rjsf/core';

-const { StringField } = getDefaultRegistry().fields;
+const { StringField } = generateFields();
```

To reuse a single component, import it directly instead — `import { StringField } from '@rjsf/core'` — so the rest of the core components stay out of your bundle.

### `Form.getRegistry()` is now the `buildRegistry()` export BREAKING CHANGE

`getRegistry()` was a `static` on the `Form` class. It is now a standalone `buildRegistry()` export from `@rjsf/core`, taking the same arguments:

```diff
-import Form from '@rjsf/core';
+import { buildRegistry } from '@rjsf/core';

-const registry = Form.getRegistry(props, schema, schemaUtils);
+const registry = buildRegistry(props, schema, schemaUtils);
```

Most code never needs it. Inside a field, widget or template, use the `registry` prop you already receive — it is the registry the `Form` actually rendered with, including its real `schemaUtils`.
To build one for a test, use `getTestRegistry()` from `@rjsf/core/testing`.
For the core component dictionaries on their own, use `generateTheme()`.

### `_internalFormWrapper` removed BREAKING CHANGE

The private `_internalFormWrapper` prop, and its entry in the `ThemeProps` a theme passes to `withTheme()`, have been removed.
It existed so `@rjsf/semantic-ui` could wrap the `<form>` element in that library's own `Form` component, and it was the only theme that ever used it.
Use the public `tagName` prop to render a different element in place of `<form>`.

### `getTestRegistry()` moved to `@rjsf/core/testing` BREAKING CHANGE

Update the import and add `@rjsf/validator-ajv8` to your dev dependencies:

```diff
-import { getTestRegistry } from '@rjsf/core';
+import { getTestRegistry } from '@rjsf/core/testing';
```

```bash
npm install --save-dev @rjsf/validator-ajv8
```

`@rjsf/validator-ajv8` is now an optional peer dependency of `@rjsf/core` that only this entry point needs, so it no longer ships as a transitive dependency of the main entry.
The arguments are unchanged: `getTestRegistry(schema, {}, templates)` still works.

### `Registry` members are read-only BREAKING CHANGE

Every member of the `Registry` type in `@rjsf/utils` is now `readonly`.
The registry is the plumbing `Form` builds from its props and hands down to fields, widgets and templates; nothing is supposed to write back into it, and now nothing can.

This is only a breaking change if you assigned into a registry you received, e.g. `registry.globalUiOptions = {...}` or `registry.formContext = {...}`.
Build a modified copy instead and pass that down:

```diff
-registry.globalUiOptions = { enableMarkdownInHelp: true };
+const registry = { ...baseRegistry, globalUiOptions: { enableMarkdownInHelp: true } };
```

Only the registry's own members are read-only.
The component maps it holds are not deeply read-only, so `registry.widgets.MyWidget = ...` still compiles; override widgets, fields and templates through the `Form` props or `withTheme()` rather than by writing into the maps.

The registry that `getTestRegistry()` returns is additionally frozen at runtime, along with its `fields`, `templates` and `widgets` maps and the nested `ButtonTemplates`, so a test that mutates it throws instead of silently affecting later assertions.
The freeze is shallow by design: a deep freeze would reach objects the caller owns, such as `formContext`, `rootSchema` and the validator's internal caches.

### `schema`, `uiSchema` and `registry` props are read-only BREAKING CHANGE

`schema`, `uiSchema` and `registry` are now `readonly` on `RJSFBaseProps`, which every field, widget and template props type extends, and on `SubmitButtonProps`, which declares its own.
These are values the form builds and passes down; writing back into them never reached the form and now fails to compile.

This is only a breaking change if you assigned into the props your custom component received, e.g. `props.schema = modifiedSchema`.
Spread a copy and use that instead, which also drops the modifiers:

```diff
-props.schema = { ...props.schema, title: 'Custom' };
+const schema = { ...props.schema, title: 'Custom' };
```

Note that these props are read-only, not deeply immutable.
The objects behind them are shared with the form, so mutating `props.schema.title` in place is still a bug even though it compiles.

### Markdown is an opt-in template

`markdown-to-jsx` is no longer part of the `@rjsf/core` bundle (it was a third of it) and is now an optional peer dependency instead of a dependency, so `@rjsf/core` no longer installs it.
Markdown is rendered through the `MarkdownTemplate`, whose core default is plain text; `@rjsf/core/markdown` provides the `markdown-to-jsx` implementation. Install `markdown-to-jsx` and register it:

```tsx
import Form from '@rjsf/core';
import MarkdownTemplate from '@rjsf/core/markdown';

<Form
  schema={schema}
  validator={validator}
  templates={{ MarkdownTemplate }}
  uiSchema={{ 'ui:enableMarkdownInDescription': true }}
/>;
```

The `ui:enableMarkdownInDescription` and `ui:enableMarkdownInHelp` options remain independent, default to `false`, and can still be set through `ui:globalOptions`.
Translatable strings that allow markdown go through `RichDescription`, so they also need `ui:enableMarkdownInDescription`.
`RichDescription.TEST_IDS` and `RichHelp.TEST_IDS` no longer exist, since neither component renders markdown itself any more; the markdown test id lives on the renderer as `MarkdownTemplate.TEST_IDS.markdown` from `@rjsf/core/markdown`.
Raw HTML is never parsed, including in `FileWidget`'s file information, which used to allow it.

The English `InvalidObjectField`, `UnsupportedField*` and `FilesInfo` translatable strings no longer use markdown syntax.
`FileWidget`'s file information used to render through `markdown-to-jsx` unconditionally, which is what made the file name bold; it now goes through `RichDescription` like every other translatable string, so it is plain text unless you register a `MarkdownTemplate`, set `ui:enableMarkdownInDescription`, and supply a `translateString` that marks the name up.
A custom `translateString` that returns markdown keeps working when the template is registered and `ui:enableMarkdownInDescription` is enabled.

### Removal of `defaultProps` support on widgets BREAKING CHANGE

`getWidget()` no longer merges a widget component's (deprecated) `defaultProps.options` into the `options` it renders with.
React 19 removed `defaultProps` support for function components, so this merging behavior was already broken for function widgets there and only ever worked for `forwardRef`/`memo`-wrapped ones.

If you relied on `defaultProps` to supply default `options` for a custom widget, apply the defaults inside the widget itself instead, e.g. via destructuring defaults: `const { color = 'red' } = options;`.
See [Custom widget options](../advanced-customization/custom-widgets-fields.md#custom-widget-options).

### `Widget` type BREAKING CHANGE

The `Widget<T, S, F>` type in `@rjsf/utils` is now a plain `ComponentType<WidgetProps<T, S, F>>` alias.
It no longer carries the optional `MergedWidget` property, which `getWidget()` used to stamp onto a widget component to cache the wrapper it created for merging `defaultProps.options` (see above).
That caching is gone along with the merging behavior it supported.

This is only a breaking change if you referenced `Widget['MergedWidget']` directly, or otherwise depended on the `Widget` type being an intersection type rather than a plain component type.

### `withTheme()` BREAKING CHANGE

`withTheme()` now returns a plain function component instead of a `forwardRef`-wrapped one, now that React 19 supports passing `ref` as a regular prop to function components.

This is a breaking change if you pass the return value of `withTheme()` directly to `useState()` or a state setter, e.g. `useState(withTheme(theme))` or `setFormComponent(withTheme(theme))`.
React treats a bare function passed to either as a lazy initializer/updater and calls it immediately with no arguments, which throws (a `forwardRef` object isn't a function, so this pattern happened to work before).
Wrap it in a lazy initializer instead: `useState(() => withTheme(theme))`.

### `FormProps['onSubmit']` event type BREAKING CHANGE

The `event` parameter passed to `onSubmit` is now typed as `SubmitEvent<any>` instead of the deprecated `FormEvent<any>` (both from `react`; `FormEvent` doesn't correspond to a real event type and is annotated `@deprecated` in `@types/react` in favor of `SubmitEvent`, `ChangeEvent`, `InputEvent`, or `SyntheticEvent`).
This is only a breaking change if you referenced `FormEvent` directly for your `onSubmit` handler's event parameter type.

`SubmitEvent` was added to `@types/react` in version 19.2.18; earlier 19.2.x patches don't have it and will fail to compile against `@rjsf/core`'s published types with `TS2305: Module 'react' has no exported member 'SubmitEvent'`.
Make sure your project's `@types/react` is at least `19.2.18`.

### `ObjectFieldTemplatePropertyType` BREAKING CHANGE

`ObjectFieldTemplatePropertyType` in `@rjsf/utils` is now generic (`<T, S, F>`, defaulted like every other RJSF generic type), and its `content` field is typed as `ReactElement<Pick<FieldProps<T, S, F>, 'schema' | 'uiSchema'>>` instead of a bare `ReactElement`. `ObjectFieldTemplateProps['properties']` threads its own `<T, S, F>` through to it.

This is only a breaking change if you referenced `ObjectFieldTemplatePropertyType` with explicit (non-default) generic arguments, or relied on `content.props` being typed as `any`.

### Removal of deprecated APIs BREAKING CHANGE

The following APIs, deprecated in prior releases, have been removed:

- **`UiSchema['ui:rootFieldId']`**: use the `Form.idPrefix` prop instead.
- **`Form.getUsedFormData()` and `Form.getFieldNames()`** instance methods, and the underlying `getUsedFormData`/`getFieldNames` exports from `@rjsf/utils`: there is no direct replacement.
- **`Form.omitExtraData()`** instance method: use `SchemaUtils.omitExtraData(schema, formData)` instead (build one with `createSchemaUtils`, or use the `registry.schemaUtils` your fields, widgets and templates already receive).
- **`FormProps.removeEmptyOptionalObjects`**: this prop had already stopped doing anything; use `omitExtraData` instead, which now prunes empty optional objects as part of its filtering.
- **`removeOptionalEmptyObjects()`** exported from `@rjsf/utils`: use `omitExtraData` instead, which has the equivalent pruning built in.
- **`toPathSchema()`** exported from `@rjsf/utils`, and `SchemaUtils.toPathSchema()`: there is no direct replacement.
- **`PathSchema` type** exported from `@rjsf/utils`: there is no direct replacement.
- **The `boolean` options for `FormProps.liveValidate` and `FormProps.liveOmit`**: use `'onChange'` in place of `true`, or omit the prop (or pass `undefined`) in place of `false`.

### `ErrorSchema<T>` and `FormValidation<T>` node shapes BREAKING CHANGE

`ErrorSchema<T>` and `FormValidation<T>` now describe the tree that `toErrorSchema()` and `createErrorHandler()` actually build. Previously they resolved to the wrong shape for anything but a plain object: a leaf field's node resolved to that field's own type, an array's node to an array rather than a node keyed by index, and `ErrorSchema<any>` to an index signature that no concrete error schema was assignable to. In practice a typed error schema never type-checked.

There are two things to do.

**Drop the casts you used to work around the old shapes.** The value type-checks on its own now:

```diff
-const extraErrors = { name: { __errors: ['too short'] } } as unknown as ErrorSchema;
+const extraErrors: ErrorSchema<FormData> = { name: { __errors: ['too short'] } };
```

**Reach into nodes with `?.`.** Every node is optional, because the tree only contains the fields that actually have errors:

```diff
-errors.address.city.addError('unknown city');
+errors.address?.city?.addError('unknown city');
```

For reference, this is the shape a typed error schema now accepts — a node per field, keyed by index for arrays, with no children below a leaf:

```ts
type FormData = { name: string; address?: { city: string }; tags: string[] };

const errors: ErrorSchema<FormData> = {
  __errors: ['form-level problem'],
  name: { __errors: ['too short'] },
  address: { city: { __errors: ['unknown city'] } },
  tags: { 0: { __errors: ['not allowed'] } },
};
```

A field whose type is a union — what a `oneOf`/`anyOf` property gives you — accepts the children of every member it can hold, since which one is present depends on the current value:

```ts
type FormData = { thing: string | { city: string } };

const errors: ErrorSchema<FormData> = { thing: { city: { __errors: ['unknown city'] } } };
```

`FormValidation<T>`, the tree a `customValidate` function receives, is the same tree with `addError()` on every node.

In full, the children a node accepts are decided by the type of the data it describes:

| Field's type                                | Children of its error node                            |
| ------------------------------------------- | ----------------------------------------------------- |
| An object                                   | A node per property                                   |
| An array                                    | A node per index, keyed as `0`, `1`, …                |
| A tuple                                     | A node per position, each of that position's own type |
| A tuple with a rest element                 | Its declared positions as above, the rest as an array |
| A primitive (`string`, `number`, `boolean`) | None — a leaf holds only `__errors`                   |
| `Date` or `File`                            | None — an object holding no form fields               |
| A union                                     | The children of every member                          |
| `any` or `unknown`                          | Unconstrained                                         |

An optional property is described by the type it holds, so `address?: { city: string }` gets the same node as `address: { city: string }`.
Any other class instance used as a field value (a `Money` or `LatLng` value object, say) is treated as an object, so its properties are accepted as children even though nothing produces errors for them.

If you leave `T` at its `any` default and never annotate an error schema, nothing changes for you.

### `extraErrors` now blocks submission by default BREAKING CHANGE

`FormProps.extraErrorsBlockSubmit` has been replaced with `FormProps.extraErrorsAreWarnings`, and the default behavior is inverted: `extraErrors` now block form submission by default, the same as JSON Schema validation errors.

If you were relying on the old default (`extraErrors` displayed but non-blocking), set `extraErrorsAreWarnings` to `true`.
If you were setting `extraErrorsBlockSubmit` to `true` to get blocking behavior, remove the prop entirely — that is now the default.

If your app sets `extraErrors` from a failed server response (the async validation pattern above) and leaves it populated afterward, resubmitting the form will now re-block on those same stale errors and call `onError` again, since every submit re-merges whatever `extraErrors` is currently set to.
Clear `extraErrors` (e.g. back to `{}`) when the user edits the form or before they resubmit, the same way you'd clear a schema validation error.

### Removal of the `experimental_`/`Experimental_` prefix BREAKING CHANGE

The features below were marked experimental while their API stabilized. They are no longer experimental in v7, and the prefix has been dropped from their names:

| Old name                                                      | New name                             |
| ------------------------------------------------------------- | ------------------------------------ |
| `FormProps.experimental_defaultFormStateBehavior`             | `FormProps.defaultFormStateBehavior` |
| `FormProps.experimental_customMergeAllOf`                     | `FormProps.customMergeAllOf`         |
| `Experimental_DefaultFormStateBehavior` (type, `@rjsf/utils`) | `DefaultFormStateBehavior`           |
| `Experimental_ArrayMinItems` (type, `@rjsf/utils`)            | `ArrayMinItems`                      |
| `Experimental_CustomMergeAllOf` (type, `@rjsf/utils`)         | `CustomMergeAllOf`                   |

The corresponding `experimental_defaultFormStateBehavior`/`experimental_customMergeAllOf` parameters on the `@rjsf/utils` schema functions (e.g. `getDefaultFormState`, `retrieveSchema`, `createSchemaUtils`, and others) were renamed the same way. Update any code that names these props, types, or parameters explicitly.

### `time`/`date-time` formats now require a timezone offset BREAKING CHANGE

`@rjsf/validator-ajv8` now depends on `ajv-formats` 3.x instead of 2.x. Per [RFC 3339](https://datatracker.ietf.org/doc/html/rfc3339#section-5.6), `ajv-formats` 3 requires the JSON Schema `time` format to include a timezone offset (`Z`, or `+HH:MM`/`-HH:MM`); previously the offset was optional for `time` alone. `date-time` already required an offset in `ajv-formats` 2.x, so it's unaffected by this change.
This closes [#3930](https://github.com/rjsf-team/react-jsonschema-form/issues/3930), where `format: "time"` values produced by RJSF were not spec-compliant.

- **`@rjsf/core`'s `TimeWidget`** (used for `format: "time"`, and the equivalent `TimeWidget` in `@rjsf/daisyui` and `@rjsf/mantine`) now appends the browser's local UTC offset to the value whenever it's changed, e.g. `14:30:00-04:00` instead of `14:30:00`. The offset is stripped back off when displaying a value in the native time input. `format: "date-time"`/`alt-datetime` were already emitting `Z`-suffixed UTC strings and are unaffected.
- If you have previously-stored `formData` for a `format: "time"` field that lacks a timezone offset, it will now fail validation. Options:
  - Let the widget resave the value the next time a user edits that field — it will pick up the offset automatically. Note this reinterprets the wall-clock value in the browser's _current_ local offset, so if the stored value already carried a different offset (e.g. entered in another timezone), resaving it will represent a different instant rather than preserving the original one.
  - Backfill stored data with an explicit offset (e.g. treat legacy values as UTC and append `Z`).
  - If you need to keep accepting offset-less values for a given field, change that field's schema to `format: "iso-time"`/`format: "iso-date-time"` instead of `format: "time"`/`format: "date-time"` — `ajv-formats` 3 added these as an explicit, optional-timezone escape hatch for validation. RJSF maps both to the same widget used for `time`/`date-time` (`TimeWidget`/`DateTimeWidget`, including the dedicated `DateTimeWidget`s in `@rjsf/antd` and `@rjsf/daisyui`), and doesn't add a timezone offset for those formats, so committed values keep behaving like `format: "time"`/`format: "date-time"` did before this release. A stored value that happens to carry an offset anyway is still stripped for display, since the underlying date/time picker can't render one either way.

### `UiSchema<T>` checks field names BREAKING CHANGE

`UiSchema<T>` used to intersect `GenericObjectType` (`Record<string, any>`), so any string key was accepted. The per-field entries are now a mapped type over `T`, which means a field name that isn't in the form data is a compile error:

```ts
type FormData = { firstName: string; address: { city: string } };

const uiSchema: UiSchema<FormData> = {
  firstName: { 'ui:widget': 'textarea' },
  address: { city: { 'ui:placeholder': 'City' } },
  lastName: { 'ui:widget': 'text' }, // error: `lastName` is not a field of FormData
};
```

`FormProps` already infers `T` from `formData`, so a form with typed form data gets this without naming the type anywhere.

What has _not_ changed:

- **Untyped uiSchemas.** `UiSchema` with no type argument, or with `any` form data, accepts exactly what it accepted before — arbitrary nesting included.
- **The `ui:` namespace.** Any `ui:`-prefixed key is still accepted at every level, so theme-specific and application-specific directives keep working.
- **`oneOf`/`anyOf` fields.** A union-typed field accepts the keys of every branch, since which branch is present depends on the current value.

What to fix, if any of it affects you:

- **A uiSchema that names a field absent from `T`** — a property added by a `dependencies` subschema, or an `additionalProperties` key when `T` has no index signature. Give `T` an index signature (`{ [key: string]: unknown }` on the relevant object), or nest the entry under the `additionalProperties` key described below.
- **Keys the old index signature accepted silently** are now declared, with types: `additionalProperties` (a uiSchema for the data the index signature of `T` holds, unconstrained when `T` has none), `additionalItems` (a uiSchema for the array's element type), `anyOf` and `oneOf` (positional lists, one uiSchema per subschema), and the legacy unprefixed `classNames` (a string; `ui:classNames` is the prefixed spelling of the same thing). If you passed an object where a positional list is expected — `oneOf: { 'ui:title': '...' }` — it was already ignored at runtime, with a console warning; it is now also a type error.
- **A form data field named `classNames`, `anyOf` or `oneOf`** cannot be given a per-field entry, because the entry's type is intersected with the declared key's type and a string or a list has nothing in common with a uiSchema. This makes a runtime limitation visible rather than adding one: `SchemaField` consumes and deletes `classNames` from every uiSchema it receives, and `anyOf`/`oneOf` are read as positional lists wherever the schema has that keyword, so such a field's uiSchema was never reliably delivered. Rename the field, or configure it through `ui:options` on the parent. A field named `items`, `additionalItems` or `additionalProperties` is fine: those keys hold a uiSchema, so the intersection accepts the per-field entry.
- **A self-referential form data type** (`type TreeNode = { children: TreeNode[] }`) nested far enough in one uiSchema literal can exhaust the type checker (`Excessive stack depth comparing types`), since the per-field entries recurse with the data. Annotate the deep sub-entry as plain `UiSchema` to stop the recursion there.
- **A uiSchema typed by an `interface` you declared** is rejected, because an interface has no index signature and `UiSchema` requires one for its `ui:` keys. This is not new — the `ui:${string}` signature predates this change — but the field-name checking makes it easier to hit. Use a `type` alias, or annotate the literal with `UiSchema<T>` directly.

### `@rjsf/mantine`'s `onChangeOverride` now receives the change event BREAKING CHANGE

`@rjsf/mantine`'s `BaseInputTemplate` routed `onChange` and `onChangeOverride` through a single variable and handed the value to both, so an `onChangeOverride` received the input's string value. Every other theme, and `@rjsf/core`'s own `BaseInputTemplate`, pass it the raw `ChangeEvent` — which is also what `WidgetProps['onChangeOverride']` has always declared.

`onChangeOverride` now receives the `ChangeEvent` with this theme too. If you pass one to a `@rjsf/mantine` widget, read the value off the event:

```tsx
// Before
const onChangeOverride = (value: string) => setSomething(value);

// After
const onChangeOverride = (event: ChangeEvent<HTMLInputElement>) => setSomething(event.target.value);
```

A numeric field with an `onChangeOverride` now renders Mantine's `TextInput` rather than its `NumberInput`, which reports only the parsed value and never an event.
The input keeps `type="number"` (`@rjsf/core`'s `<input>` no longer does, see below); the override is what handles the input in that case, so the stepper controls and number formatting it replaces have nothing to drive.

Note that `@rjsf/core` applies `ui:emptyValue` for you when the input is cleared; an `onChangeOverride` bypasses `onChange` entirely, so handle an empty string yourself if you need that behaviour.

### `@rjsf/antd`'s `onChangeOverride` is now called for a numeric field BREAKING CHANGE

`@rjsf/antd`'s `BaseInputTemplate` wired its `InputNumber` branch straight to `onChange`.
`InputNumber` reports only the parsed value and never an event, so an `onChangeOverride` on a numeric field was never called at all.

A numeric field with an `onChangeOverride` now renders the `Input` branch (still `type="number"`) so the override receives the `ChangeEvent`, as `WidgetProps['onChangeOverride']` declares and as every other theme does. That field loses `InputNumber`'s stepper controls and formatting, which the override replaces anyway; a numeric field without an `onChangeOverride` still renders `InputNumber` as before.

### Field identity is a `FieldPath` string instead of a `FieldPathId` object BREAKING CHANGE

Every field, template and widget used to receive a `fieldPathId` prop, an object `{ $id, path, name? }` rebuilt on every render.
Because it was a new object each time, it defeated `React.memo` at every level and forced deep comparison of props to compensate.
Field identity is now two primitive strings:

- `fieldPath`: a `FieldPath` such as `friends[0].firstName`, telling **where the data lives**. It drives `onChange` writes. Property names are separated by `.`, array indexes are bracketed, and `\ . [ ]` inside a property name are backslash-escaped, so it stays unambiguous when property names contain dots or brackets. The root form is the empty string, exported as `ROOT_FIELD_PATH`.
- `id`: the DOM id such as `root_friends_0_firstName`, telling **what the element is called**. It drives `htmlFor`, focus and accessibility attributes. Ids are byte-identical to v6, including the `XxxOf` suffixes used to disambiguate `oneOf`/`anyOf` option fields, with one exception: the optional-data controls (`enableOptionalDataFieldForType`) of an object or array whose schema is itself an `oneOf`/`anyOf` take the `XxxOf`-suffixed id of the field that renders them. v6 gave those controls and the selected option's controls the same DOM id. A schema property named `''` is a second such exception: v6 dropped an empty path segment at every level, so the property took its parent's id and the two collided; it now gets a trailing separator of its own (`root_obj_`).

`FieldProps` and `FieldTemplateProps` receive both. Every other template that received `fieldPathId` (`ArrayFieldTemplate`, `ArrayFieldTitleTemplate`, `ArrayFieldDescriptionTemplate`, `ArrayFieldItemButtonsTemplate`, `CyclicSchemaExpandTemplate`, `FieldErrorTemplate`, `FieldHelpTemplate`, `ObjectFieldTemplate`, `UnsupportedFieldTemplate`) now receives `id` instead.
The `childFieldPathId` prop on `ObjectField`/`ArrayField` is gone, since `fieldPath` is always a truthful data address.
`IChangeEvent` and `FormState` no longer carry `fieldPathId` either, so an `onChange(e)`/`onSubmit(e)` handler that read `e.fieldPathId` must derive what it needs some other way — the root form's id is `idPrefix`, and `e.schemaUtils`, `e.formData` and `e.errorSchema` are unchanged.

```diff
-const { fieldPathId } = props;
-<label htmlFor={fieldPathId.$id}>
-<h2 id={titleId(fieldPathId)}>
+const { id } = props;
+<label htmlFor={id}>
+<h2 id={titleId(id)}>
```

The id helpers `titleId()`, `descriptionId()`, `helpId()`, `errorId()`, `examplesId()`, `buttonId()`, `optionalControlsId()` and `ariaDescribedByIds()` accept only a `string` id.

`FieldProps['onChange']` carries the `FieldPath` string instead of a `FieldPathList`; fields forward the `fieldPath` prop they already hold:

```diff
-onChange(newValue, fieldPathId.path, errorSchema, fieldPathId.$id);
+onChange(newValue, fieldPath, errorSchema, id);
```

`toFieldPathId()` and the `FieldPathId` type are removed.
Build paths with `toFieldPath(segment, parentPath?)` and derive what you need from them:

| Was                                    | Now                                               |
| -------------------------------------- | ------------------------------------------------- |
| `toFieldPathId(name, options, parent)` | `toFieldPath(name, parentFieldPath)`              |
| `fieldPathId.$id`                      | `id` prop, or `fieldPathToId(fieldPath, options)` |
| `fieldPathId.path`                     | `fieldPathToList(fieldPath)`                      |
| `fieldPathId.name`                     | `fieldPathToName(fieldPath, options, isMulti)`    |

`FieldPath` is a branded `string`, so a plain string (a DOM id, for example) is rejected by the compiler where a `FieldPath` is expected.
A `FieldPath` is still assignable wherever a `string` is accepted.

The `useDeepCompareMemo()` hook is removed.
It existed to hand out a stable `fieldPathId` object across renders; with two primitive strings there is nothing to stabilize.
A custom field or widget that used it for its own props can use `useMemo()`, or compare the values it cares about directly.

### `IChangeEvent` members are read-only BREAKING CHANGE

`IChangeEvent`, the event `onChange` and `onSubmit` receive, is now declared on its own instead of as a `Pick` of the `Form`'s internal state, and every member is `readonly`.
The members and their types are unchanged.
Readonly modifiers do not affect assignability, so a handler that reads the event or passes it on compiles as before; only code that assigns into the event breaks:

```tsx
// Before: compiled, and wrote into data the form shares with its parent
onChange={(event) => { event.formData = normalize(event.formData); setData(event.formData); }}

// After: copy out of the event into your own state
onChange={(event) => setData(normalize(event.formData))}
```

The modifier is shallow: it stops `event.formData = ...`, not a write inside `formData`.
Treat the whole event as immutable, as the guide says for received form data above.

### `ui:emptyValue` extended scope BREAKING CHANGE

`ui:emptyValue` used to only supply a value when a user actively cleared a field's widget.
It now applies whenever the field is blank for any reason — on initial render, after a form reset, or when cleared — since `getDefaultFormState()` threads `uiSchema` through its defaults pipeline (`computeDefaults()`/`getObjectDefaults()`) to pick it up.

If a field has no `formData` and no `schema.default`, and you set `ui:emptyValue` for it, that field's `formData` will now be populated with the `ui:emptyValue` on first render and after a reset, instead of staying `undefined` (and being omitted from `formData` entirely) until the user clears it once.
See [`ui:emptyValue`](../api-reference/uiSchema.md#emptyvalue).

### Shallow comparison replaces `experimental_componentUpdateStrategy` BREAKING CHANGE

`Form` and `SchemaField` now compare their props shallowly, as `React.memo` does, and keep the references of unchanged data across changes so that comparison is enough.
The `experimental_componentUpdateStrategy` prop is removed, and with it `shouldRender()`, `shallowEquals()` and the `ComponentUpdateStrategy` type from `@rjsf/utils`.

What to change:

- Remove the `experimental_componentUpdateStrategy` prop from `<Form>` and from any `globalFormOptions` read of it.
- Give `Form` stable references for props that hold functions: `customValidate`, `transformErrors`, `translateString`, `nameGenerator`, `customMergeAllOf`, `validator`, `fields`, `widgets`, `templates`, `formContext`, and a `uiSchema` carrying components such as `ui:widget`. A value recreated on every render re-derives the form's state on every render, so wrap it in `useCallback` or `useMemo`, or define it outside the render function. A changed one now takes effect at once, where v6 ignored it until another prop changed; with `liveValidate: 'onChange'`, a changed `validator`, `customValidate`, `transformErrors`, `customMergeAllOf` or `schema` also re-validates the current data. That re-validation, and the one a replaced `formData` triggers, validates with the schema resolved for the data whenever the schema utilities are unchanged (the same `schema`, `validator`, `defaultFormStateBehavior` and `customMergeAllOf`), the way an edit is validated; a replaced value shows the same live errors typing it would, and a miss that only the root schema reports (`if`/`then`, `oneOf`) shows on submit, as it does for typed data. `uiSchema` and `formContext` take effect in rendering at once, but a change to either re-validates only on the next data change, blur or submit, which matters if `ui:required` depends on state outside the form.
- Treat the `formData` you receive from `onChange`, `onBlur`, `onSubmit` and the other callbacks as immutable. It shares unchanged subtrees with the previous value, which for a controlled form is the object you passed in, so mutating it in place corrupts your own state. Copy before changing, as with any reducer.
- Treat schemas returned by `retrieveSchema()` as immutable; it may return the same instance across calls.
- Replace `shouldRender(this, nextProps, nextState)` in a class component's `shouldComponentUpdate` by extending `PureComponent`, which is the same comparison.
- Replace `shallowEquals` with `shallowEqual` from `fast-equals`.

### A typeless `oneOf`/`anyOf` of constants now renders as a select BREAKING CHANGE

A `oneOf`/`anyOf` whose options are all constants (`const` or a single-value `enum`) used to render as an unsupported field when the schema omitted `type`, because neither a field nor a widget could be resolved without one.
`SchemaField` now infers the `type` from the constant values, so the select these schemas always described actually renders ([#4666](https://github.com/rjsf-team/react-jsonschema-form/issues/4666)):

```json
{
  "oneOf": [
    { "const": "gpl", "title": "GPL" },
    { "const": "mit", "title": "MIT" }
  ]
}
```

Most forms only gain the field they were already asking for.
Two narrower shapes change behavior, and each is worth checking:

**Constant options under both `anyOf` and `oneOf`.** `optionsList()` reads `anyOf` before `oneOf` everywhere else, but `BooleanField` only ever read `oneOf`.
It now reads `anyOf` first as well, so a `type: 'boolean'` schema carrying constant options under _both_ keywords renders the `anyOf` titles where it used to render the `oneOf` ones.
A schema with only one of the two keywords is unaffected, as is an `anyOf` whose options aren't all constants, which still falls through to the `oneOf`.

_What to change:_ give the two keywords the same titles, or drop the redundant one.

**A typeless falsy `const` with `constAsDefaults: 'never'`.** `getSchemaType()` returned `undefined` for a typeless schema whose `const` was falsy (`0`, `false`, `''` or `null`), which is what rendered those as unsupported fields.
A typeless `{ "const": null }` now resolves to `null` and renders through `NullField`, exactly like an explicit `{ "type": "null" }`.

At the default `constAsDefaults` setting nothing changes in the emitted data: such a property already contributed its constant as its own default.
With `defaultFormStateBehavior.constAsDefaults` set to `'never'`, which suppresses that default, a typeless `{ "const": null }` and a _required_ typeless `{ "const": false }` now write `null` and `false` into the form data on mount where nothing was written before — the first from `NullField`, the second from the required-boolean default.
Each matches what the explicit `type` spelling already did. Required `{ "const": 0 }` and `{ "const": "" }` are unaffected.

_What to change:_ nothing, if you want the two spellings to agree.
If a form relied on those keys staying absent, drop the property from the schema instead of relying on it not rendering.

### `number`/`integer` fields no longer render a native `<input type="number">` by default BREAKING CHANGE

`getInputProps()` now defaults a `number`/`integer` field to `<input type="text" inputMode="decimal|numeric" pattern="...">` instead of `<input type="number">`, avoiding the cross-browser keystroke-filtering, scroll-wheel, and locale decimal-separator quirks of a native number input.
The `pattern` still blocks a non-numeric submission the same way `required` already does, and accepts the exponent notation JavaScript renders very small and very large numbers with.
A `number` accepts either sign of exponent (`1e-7`, `1e+21`); an `integer` is only ever rendered that way from `1e21` up and always with a `+`, so a negative exponent is rejected there rather than admitting `1e-7` where `0.0000001` is refused.
The `integer` pattern accepts every spelling of a whole number the field itself produces while you type — a trailing separator and zeros (`5.`, `5.00`), and the fractional mantissa of the exponent form (`String(2 ** 70)` is `1.1805916207174113e+21`) — while still refusing an actual fraction such as `1.5`.
Set `ui:options.inputType: 'number'`, or use the `updown` widget, to keep a native number input for a field. See [#4038](https://github.com/rjsf-team/react-jsonschema-form/issues/4038).

A schema whose `type` is an array counts as a `number`/`integer` field when exactly one of its entries isn't `"null"`, so `["number", "null"]` and `["number"]` both render the numeric text input — `SchemaField` already rendered them through `NumberField`, and they used to come back as a plain text input carrying `min`/`max`/`step`.
A union of more than one non-null type, such as `["number", "string"]`, keeps the plain text input it had before.
A schema with no `type` at all but a numeric `const` counts the same way, since that is the type `SchemaField` picks its field by.

`step`, `min` and `max` only constrain a native number input, so `getInputProps()` no longer returns them for these fields, and the browser no longer range- or step-checks the value before submit.
`minimum`, `maximum` and `multipleOf` are still enforced by RJSF's own validation, which reports them as form errors.
They are still returned when the field renders a native number input, through `ui:options.inputType: 'number'` or the `updown` widget, along with `step="any"` for a `number` field with no `multipleOf` so decimals are accepted (the `updown` widget did not get that `step` before).

Because the value lives in a text input with a `pattern`, native constraint validation can now block a submit whose value doesn't match, such as legacy server data like `'yo'` loaded into a number field. When that happens `onSubmit` and `onError` never fire, and the browser shows its own message on the field instead of an RJSF error.
If you want RJSF's validation to be the only validator, set `noHtml5Validate` on the `Form`.

A `pattern` the value fails is reported by the browser as a bare "Please match the requested format", which says nothing on a field that now looks like a plain text box, so RJSF sets a `title` on the input for the browser to append to that message.
The two strings go through `translateString` as `TranslatableString.NumberInputTitle` ("Enter a number") and `TranslatableString.IntegerInputTitle` ("Enter a whole number"); translate them as you do the rest.
A `pattern` of your own replaces the derived one and takes the derived `title` with it, since that title describes a rule no longer in force: pass it as a widget prop in `core`, through `extraProps` in `shadcn` and `react-bootstrap`, or through `slotProps.htmlInput` in `mui`.
`chakra-ui`, `daisyui` and `fluentui-rc` render a fixed set of props, so a `pattern` or `title` of your own doesn't reach the input in those themes at all.

That `title` is set whenever the `pattern` is, not only when the value fails it, which has two visible consequences.
The browser shows it as a tooltip when the pointer rests on any `number`/`integer` field, and because `title` is the last fallback in accessible-name computation, a numeric field rendered with no label at all (`ui:options: { label: false }`, or a layout that hides it) is now announced by that title instead of going unnamed — the same name for every such field on the page.
Give those fields a `ui:title` or an `aria-label` if either matters, or, in the themes listed above that forward them, your own `title` or `pattern`.

A text input also lets a value that isn't a number reach `formData`: `asNumber()` keeps the raw string when `Number()` can't parse it, so a half-typed `1.2.3` or a lone `-` stays in the `number` slot, where a native number input reported an empty value instead.
Code reading `formData` from `onChange`, from `getFormData()`, or through `liveValidate` errors should expect a string there while a field is being edited.
RJSF's validation reports it as a type error, and the `pattern` blocks submitting it.

The numeric virtual keyboards that `inputMode="decimal"` and `"numeric"` request are also digit-only on some platforms: the iOS ones have no minus key, so a field that accepts negative values can't have one typed on an iPhone or iPad.
RJSF doesn't switch `inputMode` by the schema's `minimum`, because most number fields have none and would lose the numeric keyboard.
For a field that needs negative values on iOS, set `ui:options.inputType: 'number'` (or use the `updown` widget), whose keyboard does have a minus key.

Accessibility changes with the element. A native `<input type="number">` is exposed as a `spinbutton`, and `min` and `max` give it `aria-valuemin`/`aria-valuemax`, so a screen reader announces a `{ "type": "integer", "minimum": 1, "maximum": 10 }` field as "spin button, 1 to 10".
A text input with `inputMode` is a `textbox`, and `inputMode` is only a virtual-keyboard hint that assistive technology doesn't see, so the range is no longer announced.
RJSF doesn't add `role="spinbutton"` or `aria-valuemin`/`aria-valuemax` to compensate: the role promises arrow-key stepping that a text input doesn't implement, and those attributes aren't valid on a `textbox`.
For a field where the range matters to the user, state it in `ui:description` or `ui:help`, which the input is already linked to through `aria-describedby`, or set `ui:options.inputType: 'number'` (or use the `updown` widget) to keep the native semantics.

This only affects themes whose `BaseInputTemplate` renders a plain native `<input>`; `@rjsf/antd` and `@rjsf/mantine` already render their own `InputNumber`/`NumberInput` component and are unaffected, except that the plain input they fall back to when a widget supplies an `onChangeOverride` is still `type="number"`.
If your code selects the widget by its DOM `type` (`input[type="number"]`, `getByRole('spinbutton')`), select on `inputMode` (`input[inputmode="decimal"]`) or your own field/id instead.

### `getInputProps()`'s fourth parameter is now `plainNativeInput` BREAKING CHANGE

The fourth parameter of `getInputProps()` was `autoDefaultStepAny`, which only decided whether a `number` field got `step="any"`. It is now `plainNativeInput`, and it decides whether the theme renders a plain native `<input>` for numbers. It is positional and still defaults to `true`, so a call that passes it needs no edit, but its meaning changed:

- `true` (the default): a `number`/`integer` field with no `defaultType` comes back as `type: 'text'` with `inputMode` and `pattern` and without `step`, `min` or `max`, as described above. A native `number` input, whether from an explicit `ui:options.inputType` of `'number'` or a widget's `defaultType` of `'number'` (as the `updown` widget passes), returns `type: 'number'` and now also `step: 'any'` for a `number` with no `multipleOf`, so decimals are accepted.
- `false`: for a theme with its own numeric widget, such as `@rjsf/antd` and `@rjsf/mantine`. The result is what it was before: `type: 'number'` (with `step: 1` for an `integer`, or `type: 'text'` for a `number` in a locale whose decimal separator isn't `.`), never `step: 'any'`, `inputMode` or `pattern`.

`InputPropsType` gained optional `inputMode` and `pattern` members.
If your own `BaseInputTemplate` spreads the result of `getInputProps()` onto an `<input>`, they reach it automatically.
If it hands them to a component that doesn't forward unknown props to the native `<input>`, pull `inputMode` and `pattern` out and pass them to it explicitly, as `@rjsf/mui` does through `slotProps.htmlInput`; without them the field renders as a plain text input with no numeric keyboard or `pattern`.

`@rjsf/mui` now applies the `getInputProps()` attributes before `slotProps.htmlInput`, so a `step`, `min`, `max` or `accept` you pass through `slotProps.htmlInput` or `ui:options.mui.slotProps.htmlInput` takes precedence instead of being overwritten by the derived value.
If you added one of those to work around the old clobbering — a `{ "type": "integer", "multipleOf": 5 }` field given `slotProps={{ htmlInput: { step: 1 } }}`, say — it now takes effect, and the browser step-checks against your value rather than the schema's.
`BaseInputTemplateMuiProps['slotProps']['htmlInput']` is typed as `InputHTMLAttributes<HTMLInputElement | HTMLTextAreaElement>` so those `<input>`-only attributes are accepted.

### `FieldTemplateProps` gains a required `keyName` BREAKING CHANGE

`FieldTemplateProps` has a new required `keyName: string` member, the name of the field's property in its parent object, and `WrapIfAdditionalTemplateProps` picks it up too.
It carries none of the decoration `label` may have picked up — a `ui:title`, or the `(deprecated)` marker the default `deprecatedHandling` appends — so an `additionalProperties` key is read and renamed from the real key rather than from what is displayed.
Rendering a `FieldTemplate` does not change; only code that constructs `FieldTemplateProps` itself is affected, and that code fails to compile with `TS2741` until it supplies `keyName`.

A **custom `WrapIfAdditionalTemplate`** should take the key control's value from `keyName` instead of `label`, keeping `label` for the control's own label:

```tsx
const keyLabel = translateString(TranslatableString.KeyLabel, [label]);
// ...
<input type='text' id={`${id}-key`} onBlur={onKeyRenameBlur} defaultValue={keyName} />;
```

Without it, a `deprecated` additional property keyed `foo` shows `foo (deprecated)` in its key input and renames itself to that string on blur.

### `ui:hideError` now suppresses the theme's error styling BREAKING CHANGE

`ui:hideError` was only ever half honored by the themes.
It suppressed the error messages RJSF renders, but the input underneath kept whatever the theme uses to signal invalid — MUI's `Mui-error`, Bootstrap's `is-invalid`, Chakra's `invalid` flag, Fluent's `validationState`, shadcn's `border-destructive` — so a field with hidden errors still rendered a red outline with nothing explaining it ([#3684](https://github.com/rjsf-team/react-jsonschema-form/issues/3684)).
`@rjsf/mantine` went further: its widgets handed the messages to Mantine's own `error` prop, and its `AltDateWidget` and `RangeWidget` rendered an `Input.Error` apiece, so a Mantine user saw the error text itself under a directive asking for it to be hidden.
Every theme's widgets now respect the directive, so a form using `ui:hideError` loses that outline — and, on Mantine, the error text that came with it.
The directive also reaches components that were never handed it: the `oneOf`/`anyOf` selector `MultiSchemaField` renders, the widget `ArrayField` renders for a multi-select array or an array of files, and the `ArrayFieldTemplate` and `ObjectFieldTemplate`, whose `hideError` prop was declared but never set.

`@rjsf/chakra-ui`'s `CheckboxesWidget` changes in two more ways, since it had a second, unrelated source of error styling:

- It no longer flags a required field while it is still empty.
  Its inner `CheckboxGroup` was marked invalid whenever the field was required and had nothing selected, before validation had found anything wrong and whatever `ui:hideError` said, so every checkbox carried `aria-invalid="true"` and `data-invalid` from the first render.
  That state is now derived from the field's visible errors like every other error state, and there is no option to bring the old behavior back; a required checkboxes field is flagged once validation reports an error for it, as any other field is.
- Once the field does have visible errors, every checkbox is marked invalid (`aria-invalid="true"` and `data-invalid`), where a field that was not required used to mark only the surrounding fieldset.

This changes nothing about what `rawErrors` contains.
Fields and widgets are still handed the full list while errors are hidden, which is what lets a custom widget render them its own way — that is the whole point of the directive.
What changed is that the built-in widgets no longer treat a non-empty `rawErrors` as reason enough to style themselves as invalid.

If you maintain a custom theme or widget, derive your error state with the new [`getVisibleErrors()`](#new-non-validator-utility-functions), or its boolean form `hasVisibleErrors()`, rather than reading `rawErrors` directly:

```tsx
// Before: renders an error state even when `ui:hideError` is set
const hasError = rawErrors.length > 0;

// After
const hasError = hasVisibleErrors(props);
```

A custom `FieldTemplate` needs no such change.
`SchemaField` withholds `rawErrors` from the `FieldTemplate` while the errors are hidden, as it always has, and `LayoutMultiSchemaField` now passes both props on those same terms.
What a `FieldTemplate` gains is `errorSchema`, which `ArrayFieldTemplateProps` and `ObjectFieldTemplateProps` already declared: it carries every error whatever `hideError` says, so a template that renders the errors itself can reach the ones the directive withholds, which blanking `rawErrors` had left it no way to do.
A template that spreads its leftover props onto a DOM node should destructure `errorSchema` out along with the rest, or React will warn about an unknown `errorschema` attribute.

The form-level error list is unaffected; it is controlled separately by [`showErrorList`](../api-reference/form-props.md#showerrorlist).


### Clearing a custom error now also clears it from the error list BREAKING CHANGE

A field, widget or template can raise its own error by passing an `errorSchema` as the third argument of `onChange`:

```tsx
onChange(value, fieldPath, { __errors: ['must be a company address'] });
```

Clearing it again — calling `onChange` for the same path with no `errorSchema` — used to remove the message from the field but leave it in the list the `ErrorListTemplate` renders, until the next validation replaced the list wholesale. Both now drop the entry at the same time.

This was an aliasing accident rather than a design: when the validator's own error schema is empty, `validationDataMerge()` returns the additional schema *by reference*, so the form's committed `errorSchema` and the custom-error builder were the same object. Clearing mutated it in place, which the field saw when it re-rendered, while the top-level `errors` array was never rebuilt. The form no longer mutates committed state, so the list is recomputed instead.

If you have a test asserting that a cleared custom error is still listed at the top of the form, it will now fail; the error is gone from both places.

### `noValidate` now turns off live validation on blur BREAKING CHANGE

`noValidate` disables validation everywhere else — on change, on submit, and when props change — but `liveValidate='onBlur'` ran and displayed schema errors regardless of it. It is now honored there too.

If you combined `noValidate` with `liveValidate='onBlur'` and depended on blurring a field to produce errors, drop `noValidate`:

```diff
-<Form noValidate liveValidate='onBlur' ... />
+<Form liveValidate='onBlur' ... />
```

### `FormHandle.validate()` takes only the data BREAKING CHANGE

`validate()` now takes only the data to validate: `validate(formData)`. Its `schema`, `altSchemaUtils` and `retrievedSchema` parameters are gone. They existed for the form's own validation passes, which call the internal pipeline directly. Nothing on the handle is typed by the schema or the form context any more, so the type is `FormHandle<T>` rather than `FormHandle<T, S, F>`.

To validate against another schema or validator, build the utilities for it and call its validator yourself, passing the form's `customValidate`, `transformErrors` and `uiSchema` as `validate()` did:

```diff
-const { errors } = formRef.current.validate(data, otherSchema, otherSchemaUtils);
+const { errors } = otherSchemaUtils
+  .getValidator()
+  .validateFormData(data, otherSchema, customValidate, transformErrors, uiSchema);
```

`validate()` also added the errors of `ui:required` fields on top. For those, merge `otherSchemaUtils.getUiRequiredErrorSchema(uiSchema, data)` into the result with `validationDataMerge()`.

## New Features

### `getFormData()` and the `FormHandle` type

Think of `formData` and `initialFormData` as `value` and `defaultValue` on an `<input>`.
With `initialFormData` the form owns the data, and until now the only way to see it was `onChange`, so autosave, an "unsaved changes" guard, or a submit button rendered outside the form all had to copy every change into your own state.
`getFormData()` reads it on demand:

```tsx
function Editor({ record }) {
  const formRef = useRef<Form>(null);

  useEffect(() => {
    const timer = setInterval(() => api.draft(formRef.current?.getFormData()), 30_000);
    return () => clearInterval(timer);
  }, []);

  return <Form ref={formRef} schema={schema} validator={validator} initialFormData={record} />;
}
```

Two things to know:

- **It reads committed data.** An edit or `setFieldValue()` in the same tick is not visible until React commits it, so read after the commit (in tests, after `await act(...)`).
- **It returns what the form renders.** With a `formData` prop that is usually the value you passed, but not always: the form still keeps a reconciled copy, so a change your `onChange` handler declined is returned until you re-render the form with the value you want. The ownership switch removes that copy and makes the prop the only source.

`FormHandle<T>` names every supported ref member and `Form` implements it. The deprecation note above shows how to type a ref against it.

### `ui:initialValue` and `ui:required`

Two new uiSchema directives complement the extended `ui:emptyValue` above, for forms that want to control a field's initial value or required-ness without editing the underlying schema:

- **`ui:initialValue`** pre-fills a field on initial render and after a form reset. It takes priority over `schema.default`, but never overrides `formData` that's already been provided. This is useful for a field — often hidden — that a particular form wants to fix to a known value, e.g. a `country` field defaulted to `'US'` for a US-only form.
- **`ui:required`** overrides a field's `required` status from the UI side only. Setting it to `true` shows the required indicator and adds the field to the effective required set used for validation, even if the schema doesn't mark it required. Setting it to `false` hides the indicator on a schema-required field, but does **not** suppress schema-level validation — pair it with `ui:initialValue` or `ui:emptyValue` so the field always has a value, or you'll get a `console.warn`. `ui:required` must be set per field; it is not honored via `ui:globalOptions`.

See [`ui:initialValue`](../api-reference/uiSchema.md#initialvalue) and [`ui:required`](../api-reference/uiSchema.md#required) for details and examples.

`ui:required` is enforced by walking the rendered form itself rather than by rewriting the schema handed to your validator, so it works the same way regardless of which validator you use — including the precompiled validators (`AJV8PrecompiledValidator` from `@rjsf/validator-ajv8` and `ATAPrecompiledValidator` from `@rjsf/validator-ata`), which enforce it too. The one difference from a schema-level required error: a `ui:required` error is built by RJSF, not your validator, so it doesn't pass through a custom `transformErrors` function and doesn't carry validator-specific fields like AJV's `params.missingProperty`. See [`ui:required`](../api-reference/uiSchema.md#required) for details.

### `ui:options.optgroups` for grouped `<select>` options

Every theme's `SelectWidget` now supports grouping enum options into labeled sections (rendered as `<optgroup>` elements, or each theme's closest equivalent — see the [`optgroups` docs](../api-reference/uiSchema.md#optgroups) for the specifics per theme) via `ui:options.optgroups`:

```tsx
const uiSchema: UiSchema = {
  'ui:options': {
    optgroups: {
      Latin: ['lorem', 'ipsum', 'dolorem'],
      Greek: ['alpha', 'beta', 'gamma'],
    },
  },
};
```

Keys are the group labels; values are arrays of enum values belonging to that group. Enum values not listed in any group render ungrouped after the groups. This is purely additive — existing forms are unaffected unless `optgroups` is set.

### `propertyNames.enum` renders the key as a dropdown

An object whose `propertyNames` enumerates the allowed key names now renders each `additionalProperties`/`patternProperties` key as a dropdown of those names rather than a free-text input, in every theme:

```tsx
const schema: RJSFSchema = {
  type: 'object',
  additionalProperties: { type: 'boolean' },
  propertyNames: { enum: ['darkMode', 'betaBanner', 'offlineCache'] },
};
```

A name another key already holds is left out of the dropdown, and the add button creates the new property under the first allowed name that is still free instead of `newKey`.
`canExpand()` hides the add button once every allowed name is taken, the way it already does at the `maxProperties` limit, so a **custom `ObjectFieldTemplate`** that calls it picks this up on its own.
A `propertyNames` without an `enum`, such as one constraining names by `pattern`, keeps the free-text input, so existing forms are unaffected.

The names reach `WrapIfAdditionalTemplate` as a new optional `propertyNamesEnum` prop on `FieldTemplateProps`/`WrapIfAdditionalTemplateProps`.
A **custom `FieldTemplate`** that lists the props it forwards to `WrapIfAdditionalTemplate` one by one, rather than spreading them, has to add `propertyNamesEnum` to that list for the dropdown to appear, and `keyName` for the key it renders to be the real one (see [`FieldTemplateProps` gains a required `keyName`](#fieldtemplateprops-gains-a-required-keyname-breaking-change)).
A **custom `WrapIfAdditionalTemplate`** renders the dropdown by handing the prop to the new `AdditionalPropertyKeySelect` component from `@rjsf/utils`, which resolves the theme's own `SelectWidget`:

```tsx
{propertyNamesEnum ? (
  <AdditionalPropertyKeySelect
    id={`${id}-key`}
    label={keyLabel}
    value={keyName}
    propertyNamesEnum={propertyNamesEnum}
    onKeyRename={onKeyRename}
    disabled={disabled}
    readonly={readonly}
    required={required}
    registry={registry}
  />
) : (
  <input type='text' id={`${id}-key`} onBlur={onKeyRenameBlur} defaultValue={keyName} />
)}
```

### Multiple types and unconstrained properties can be edited through the fallback UI

JSON Schema lets a `type` be a list of types.
v6 rendered the first type in that list and gave no way to reach the others, and it rendered a property described only by `additionalProperties: true` as a field for whatever type the data happened to hold, with the same one-way door.
Turning on the [useFallbackUiForUnsupportedType](../api-reference/form-props.md#usefallbackuiforunsupportedtype) prop now renders both through `FallbackField`, which pairs a type selector with the field for the type currently chosen:

```tsx
const schema: RJSFSchema = {
  type: 'object',
  properties: {
    // a selector offering exactly these three types
    multi: { type: ['string', 'number', 'boolean'] },
    // a selector offering every JSON Schema type, for each key added here
    anything: { type: 'object', additionalProperties: true },
  },
};

render(<Form schema={schema} validator={validator} useFallbackUiForUnsupportedType />, document.getElementById('app'));
```

Switching the type casts the value that is already there where it can (a number to its string spelling, a string to the number it reads as) and starts from an empty value where it cannot, such as an object, an array, or a number from text that reads as no number at all.
The selector also now offers `integer` and `null` alongside the five types it offered in v6, and starts on the type the current form data has.
Every other keyword of the schema still describes the value, so a union declaring `properties`, `items`, `format` or `minimum` keeps them for whichever type is in effect.

A schema pairing multiple types with an `anyOf` or `oneOf` gets both selectors: the type selector wraps the option selector, and each option renders for whichever type is currently chosen.
Every member of the union is therefore reachable from within an option, where in v6 an option could only ever be the first type in the list.

Four things are deliberately unchanged:

- **A nullable type** (`['string', 'null']`) still renders as a plain `string` field, since [getSchemaType()](../api-reference/utility-functions.md#getschematype) resolves it to that single type. Only a union of more than one non-`null` type gets a selector.
- **With the prop off** (the default), the first type in the list still wins, exactly as in v6. The selector is the opt-in fallback UI, so nothing changes for a form that hasn't enabled it. A union paired with an `anyOf` or `oneOf` stays one-way too, since the option selector alone cannot reach the other types.
- **A schema pinning its value with an `enum`, a `const`, or an `anyOf`/`oneOf` of constants** renders as the select or constant field it always has, with no type selector, since switching type would only cast a value the user picked into one the schema rejects.
- **A field whose `ui:widget` is a component** renders through that control alone, with no type selector, the same way one with a `ui:field` does.
  A control written for that schema handles the types it allows, so wrapping it would pin the schema to one of them and cast the value on every switch.
  A `ui:widget` naming a widget by string is a theme's control for a single type, which is the choice the selector is there to make, so it renders within the selector instead — and is dropped for a chosen type the theme has no implementation of.
  A schema with no usable type of its own — an unrecognized `type`, or an `additionalProperties` entry left unconstrained — still gets a selector, since it lists no types for such a control to handle, and the widget renders within it for whichever type is chosen.
  A list naming an unrecognized type alongside a recognized one offers only the recognized ones, `null` included: a `['foo', 'null']` offers `null` and nothing else.

See [Multiple types](../json-schema/single.md#multiple-types) for details.

### New types

The following new types were added to `@rjsf/utils`:

- **`MarkdownTemplateProps<T, S, F>`**: the props a `MarkdownTemplate` receives, generic over the same `<T, S, F>` as every other template's props. `children` is the markdown string to render; `uiSchema` and `registry` are picked from the form's base props, so an implementation can read `ui:options`, reach `registry.translateString`, or fall back to another template.
- **`FieldPath`**: a branded string identifying a field by the path to its data, such as `friends[0].firstName`. See [Field identity](#field-identity-is-a-fieldpath-string-instead-of-a-fieldpathid-object-breaking-change).
- **`UiOptionsCheck`**: The `{ when, then }` shape used to extend `UiSchema`'s widget/field/option vocabulary for a given form-data type, once a `Checks` union is passed as `UiSchema`'s fourth type parameter.
- **`CoreUiOptionsChecks`** (`@rjsf/core`): The `UiOptionsCheck` union describing `@rjsf/core`'s own built-in widgets, fields and `ui:options`. Pass it as `UiSchema`'s `Checks` argument (union it with your own `Checks` to extend it further) - it isn't included automatically.
- **`IndexedEnumOptionType<S>`**, **`EnumOptionsGroupType<S>`**, **`GroupedEnumOptionsType<S>`**: the option/group shapes returned by `groupEnumOptions()`, described below.

### Type-safe UiSchema (opt-in)

`UiSchema<T, S, F, Checks>` takes a fourth, opt-in type parameter: pass a `Checks` union and it narrows `ui:widget`/`ui:field`/`ui:options` to only the values valid for each field's form-data type, instead of accepting any value the way it does with no `Checks`. An inline `uiSchema` JSX literal gets this narrowing too, by checking it with TypeScript's `satisfies` operator - no wrapper component needed.

`Checks` defaults to `never`, which preserves `UiSchema`'s behavior exactly as it was before this parameter existed - passing it is entirely opt-in and can be done incrementally, field by field or form by form.

See [Type-safe UiSchema](../api-reference/uiSchema.md#type-safe-uischema) for the full documentation, including examples, how to extend the widget/option vocabulary via `Checks`, and the current known gaps.

### New non-validator utility functions

- **`toFieldPath(segment, parentPath?)`**: appends a property name or array index to a parent `FieldPath`. `ROOT_FIELD_PATH` is the path of the root form.
- **`fieldPathToList(fieldPath)`**: parses a `FieldPath` back into a `FieldPathList`, with array indexes as numbers.
- **`fieldPathToId(fieldPath, globalFormOptions)`**: derives the DOM id from a `FieldPath` using `idPrefix` and `idSeparator`.
- **`fieldPathToName(fieldPath, globalFormOptions, isMultiValue?)`**: derives the HTML `name` from a `FieldPath` using the configured `nameGenerator`.
- **`fieldPathEndsWithIndex(fieldPath)`**: reports whether a `FieldPath` addresses an array element.
- **`replaceEqualDeep(prev, next)`**: returns `next` with every subtree deeply equal to `prev` replaced by the `prev` instance, so reference-based memoization sees unchanged data as unchanged. `Form` applies it to the state it builds for a change.
- **`localTimeToOffsetTime(time)`**: appends the browser's current local UTC offset to a bare `HH:MM`/`HH:MM:SS` time string, without altering the wall-clock value.
- **`offsetTimeToLocalTime(time)`**: strips a trailing timezone offset (`Z` or `+HH:MM`/`-HH:MM`) from a `time` string, for feeding back into a native time input.
- **`padTimeSeconds(value)`**: appends `:00` seconds to a bare `HH:MM` time or the time portion of a naive local date-time string that's missing them, since RFC 3339 requires seconds regardless of whether a timezone offset is present.
- **`useTimeWidgetProps(props)`**: hook that combines the three functions above into a `TimeWidget`'s offset-free display value and a `computeTimeValue()` transform for its `onChange` handler. Shared by the `TimeWidget`s in `@rjsf/core`, `@rjsf/daisyui`, and `@rjsf/mantine`.
- **`getDateTimeLocalValue(schema, value)`**: reports whether `schema.format` is `iso-date-time` and, if so, strips a timezone offset from the value for display. Shared by the `DateTimeWidget`s in `@rjsf/core`, `@rjsf/antd`, `@rjsf/daisyui`, and `@rjsf/mantine`.
- **`getNumericInputTitle(inputProps, translateString)`**: returns the `title` for the numeric text input a `number`/`integer` field now defaults to — `TranslatableString.NumberInputTitle` ("Enter a number") or `TranslatableString.IntegerInputTitle` ("Enter a whole number"), localized through the given `translateString` — or `undefined` when `getInputProps()` set no `pattern` for the browser to reject a value against. Called by the `BaseInputTemplate` of every theme that renders a plain native `<input>`; call it from your own if you replace that template.
- **`getStaticItemsUiSchema<T = any, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = any>(uiSchema?: UiSchema<T, S, F>, index?: number): UiSchema<T, S, F> | undefined`**: Returns the static (non-function) form of `uiSchema.items` that applies at tuple position `index` — a single object applies uniformly, an array of per-position objects resolves to the entry at `index` (or `undefined` when no `index` is given), and the dynamic `(itemData, index, formContext) => UiSchema` function form always resolves to `undefined`, since callers computing array item defaults don't have an item's data, index, or form context available to call it with
- **`getUiRequiredErrorSchema<T = any, S extends StrictRJSFSchema = RJSFSchema, F extends FormContextType = any>(validator: ValidatorType<T, S, F>, rootSchema: S, uiSchema: UiSchema<T, S, F> | undefined, formData: T | undefined, customMergeAllOf?: CustomMergeAllOf<S>, uiSchemaDefinitions?: UiSchemaDefinitions<T, S, F>, globalUiOptions?: GlobalUISchemaOptions, formContext?: F): ErrorSchema<T>`**: Walks `rootSchema` and `formData` the same way `SchemaField` resolves each node while rendering, returning an `ErrorSchema` with a required error for every `ui:required: true` field that's missing. Also available as `SchemaUtilsType.getUiRequiredErrorSchema(uiSchema, formData, uiSchemaDefinitions, globalUiOptions, formContext)`, which supplies the first two arguments from the `SchemaUtils` instance
- **`groupEnumOptions(enumOptions, optgroups?, enumDisabled?)`**: groups `enumOptions` according to `ui:options.optgroups`, tagging every option with its original array index (needed for index-based value encoding) and its disabled status. Powers the `optgroups` support in every theme's `SelectWidget`, described above.
- **`isEnumOptionsGroup(item)`**: type guard distinguishing a group from a standalone option in the list `groupEnumOptions()` returns.
- **`flattenGroupedOptions(groupedOptions)`**: flattens the list `groupEnumOptions()` returns back into a plain list of options, in render order. For widgets that need every option in one flat collection (e.g. for value lookup) while still rendering the grouped structure.
- **`getUnionTypes<S extends StrictRJSFSchema = RJSFSchema>(schema: S): JSONSchema7TypeName[] | undefined`**: Returns the types a schema allows when it allows more than one of them, i.e. its `type` is an array of two or more non-`null` type names, dropping unknown names and duplicates; `undefined` for anything `getSchemaType()` resolves to a single type, a nullable type included. Paired with the new `JSON_SCHEMA_TYPES` constant, the list of every JSON Schema type name, which is what the fallback UI offers for a schema that constrains the type not at all
- **`getKnownTypes<S extends StrictRJSFSchema = RJSFSchema>(schema: S): JSONSchema7TypeName[]`**: Returns the JSON Schema types a schema lists, dropping unknown names and duplicates, however many are left; an empty array for a schema whose `type` is a single name, since a name of its own is not a list to choose from. This is the list `getUnionTypes()` narrows to the schemas allowing more than one type, and the one the fallback UI offers for a schema that lists only one recognized type alongside names no field can render
- **`getVisibleErrors(props)`**: returns the errors a widget or template should surface in its own UI, given anything carrying `rawErrors` and `hideError` (its `VisibleErrorsProps` parameter type is exported too). The list is empty whenever `ui:hideError` is in effect, so a component can derive its error state from one call instead of pairing `rawErrors` with `hideError` itself. Used by every theme's widgets; see [`ui:hideError` now suppresses the theme's error styling](#uihideerror-now-suppresses-the-themes-error-styling-breaking-change).
- **`hasVisibleErrors(props)`**: the boolean form of `getVisibleErrors()`, for the widgets and templates that only need to decide whether to render an error state rather than render the errors themselves.

### Changes to existing utility functions

- **`getDefaultFormState()`**: Added an optional trailing `uiSchema` parameter used to apply `ui:emptyValue` and `ui:initialValue` as defaults
  - This new optional parameter was added to the `SchemaUtilsType` interface's version of `getDefaultFormState()` as well
- **`getSchemaType()`**: A schema without a `type` whose `const` is falsy (`0`, `false`, `''` or `null`) now reports the constant's type instead of `undefined`. See [A typeless `oneOf`/`anyOf` of constants now renders as a select](#a-typeless-oneofanyof-of-constants-now-renders-as-a-select-breaking-change) for what this changes
- **`enumOptionSelectedValue()`**: In the `realValue` format the selected value is encoded with `enumOptionValueEncoder()`, the same way the options' values are, instead of with `String()`, so a selected object value now matches its option. A `null` still encodes to the empty string, which a select's placeholder option also carries, so a `null` option is not yet selectable in `realValue` specifically; the default `indexed` format handles it correctly. It also no longer reports "no selection" purely because the value equals the `emptyValue` a widget passed it, so an option carrying that widget's `null` or `''` sentinel shows as selected
- **`retrieveSchema()`**: The stub it builds for a property described only by an `additionalProperties` with no `type` now keeps the rest of that subschema instead of discarding it, so a property constrained by an `enum`, a `format`, a length or a range renders as a field that honors it rather than as free text. Subschema keywords such as `allOf`, identifiers such as `$id`, containers such as `$defs` and `definitions`, and a `default` of another type than the data are left out. This is not gated behind `useFallbackUiForUnsupportedType`, so such a property renders as the field its constraint calls for in every form, and a value of another type than that constraint allows is as invisible in it as in any field for a schema that names a type. The stub still takes the type of the data the property holds, and is now marked with the new `GUESSED_TYPE_FLAG` symbol to record that the type was guessed rather than declared by the schema when the subschema asserts nothing about the value
- **`sanitizeDataForNewSchema()`**: A property is no longer treated as having changed schema when its type differs but both the old and the new type carry `GUESSED_TYPE_FLAG`, since those types describe the data rather than anything either schema requires. Without this, switching the type of such a property through the fallback UI discarded the value as data belonging to an old schema. A new schema that declares a type of its own is still the type the data has to satisfy
