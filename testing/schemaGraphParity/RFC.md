# RFC: Parse each schema once into a graph and build the form from a field tree (v7)

Status: proposal, for discussion. Target branch: `v7`, which is unreleased; the latest published version is 6.11.0. Packages: `@rjsf/utils`, `@rjsf/core`, the validator packages, and the themes in stage 4 only.

Everything here was checked against `origin/v7` at `c8856747e`. The labels mean:

- **Verified**: a probe was run on that commit. The probes are not committed.
- **Inferred**: the claim comes from reading the code and was not executed.
- **Prototype**: a standalone model of the recursion rule in section 4.4. It ran over 65 hand-written recursive shapes, then over 154 recursive cases captured mechanically from the utils and core test suites and the playground samples. Each result was compared with v7's `getDefaultFormState` (checked for idempotence over repeated passes) and with a real `Form` render (input ids and Expand buttons). Three adversarial reviews then attacked the rule on termination, parity with v7 and implementability, and their findings are folded in below. The prototype has known gaps, listed in section 8.

## 1. Summary

RJSF resolves a schema by building copies of it. `$ref` targets are inlined into copies, and the copies are tagged with Symbol markers so that later code can work out where each piece came from. Recursion is stopped by a single string stack that does two jobs: it records "inside of" (properties, items, additional keys) and "merged with" (`$ref` with siblings, `allOf`, `then`/`else`, `dependencies`, the selected option). On top of that, about ten consumers each re-resolve the schema their own way, and five of them guess the selected `oneOf`/`anyOf` option independently.

The proposal:

1. **Parse** each root schema once into an immutable `SchemaGraph`. Each subschema is a node addressed by its canonical location (a JSON pointer into the root). A `$ref` becomes an edge, and `$id` base URIs are resolved during the parse.
2. **Build a field tree** from three inputs: the graph, the form data, and Form-level UI state (the selected option per field, and which cycles are expanded). Each field has a data path, an ordered **merge plan** (the graph nodes merged at that path, with the `$ref` path through which each was reached) and a merged schema for widgets.
3. Use **one recursion rule**, defined exactly in section 4.4. It cuts a recursive `$ref` edge when its target is already on the field's `$ref` path, or occurs twice there through any edge. It terminates on every shape that overflows on v7 today (prototype), and its depth per chain is bounded by the number of `$ref`s (inferred argument, checked on adversarial families). It does **not** reproduce v7 on every shape. Section 7 lists each known difference with a before/after example.
4. Make the consumers read the tree: rendering, defaults, `ui:required`, sanitize and omit. Validate by pointer into the raw root where that preserves meaning, and through graph-named derived schemas where it does not (option scoring).
5. Keep the public `@rjsf/utils` functions. Where a function's output changes, record it as a breaking change in `CHANGELOG-v7.md` and the v7 upgrade guide.

The work ships in five stages (section 10). Each stage is gated by a differential harness against both 6.11.0 and current v7.

Claims dropped because probes or reviews refuted them:

- **"Compatibility wrappers with no observable change."** Refuted. `retrieveSchema`, `getDefaultFormState`, `schemaParser` and the schemas passed to validators all change, in specific and documented ways.
- **"Every validation is a pointer or a conjunction of pointers."** Refuted. Option scoring removes constraints, which a pointer cannot express. `$ref` siblings and branch merges are applied as overrides, not conjunctions.
- **"The superset rule reproduces v7."** Refuted. The superset-plus-reset rule from the earlier draft also made defaults grow on every pass (section 4.4, rejected variants). Section 4.4 replaces it.
- **"Termination follows from a finite number of node subsets."** Refuted as a useful bound. A set-equality check allows chains whose length is the lcm of coprime ref-cycle periods (depth 2311 from 29 definitions, prototype). The final rule terminates through the count-2 check instead, and set equality is only a guard.
- **"`getDefaultFormState` is idempotent because its depth is bounded by the schema."** Refuted. It is idempotent unless an `if`/`anyOf`/`oneOf` choice depends on values that defaults supply (section 4.5). v7 behaves the same on those shapes.
- **"Stage 1 can keep per-call cycle unrolling for copies."** Refuted. That mechanism is what makes v7 render out of memory on a four-definition graph (section 4.10).

## 2. Problem

### 2.1 The schema is resolved into copies

- `resolvedSchemaOf` is the one place where a `$ref` turns into a copy: `{ ...definition, ...siblings, [RJSF_REF_KEY]: ref }` (`packages/utils/src/refOf.ts:64-73`). The siblings *replace* keys of the definition shallowly. This is an override, not a conjunction. Verified: `{$ref A(properties x), properties:{y}}` resolves to `properties {y}` only.
- `resolveAllReferences` (`packages/utils/src/schema/retrieveSchema.ts:599-751`) walks a copy and inlines `$ref`s. It follows only the top-level `$ref`, `properties`, object-form `items`, and options when `resolveAnyOfOrOneOfRefs` is set. It does not follow `allOf`, `then`/`else`, `dependencies`, `patternProperties`, `additionalProperties` or `prefixItems`. Those keywords are handled by separate branch calls in `retrieveSchemaInternal` (`:1424-1586`).
- `retrieveSchema` resolves one level per call (documented in `utility-functions.md:2169`). Each `SchemaField` render resolves again, starting from a fresh path (`SchemaField.tsx:459-462`). `ObjectField.tsx:393-396`, `ArrayField.tsx:611`, `MultiSchemaField.tsx:232` and antd's `ObjectFieldTemplate/index.tsx:104-121` re-retrieve schemas that have already been retrieved.
- The eager walk is path-sensitive, so one call expands every simple path through the definitions. Verified on a dense graph `K_n` (each of `n` definitions has a `$ref` property to every other one, root `$ref d0`): one `retrieveSchema(root)` takes 364 ms at n=9 (1.1M tree nodes) and 3.4 s at n=10 (10.9M nodes), and OOMs at n=30 under `--max-old-space-size=3072`. `getDefaultFormState` takes 90 ms at n=4 and 10.7 s at n=5.

### 2.2 Markers are used to recover what copying lost

Because each copy loses its origin, the code tags copies and reads the tags back:

| Marker | Written | Read |
|---|---|---|
| `RJSF_REF_KEY` | `refOf.ts:69` | `resolveUiSchema.ts:49,92`, `enclosingRefPath`, `schemaParser.ts:109`, `getDefaultFormState.ts:675`; deleted again at `FallbackField.tsx:169` |
| `RJSF_REF_SIBLING_BRANCHES_KEY` | `refOf.ts:35-54,71` (frozen, memoized list) | `refOf.ts:109-123` |
| `RJSF_REF_CYCLE_KEY` | `retrieveSchema.ts:526,637,1539` | `SchemaField.tsx:458`, `getUiRequiredErrorSchema.ts:135`; written as `false` at `CyclicSchemaField.tsx:40` |
| `PATTERN_MERGE_LEFT_UNDONE` | `retrieveSchema.ts:1540` | `:1550` |

The markers are lossy. These failures were verified:

- An `allOf` merge replaces the outer schema's `RJSF_REF_KEY` with the first entry's (`retrieveSchema.ts:1471-1491`). For `A = {allOf:[{$ref B}], ...}`, the merged node carries `B`, so `ui:definitions['#/definitions/A']` is not applied to it.
- A self-`allOf`, and `Pet -> then Cat -> allOf[Pet]`, leave a literal `"$ref"` string key on the merged result.
- One "Expand Cycle" click reveals two levels for recursion through `properties`, and one level for recursion hosted in `then` or `allOf` (section 4.7). The second level is a side effect of the `resolveAnyOfOrOneOfRefs=true` re-retrieve at `ObjectField.tsx:394` combined with the pass-0 exception at `retrieveSchema.ts:650-665`.
- `retrieveSchema` is not idempotent. Retrieving an already-retrieved copy unrolls one more level and leaves the expanded child still flagged `RJSF_REF_CYCLE_KEY: true`. On `K4` (four definitions) this makes the `Form` render run out of memory: along one path the copy grows from 81 nodes to 2721 after ObjectField's re-retrieve, then 906 → 29 946 → 988 266 at depth 1 (verified).

The marker approach cannot be removed in one step. A raw subschema can be expanded in one place and collapsed in another, and only provenance carried on the copy can tell them apart (verified, `v7` and prototype agree): with `A={a, b:$ref B}`, `B={c, a2:$ref A}`, `C={x:$ref A, y:$ref B}` and root `$ref C`, the same object `A.properties.b` renders at `root_x_b` and collapses at `root_y_a2_b`, and both parent copies carry `RJSF_REF_KEY = A`. Stages 1-2 therefore replace the four markers with one private provenance stamp (section 4.1). Provenance on copies disappears only in stage 3, when consumers read the field tree.

### 2.3 One path stack for two kinds of edge

`recurseList` is a `string[]` of `$ref`s. Containment edges and conjunction edges both push onto it. Branch calls rebuild it from markers with `enclosingRefPath` (`refOf.ts:117-140`, nine call sites), and many calls reset it to `[]`:

- `resolveAnyOrOneOfSchemas:1643`
- `matchingOption:1230`
- `relaxOptionsForScoring:1722`
- `getClosestMatchingOption.ts:155`
- `omitExtraData.ts:280,374`
- the nested `retrieveSchema` at `:1350`
- every `SchemaField` render

Several devices exist only to make this terminate:

- `passCount`, with `+1` and `>0 ? 1 : 0` resets, and its backstop `MAX_RESOLUTION_PASSES = 100` (`:54, 522-527`)
- `ReferenceTally`, which detects the fixpoint (`:563-574`)
- the pass>0 checks at `:629-640`
- the pattern-merge seed list (`:1501-1532`)
- three private `followedRefs` sets (`:285-387`, `:1040-1203`)

The result still overflows on real shapes. Verified: #5500 (six shapes), #5452 (a, b, c), the mutual `dependencies` recursion A<->B, and render OOMs for #5501, for a self-referencing `anyOf` option, and for `K4`.

### 2.4 Many consumers, each with its own resolver and option predictor

| Consumer | How it resolves | How it picks the option |
|---|---|---|
| `SchemaField` render | `retrieveSchema` per level, path reset | `MultiSchemaField` `useState` (`MultiSchemaField.tsx:164`), re-matched during render |
| `getDefaultFormState` | root retrieve plus its own `_recurseList` walk (`getDefaultFormState.ts:287-569`) | `getClosestMatchingOption(rawFormData ?? default, raw options, 0)` (`:439-442`) |
| `namesRenderedElsewhere` (stubbing extra keys) | separate lookup-based resolver (`retrieveSchema.ts:939-1294`) | `getFirstMatchingOption` on ref-resolved raw options (`:1221-1244`) |
| `omitExtraData` | own walk with a `resolvedRefs` map, importing `resolveAllReferences` | `getClosestMatchingOption` over relaxed options (`omitExtraData.ts:259-283`) |
| `getUiRequiredErrorSchema` | own walk; stops at the cycle marker (`:135`) | `getClosestMatchingOption(..., 0)` (`:75`) |
| `formState.getPropertySchemaAt` | per-level retrieve (`formState.ts:1524-1577`) | `getClosestMatchingOption(..., 0)` |
| `stalePathsForNewSchema` | per-key retrieve | gives up at any level whose options declare properties (`:83-95, 371-376`) |
| `schemaParser` | expand-all-branches copies | records every option form, plus four side-effect `isValid` passes (`retrieveSchema.ts:1645-1678`) |
| `sanitizeDataForNewSchema` | lockstep walk of two retrieved copies | inherits whatever the caller passes |

These predictors disagree with each other and with the user's explicit choice. Verified on v7:

- #5461: the selector shows B while `root_b` renders twice.
- #5465: a stale `cfg: {name:'a'}` survives a branch switch.
- Typing into option B switches the selector back to A, because `getClosestMatchingOption.ts:97-101` scores a truthy default.
- A `{type:'null'}` first option makes an object selection revert to None (the tie-break at `:201-203`).
- `ui:required` inside the selected `anyOf` option is not enforced: `validateForm()` returns `true`.
- `ui:required` below a cycle is never enforced, even after the user expands it.

The Form data pass itself is a fixpoint loop (`formState.ts:812-1091`): fill defaults, retrieve, sanitize, drop stale paths, repeat until the data hash repeats. A settled-snapshot apparatus (`Form.tsx:261-302`) exists to give sanitize a "previous" side to compare against.

## 3. Principles

- **Parse, don't validate.** Turn the untyped schema into a typed graph once. Downstream code receives node handles and never re-inspects raw objects to work out where they came from.
- **One source of truth per fact.**
  - Where a subschema lives: its canonical location.
  - What is merged at a data path: the field's merge plan.
  - Which option is selected: Form state.
  - Whether a cycle is expanded: Form state.
  - What a validator checks: a named pointer or a named derived schema.
- **Separate containment from conjunction.** Only containment creates ancestors. A conjunction adds members to the same field.
- **Name the policy.** Where v7 behaviour is a policy rather than structure (depth of defaults, which edges may collapse, `allOf` under `skipDefaults`), state it as a rule with a name and a test, instead of leaving it as a side effect of a resolver.
- **Change behaviour only on purpose.** Every output difference from v7 has to appear on the harness allowlist with a changelog entry.

## 4. Design

### 4.1 Parser, `SchemaGraph` and provenance

```ts
type NodeId = number & { readonly __node: unique symbol };

interface SchemaGraph<S extends StrictRJSFSchema = RJSFSchema> {
  /** schemaUtils.getRootSchema(): for 2020-12 roots this is still the makeAllReferencesAbsolute copy,
   *  which validators register today. Pointers in the graph are pointers into this object. */
  readonly rawRoot: S;
  readonly root: NodeId;
  node(id: NodeId): SchemaNode<S>;
  byPointer(pointer: string): NodeId | undefined;
  /** Interned derived schemas: one per (node, transform); see 4.9. */
  derived(id: NodeId, transform: DerivedTransform): DerivedNode<S>;
  readonly diagnostics: readonly Diagnostic[];
}

type SchemaNode<S> =
  | { kind: 'boolean'; id: NodeId; pointer: string; value: boolean }
  | { kind: 'invalid'; id: NodeId; pointer: string; ref: string; reason: 'dangling' | 'circular-alias' }
  | ObjectNode<S>;

interface ObjectNode<S> {
  kind: 'schema';
  id: NodeId;
  pointer: string;            // canonical location: JSON pointer into rawRoot
  baseUri: string;            // resolved per RFC 3986 against the parent's base
  literalId?: string;         // $id as written: `fields` registry lookup keys on this (SchemaField.tsx:286,325)
  raw: S;                     // the original object, never copied
  /** True when the node holds only $ref plus definitions/$defs/$schema/$comment/title/description. */
  pureRef: boolean;
  ref?: NodeId;               // resolved $ref target; with siblings the node keeps override semantics (4.2)
  keywords: Readonly<Partial<S>>;  // non-subschema keywords
  // containment edges
  properties?: ReadonlyMap<string, NodeId>;
  patternProperties?: readonly { pattern: string; node: NodeId }[];
  additionalProperties?: NodeId | false;
  items?: NodeId;
  prefixItems?: readonly NodeId[];   // also tuple-form `items`
  additionalItems?: NodeId | false;
  // conjunction edges
  allOf?: readonly NodeId[];
  if?: NodeId; then?: NodeId; else?: NodeId;
  dependencies?: ReadonlyMap<string, { required: readonly string[] } | { schema: NodeId }>;
  // choice edges
  oneOf?: readonly NodeId[];
  anyOf?: readonly NodeId[];
  discriminator?: string;
}
```

The parser:

- **Memoization.** Results are cached by root object identity in a `WeakMap`, with the schemaUtils instance as the outer key. `doesSchemaUtilsDiffer` already decides when a new root counts as different (`createSchemaUtils.ts:110-128`).
- **Canonical locations.** Every `$ref` is resolved to the node it reaches, after percent-decoding, `$id` base-URI resolution and anchor resolution. Plans and `$ref` paths (4.4) are keyed by that `NodeId`, never by the raw `$ref` string. Otherwise two spellings of the same target count twice, `X AND X` stops being a no-op, and each alias adds a level before the collapse. Verified for percent-encoding: with `child:{$ref:'#/definitions/%41'}` aliasing `A`, v7 and the prototype both collapse at `root_child_child`, and `allOf:[{$ref:A},{$ref:'#/definitions/%41'}]` runs in the prototype while v7 runs out of heap. The `$id` and anchor cases are inferred: the prototype does not resolve `$id`.
- **`$id` and `$ref`.** Base URIs are resolved per RFC 3986 while parsing, which replaces the literal `uriEqual` lookup (`findSchemaDefinition.ts:185`) and fixes #5467. The graph is built over the object `getRootSchema()` returns, so graph pointers and the root validators register stay identical. `makeAllReferencesAbsolute` (`:259-267`) is kept until all three validators have been probed on a 2020-12 root with nested relative `$id` and non-`#` refs registered raw. The case it creates, a 2020-12 root with an `$id` whose `$ref`s it makes absolute against that `$id`, was probed in the stage 2 review: cfworker registered the root under `ROOT_SCHEMA_PREFIX` in place of its `$id`, so an option or `if` written as a `$ref` reached an absolute `$ref` it could not resolve; it now registers the root under its `$id`, as AJV and ata do (4.9, Root id).
- **Dangling refs and alias loops.** A dangling `$ref`, or a `$ref`-to-`$ref` alias loop, becomes an `invalid` node with a diagnostic. `findSchemaDefinition`, `retrieveSchema` and `getDefaultFormState` keep throwing exactly as v7 does: `Definition for <ref> is a circular reference` for an alias loop, and `Could not find a definition for <ref>` for a missing target (`findSchemaDefinition.test.ts:31-43, 171`). They must not return an empty schema; the prototype does, which is one of its gaps. The form throws them too, as 6.11.0 and v7 do (decided after stage 4: no field-error rendering in this series; section 8). Verified on stages 3 and 4 against v7: a property `{ $ref: '#/definitions/missing' }`, a root `$ref` to it and an alias loop give `Could not find a definition for #/definitions/missing.` and `Definition for #/definitions/B is a circular reference` from `retrieveSchema()`, `getDefaultFormState()` and a rendered `Form`, identical messages (`i9probe/dang.test.tsx`).
- **Normalization.** Boolean schemas, `type` lists, `items` versus `prefixItems`, and array versus schema `dependencies` are normalized into the edge fields above. The raw object is kept untouched next to them.
- **`ui:definitions` keys.** These are resolved to nodes with the same rules as `$ref`. Today, keys of the form `#/$defs/x` are silently ignored when a 2020-12 root has an `$id` (verified).

**Provenance on copies (stages 1-2).** Until stage 3, consumers keep calling `retrieveSchema` once per level on copies. The rule in 4.4 needs each copy's `$ref` path, its backstop chain and two flags. None of these can be recovered from `RJSF_REF_KEY` or from the identity of the raw node (section 2.2). So `retrieveSchema` stamps a **private, non-exported symbol** (working name `RJSF_PROVENANCE`) on its top-level output and on every subschema it hands out: `properties` values, `items`/`prefixItems`, `additionalProperties`/`patternProperties` stubs, pattern-merged properties, and `anyOf`/`oneOf` options. An option's stamp carries the field's plan plus the option.

- The value is interned (hash-consed) per `(graph identity, parent provenance id, seed NodeIds, refPath, backstop chain id, data-driven-restart flag, expanded flag)`. `replaceEqualDeep` compares symbol-keyed values with `Object.is` (`replaceEqualDeep.ts:13-21`, `createSchemaUtils.ts:316-329`), so an un-interned value would break the identity stability `renderStability` depends on. `refOf.ts` already interns its sibling-branch lists for the same reason.
- A symbol on the object is the only channel that survives the copies made today (inferred from reading): `CyclicSchemaField` and custom fields spread, which keeps symbols; `getRenderedOptionSchema.ts:84` spreads `{...parent, ...option}`; `mergeSchemas` copies the second object's symbols (`mergeSchemas.ts:34-38`). A `WeakMap` keyed by object identity would lose provenance on every spread. `shallowAllOfMerge` drops symbols, so the merge step re-applies them, as `allOfSymbols` does today.
- A stamp whose graph identity differs from the current root's is ignored, and the input is treated as a call root.
- A stamped copy that is not the object `retrieveSchema` handed out, such as an option merged with its parent or a custom `SchemaField` that renders `{...props.schema, description}`, is planned again from its own keywords, but with the **refPath and backstop chain of the field it copies**. Restarting the refPath there (stage 1 review) let a field that copies its schema at every level recurse without end on mutual recursion (`A<->B` rendered through such a `SchemaField` ran out of heap; v7 renders five fields and `root_b_a-button`), and resolved an unchanged spread `{...b}` one level later than `b` itself. Only `RJSF_REF_CYCLE_KEY: false` restarts it (4.7).
- The stamp replaces `RJSF_REF_SIBLING_BRANCHES_KEY` and `PATTERN_MERGE_LEFT_UNDONE`. `RJSF_REF_KEY` and `RJSF_REF_CYCLE_KEY` are still emitted (7.3).

### 4.2 `$ref` with siblings: an override, and a conjunction along a 2019-09/2020-12 chain

v7 applies sibling keywords as `{...definition, ...siblings}` (verified), and `findSchemaDefinition.ts:342-348` uses `allOf` for chained refs under 2019-09/2020-12. The graph keeps both. A node with both `$ref` and siblings is one node of kind `schema` with `ref` set, and the merge step applies the override per keyword: each keyword comes from the sibling node if present, otherwise from the target. Pure-`$ref` alias chains are flattened the same way.

**A `$ref` reached through another `$ref` under 2019-09 or 2020-12** reads as the `allOf` of the keywords beside it and of its own `$ref`, as `findSchemaDefinition()` reads it. This is the OpenAPI 3.1 inheritance pattern, `Cat={$ref Pet, properties:{meow}}` reached as `pet:{$ref Cat}`: 6.11.0 and v7 render `Pet`'s fields beside `meow` and keep `Pet`'s `required`, and dropping them would remove fields from a common form, so the plan keeps the reading rather than listing a change. The parser adds, for each such node whose `$ref` resolves, a `conjunction` node, `{allOf:[siblings, {$ref}]}`, whose two entries carry the node's own edges and its `$ref`; the plan's `$ref` step reads a target through its `conjunction` where it has one, and leaves the two entries to the `allOf` step, so the `allOf` policy of each view applies to them as to any other `allOf` (render merges them; the defaults under `allOf: 'skipDefaults'` leave them, which for a property gives `{}` on 6.11.0, v7 and after, and under `populateDefaults` give `{pet:{meow:true, name:'pn'}}` on all three, verified; for an extra key of the data, whose `$ref` 6.11.0 and v7 resolved in full at the root, `skipDefaults` now leaves them too, 7.1 item 27). The field's own `$ref` is still an override, as on v7: `pet:{$ref Pet, properties:{meow}}` renders `meow` alone on all three. Corpus: `R ref inheritance 2020`, `R ref inheritance 2019` and `R ref inheritance 2020 chain item`, equal to v7 in render and defaults.

**Under draft-07 and earlier**, v7 lets the final target win over the keywords beside an intermediate link (`{...remaining, ...subSchema}`), so a link's keywords count when the field holds its `$ref` and not when another `$ref` reaches it. The plan applies the override at every link, the rule a field's own `$ref` follows, and the difference is listed in 7.1, item 22. Option scoring resolves an option's own `$ref` through the same step (`refDefinition()`), so it reads a chain as the form does.

Validation of the whole root is already JSON Schema conjunction (AJV), so on submit the rendered schema and validation already diverge here. Section 4.9 shows which validator calls inherit that divergence. Whether v7 should switch `$ref` siblings to conjunction is listed as an open question (section 8), not assumed.

The defaults fold applies the same override, so defaults and render agree on `$ref` siblings. v7 does not: it uses the target's keywords at the first level and the siblings' only at the collapse (7.1, item 12).

A `default` beside a `$ref` is an override like every other keyword beside it, wherever it stands: at the root, on a property or an item, in a draft-07 tuple position or `additionalItems`, along a chain of aliases (each alias's own `default` over its target's), past a `$ref` back into a recursion, in the deep-import `computeDefaults()` on a raw `$ref`, and on an `anyOf`/`oneOf` option written as a `$ref`, which is merged with its field's `default` as an option written in place is. On the root, a property and an item this is what v7 and 6.11.0 already give (`x:{$ref Status, default:'active'}` with `Status={type:'string', default:'draft'}` gives `{x:'active'}`), so the common initial form data does not change. Stage 1 first reproduced v7's narrower reading, where `computeDefaults` read a raw `$ref` and let the target's `default` win past a recursion, along an alias chain, in the deep import and in a `$ref` option; that took a flag on every field and three special cases in the fold, for shapes where v7 was inconsistent with its own root and property behaviour. Under the parity policy (section 7) the special cases are removed and the differences listed in 7.1, item 12. Corpus: `R ref sibling default property`, `root` and `item`, equal to v7; `R ref sibling default rec` and `R ref sibling default tuple`, changed.

### 4.3 Field tree and merge plan

```ts
type Edge = 'root' | 'property' | 'item' | 'tupleItem' | 'additionalKey' | 'patternKey';
type PlanEdge = 'seed' | 'ref' | 'allOf' | 'then' | 'else' | 'dependency' | 'pattern' | 'option';

interface PlanEntry {
  node: NodeId;
  edge: PlanEdge;
  /** $ref targets entered from the nearest refPath start (4.4) to this node, by canonical location. */
  refPath: readonly NodeId[];
}

interface Field<S> {
  path: readonly (string | number)[];
  id: string;                          // today's id scheme, from the path
  edge: Edge;
  /** Containment node(s) this field was reached through: properties/x, items, ... */
  seeds: readonly PlanEntry[];
  /** Ordered merge plan: seeds, $ref targets, allOf entries, applied then/else,
   *  applied dependencies, pattern schemas, the selected option and its closure. */
  plan: readonly PlanEntry[];
  ownSchema: S;                        // SchemaField reads title/description/readOnly from both (SchemaField.tsx:579,698,717)
  schema: S;                           // merged schema for widgets, with the compatibility markers (7.3)
  required: boolean;                   // from the parent's merged `required`, including then/dependencies arrays
  readonly: boolean;                   // inherited (see below)
  disabled: boolean;                   // inherited (see below)
  option?: { list: NodeId; index: number; seeded: boolean };
  cycle?: { cutEdge: PlanEntry; expanded: boolean };
  children: readonly Field<S>[];
}
```

The plan is built from the field's seeds, conjoined in order (first wins). For each node, in v7's order:

| Step | Edge kind | Operator (unchanged from v7) |
|---|---|---|
| a | `$ref`, with or without siblings | keyword-level override, `{...target, ...siblings}` (`refOf.ts:69`); pure-`$ref` alias chains flattened the same way |
| b | `allOf` entries of the node that provides `allOf` | `context.customMergeAllOf ?? shallowAllOfMerge`, entries passed in declaration order, first wins on conflict; a failed merge drops the `allOf` and logs once, as today |
| c | `then` / `else` of the providing node | chosen by `validator.isValid(if, fieldData ?? {}, root)` on the **raw** field data (`retrieveSchema.ts:142`); merged with `mergeSchemas` (the branch deep-overrides, `required` is a union) |
| d | `dependencies` | qualify when `depData[key] !== undefined` and the **declaring node's own** `properties` are absent or contain the key (`:1909-1912`), in `for…in` order, including `withExactlyOneSubschema`'s `oneOf` rule. `depData` is the raw data for render and `{...accumulatedDefaults, ...data}` for defaults. An array dependency adds to `required`; a schema dependency is merged with `mergeSchemas`. Judging against the declaring node rather than the merged result keeps qualification monotone while the plan grows |
| e | declared property matching `patternProperties` | merged with each matching pattern schema in pattern order (`:1495-1576`), after `properties` |
| f | selected option (closest match, or the Form-state choice from stage 3) | `mergeSchemas`, last |

A node already in the plan is skipped (first occurrence wins, compared by canonical location), so `X AND X` is a no-op. Self-`allOf`, `Pet -> then Cat -> allOf[Pet]` and a dependency that refers back to its own definition need no special case, and the literal `"$ref"` that v7 leaves on such merged schemas goes away. The set-equality guard in 4.4 compares the set projection of the plan. The merged-schema memo keys on the `customMergeAllOf` identity, which is already part of the schemaUtils key.

`unevaluatedProperties` joins `additionalProperties` in the extra-key policy (4.6). The extra-key stubbing contract stays exactly as it is through stage 2: a `false` key schema gives `{type:'null'}`, a `$ref`/`allOf` key schema is resolved with its own chain (`:1348-1351`), `ADDITIONAL_PROPERTY_FLAG` and `GUESSED_TYPE_FLAG` land where they do today, and `namesRenderedElsewhere`/`getAdditionalPropertyType` stay until selection state exists in stage 3.

**What the plan depends on.** A field's plan depends on more than the data at its own path:

- the graph;
- the parent field's plan and the refPath of the plan entry that declares the field;
- the parent's *full* data subtree, because `if` and `dependencies` on the parent decide which subschema the child gets;
- for the defaults view, the accumulated defaults, because dependencies are qualified against `{...defaults, ...data}` (`getDefaultFormState.ts:374-387`);
- the Form state for that path.

When the data changes, every ancestor of the edited path re-evaluates its conditions. Any sibling subtree whose plan changed is rebuilt, not only the edited path. A field's `required` comes from its parent's merged `required`; verified: `then: {required: ['detail']}` changes the label with no change to the child's plan.

**Inherited attributes.** `required`, `readonly` and `disabled` are inherited attributes on `Field`, computed from the parent's merged schema and uiSchema. A field gets the `ui:definitions` entry of the `$ref` it was resolved from (`RJSF_REF_KEY`, the field's own `$ref`), under its own uiSchema, as on 6.11.0. The definitions it composes through `allOf` add no entry: the v7 branch applied the first `allOf` entry's instead (the lossy marker of 2.2), and stage 1 first applied both; neither is what released users see, so the rule keeps 6.11.0's single entry and needs no composition walk. Render (`resolveUiSchema`) and the defaults fold apply the same entry.

**Memoization.**

- The merged schema is memoized per `(plan, data at path)`. `if` and dependency `isValid` results are memoized per `(node, data)`, because a parent's lookahead (section 10, stage 1) and the child's own build evaluate the same conditions.
- Both memos live as long as the root schema, so the data they are keyed on must be bounded. Object data is not memoized under, since a caller may mutate it in place. A missing value, `null` or a boolean is a key of its own. A string or number is not: each `(plan seeds, policy)` or `(node)` keeps only the last one seen. A field sees a new string on every keystroke, and keying on each kept every version of the text (stage 1 review: a 100 kB textarea typed into 600 times retained 67.5 MB, against 3.1 MB on v7; 3 000 plans of distinct 20 kB strings retained 67.3 MB, and 0.2 MB once only the last string is kept, verified).
- The rendered field is memoized on a wider key: `(plan, data at path, resolved uiSchema slice, parent-derived attributes such as required/readonly/disabled, Form-state slice, id)`. Two fields with the same plan can need different output, for example `properties.a` and `properties.b` that are both `$ref X` but have different `uiSchema` entries.
- Unchanged subtrees keep their object identity, matching what `replaceEqualDeep` provides today (`createSchemaUtils.ts:316-329`). `renderStability` and `Form.renderCost` guard this.

**`$data` in conditions.** AJV's opt-in `$data` inside an `if`, a dependency or an option reads data outside the field's subtree. Today it is evaluated wrongly in nested conditions (verified: "Cannot access data 2 levels up"). This RFC declares `$data` in condition keywords unsupported and documents that, keeping today's behaviour (section 8).

### 4.4 The recursion rule

**Definitions.**

- **refPath.** Each plan entry carries `refPath`: the list of `$ref` targets, by canonical location, entered on the way from the nearest refPath start to that entry. Entering a `$ref` (step a, directly or through an `allOf` entry, `then`/`else`, a dependency, an alias or the option) appends its target. A containment child's seed inherits the refPath of the plan entry that declares it (the entry providing `properties`, `items`, `additionalProperties` or `patternProperties`). A property declared by several plan entries is checked once per declaring entry, each against its own refPath.
- **refPath starts.** The refPath restarts at:
  - the **call root**: `[]` for a schema object, `[target]` when the call root is a `$ref`. This keeps v7's asymmetry: `getDefaultFormState(pl)` returns three levels and `getDefaultFormState({$ref: pl})` two, as on v7 (verified). Sub-calls (`ArrayField.tsx:156` with raw `schema.items`, `ObjectField.tsx:607`, `OptionalDataControlsField.tsx:65`, `formDataForNewOption`) keep whichever form they pass today. The call root never collapses.
  - the **selected option, in render only**: the option node starts at `[]`, and entering the option's own `$ref` gives `[target]`. v7's `MultiSchemaField` renders the chosen option as a fresh schema. Pinned by `oneOf.test.tsx:2011-2096` and `anyOf.test.tsx:1736-1821`, where an inherited refPath would hide user data behind an Expand button at `root_components_0_fn` (verified). In the **defaults** the option keeps the refPath of the node offering it, as v7's `computeDefaults` keeps its `_recurseList` through an option. A restart there is not bounded by the data: the fold chooses an option with no data, so `node={anyOf:[{properties:{next:{$ref node}}}, {type:'string'}]}` restarted at every level and overflowed the stack (stage 1 review; v7 gives `{}`, and `[[null]]` for the array form). Restarting only where the field has data terminates but grows on every call (`[[null]]`, `[[[[null]]]]`, …), so it was rejected. Inheriting matches v7 on these shapes and changed no corpus baseline. The defaults also apply the rule to the field's plan **with the selected option merged**, since a recursion through an option enters its `$ref` only there: the option collapses where the same recursion written as a property does, expanding once (I2), whatever the data holds below. Checking only the field's plan without the option let the fold follow the data: `c:{anyOf:[{type:'null'}, {$ref node}]}` with data `{c:{c:{c:{}}}}` filled `name` at every data level, where v7 and 6.11.0 stop after two, as they do for `c:{$ref node}` (stage 1 review; corpus `R optional next data 3`, `R optional next oneOf data 6`). The selected option's own `$ref` is also checked against the ref path the option was offered under, as part of the first-entered check (an option is entered the way a seed is; in render the option's ref path is empty, so the check never fires there). A field whose option list sits behind a `$ref` of its own (`c:{$ref X}`, `X={anyOf:[{$ref node}, {type:'null'}]}`, or an object `oneOf`) has a first-entered `$ref`, `X`, which is new at every level, so the check above saw only `X` and the fold filled one level deeper than v7 and 6.11.0, bounded but different (stage 1 review; corpus `R options behind ref`, `R options behind ref data 4`, `R options behind ref data 7`, `R nullable behind ref data 7`).
  - in **render only**, an **array row, additional key or pattern key present in the data**: its seed starts at `[]`, so its own `$ref` gives `[target]`. v7's `stubExistingAdditionalProperties` gives each key a fresh `{$ref}`. Pinned by `ObjectField.test.tsx:767-806` (#4266, verified). Rows restart for the same reason (stage 1 review): a row that kept its refPath collapsed a property re-entering a list or wrapper definition the row came through, `node={v, kids:{$ref list}}`, `list={type:'array', items:{$ref node}}`, and with it every row the data had there (`root_kids_0_kids-button` over `c` and `d`), where v7 and 6.11.0 render all of them under a root `$ref`. A row exists only where the data has it, so the data bounds the restarts.
  - an **expanded field** (I2, below).
- **Array rows do not restart the refPath in the defaults.** Restarting there would break `pl arr allOf minItems` and is not bounded by the schema. In render, rows the data holds restart it (above); that keeps item 7 of 7.1 (the first row's `best` still collapses, since the restarted row enters `node` and `best` re-enters it) and renders the data rows v7 collapsed under a non-`$ref` root (7.1, item 20).

**Rule.** A field is *collapsed* when either check fires:

1. **First-entered ref.** The field's first-entered ref is its containment node's own `$ref`, following pure-`$ref` aliases (every alias target is checked). If the containment node has no `$ref`, it is the first `$ref` the field's plan enters through any edge (`allOf`, `then`/`else`, dependency, option). The check fires if that target is already in the refPath in effect where it is entered.
2. **Count-2.** Any `$ref` edge in the plan enters a target that already occurs **two or more times** in that edge's refPath.

Where it applies:

- **Render:** on object-property children only. This is where v7 places `RJSF_REF_CYCLE_KEY`, and it is the only render edge that is not data-driven (array rows and additional keys are bounded by the data).
- **Defaults:** on every non-root containment edge: properties, items and `minItems` fillers, tuple items, additional and pattern keys. v7's `computeDefaults` stops at any already-followed `$ref` regardless of edge.

**What a collapse cuts.** Only the recursive `$ref` or branch edge is cut. The collapsed field still contributes its containment node's own keywords: `type`, its own `properties` and their defaults, and the sibling keywords beside the `$ref`. Pinned by `getDefaultFormStateTest.ts:1637-1639`: `child: {type:'array', minItems:1, items:{type:'object', allOf:[{$ref:node}]}}` under populate must give `child:[{name:'n', child:[{}]}]`, not `[undefined]` (verified that cutting the whole field fails it).

**Set-equality guard.** A child on any containment edge also collapses if its plan's set equals that of an ancestor in its backstop chain. In render, children that exist in the data through a data-driven edge (array rows, additional/pattern keys in the data) are exempt and restart the guard's chain and their refPath. In render, the selected option of a field **that has data** also restarts the guard's chain: without that, selecting the recursive option of `c:{anyOf:[{type:'null'},{$ref node}]}` collapsed the next level behind an Expand button (`root_c_c-button`), where v7 renders its selector (`root_c_c__anyof_select`) (stage 1 review). An option chosen for a field with no data keeps the chain, which is what stops a recursive option selected by default. The defaults view does not apply the guard at all: its options keep their ref path and its rows never restart, so the count-2 check bounds every chain there, and dropping the guard changed no corpus baseline. This guard is **not** the termination argument: a pigeonhole over subsets of nodes allows chains whose length is the lcm of the ref-cycle periods (see below). It stays as a safety net and never fired on the 65 shapes or the 154 captured cases beyond what the refPath checks already decide (prototype).

**Expansion (I2): one level per click, for every edge kind.** A collapsed field is expanded once, by the defaults fold or by one Expand click. Its seeds' refPaths restart at `[]` (re-entering its own `$ref` gives `[target]`), and its guard chain restarts at it. Descendants collapse again at their next recurrence. A collapse inside that expansion stops the defaults fold: the field gets only what it inherited and the data.

v7 is inconsistent here (verified): one click reveals two levels for recursion through `properties` (`pl`, `$ref:'#'`, two full periods of A<->B) and one level for recursion hosted in `then` or `allOf`. Keeping two levels would need either a non-idempotent `retrieveSchema` (the K4 OOM mechanism) or a special case that would also turn v7's one-level `then`/`allOf` cases into two. A split I2 ("children declared directly by the expanded target do not see it, branch-declared children do") was suggested in review as fitting both, but it is inferred only and was not prototyped, so it is rejected for now. The change ships in stage 1 and rewrites `SchemaField.test.tsx:1302-1313` (7.1, item 1).

**Why it terminates.** (Inferred argument; checked on the shapes below.)

- Any chain of containment fields beyond the data must enter `$ref` targets infinitely often along its derivation, since a schema without `$ref` has finite depth. Targets are canonical locations, so there are finitely many. Within `2·#refs + 1` ref entries some target reaches a third occurrence on the refPath, and the count-2 check fires. The first-entered check usually fires much earlier. So depth per chain is `O(#refs)`, plus one expansion.
- The count-2 check applies on every defaults edge and on render's property edges, the only non-data-driven render edge. Render's other edges exist only where the data has rows or keys, and data has finite depth. Defaults never exempt data-driven edges, so the defaults depth is bounded by the schema alone.
- Restarts happen only at the selected option in render (the refPath at every option; the guard chain only where the option's field has data, so a chain of options chosen without data still meets the guard), at data-present rows and keys in render (bounded by the data) and at expansions (one per user click or one per collapse in the fold). The defaults fold never restarts at an option or a row, and checks the field's plan with its option merged, so a recursion through options is bounded by the schema as one through properties is.
- `O(#refs)` bounds **depth**, not size. On a dense definition graph the number of fields is factorial (section 8).

**Variants rejected:**

- Superset of an identity set, with resets at data rows ("O>=+r", the earlier draft). Defaults grow on every pass on five shapes (`treeMin` grows by two levels per pass until the guard trips), and it hides `extra` on the mixin back-ref.
- Including the own node in the identity ("T"): collapses `$ref:'#'` one level too early, and every definition recursion one level too late when siblings are present.
- `$ref`-targets-only identity: false collapse for a second use beside a `$ref`.
- Set-equality as the termination check: lcm-length chains (above).
- Count-1 on every ref edge: regresses the mixin back-ref.
- Restarting the refPath at array rows in the defaults: breaks `pl arr allOf minItems`. (Render restarts at rows the data holds, 4.4 refPath starts.)
- The selected option inheriting the refPath: hides user data (`oneOf.test.tsx:2011`).

### 4.5 Defaults

Defaults are an attribute grammar over the field tree, not a pure fold:

- **Top-down (inherited):** `parentDefaults` with ancestor/descendant precedence, `required` and `requiredAsRoot`, `includeUndefinedValues` (where `excludeObjectChildren` drops to `false` for children), the `uiSchema` with `ui:definitions`, the `constAsDefaults` override under `skipOneOf`, and the refPath and guard chain.
- **Bottom-up:** `maybeAddDefaultToObject`, the array policies, and `mergeDefaultsWithFormData`.

**Recursion.** The defaults view applies the rule in 4.4 on every non-root containment edge, with no data-driven exemption, and expands each collapse once (I2). A field with a selected option is checked again with the option merged, and the option's own `$ref` against the ref path it was offered under, so the option's `$ref` is subject to the rule as a property's is, wherever the option list is written. If a field collapses again inside that expansion, it gets only what it inherited and its data. Data below the bound is kept untouched by `mergeDefaultsWithFormData`.

**Dependency-qualification fixed point.** An object's plan is rebuilt while new dependencies qualify against `{...accumulatedDefaults, ...data}`:

- There is **no pass cap**. Qualification is monotone (judged against the declaring node, and the accumulated keys only grow) and bounded by the number of dependency keys, so the loop ends. The prototype's 6-pass cap broke idempotence on a nine-key dependency chain (`depChain(9)`: the first call stops at `k5`, the second reaches `k8`; verified).
- Each pass rebuilds the object's **own** plan only. Children are memoized per `(seeds, refPath, depData and the child's other inputs)` and re-folded only when those change between passes. Since the defaults view applies no set-equality guard (4.4), no ancestor chain enters the key: a pass that adds a dependency changes the object's plan set but not what any child is computed from. Stage 1 first kept the guard in the defaults and keyed the memo on the answers each child's chain gave the guard's checks, which was needed to avoid re-folding every child on every pass; with the guard gone that bookkeeping goes too.
- This is required for cost, not only for neatness. Re-folding every child on every pass is exponential in depth even without recursion (verified on the prototype): `deepChain(16)`, sixteen nested non-recursive definitions, takes 196 605 fold calls and 9.7 s against v7's 3 ms for the same output, and `K4` takes 250 905 calls and 1.4 s against v7's 90 ms. Stage 1 first keyed the memo on the guard chain's identity and was exponential with one `dependencies` entry per level (`deepChain deps`: 1.4 s at depth 16 and out of memory at 32; v7 is exponential too, 0.4 s at 16). With the child's inputs alone as the key, `deepChain deps 32` stays within the harness's time and heap budget (verified).

**What holds instead of idempotence.** `getDefaultFormState(getDefaultFormState(x)) == getDefaultFormState(x)` holds unless an `if`, `anyOf` or `oneOf` choice depends on values that defaults supply. `if` and option matching read the raw data, so a default that satisfies a condition switches the branch on the next call. Known shapes, all behaving the same on v7 (verified):

- `T if flip`: `{properties:{a:{default:'x'}}, if:{required:['a']}, then:{properties:{b:{default:'b'}}}}` gives `{a:'x'}`, then `{a:'x', b:'b'}`.
- `T if flip rec`: the same with `then:{properties:{child:{$ref:'#'}}}` grows over three calls, then stays stable.
- `T option flip`: `anyOf:[{properties:{a:{default:'x'}}, not:{required:['a']}}, {properties:{a:{const:'x'}, b:{default:'b'}}, required:['a']}]` gives `{a:'x'}`, then `{a:'x', b:'b'}`.

Data only grows across calls and each call's depth is bounded by the schema, so repeated calls converge (inferred; observed within three calls). Defining `getDefaultFormState` itself as that iteration would change v7 semantics and is not proposed. The harness checks idempotence on every corpus shape and lists these three as known exceptions.

**Reconciliation oracles.** Verified on v7, and kept by the prototype:

- `if b const 'z' / then b default 'y' / else b default 'z'` settles at `{b:'z'}`, which is a then-tree.
- `if a const 'x' / then a default 'y' / else a default 'x'` settles at `{a:'y'}`.

Leaves return their data when it is defined, and the final `mergeDefaultsWithFormData(..., true, false, true)` matches v7. Without the leaf rule the prototype oscillated on both oracles. Stage 3 starts with v7's hash guard (`formState.ts:839, 889, 1022-1029`) for the Form-level loop. These two values must not change unless that change is decided and recorded in the changelog.

**Defaults view policy** (not part of the rule):

- the call root always merges `allOf`;
- a nested field merges `allOf` under `allOf: 'populateDefaults'`, or when its ref-resolved schema has `if` (v7 retrieves the whole schema then, `getDefaultFormState.ts:654-668`; without this, `X Pet prop` loses `hunts` in the prototype);
- `if`/`then` is merged at every level. The existing `emptyObjectFields: 'skipEmptyDefaults'` handling at the same lines is kept as it is (inferred; not prototyped).

**Other rules.**

- **Sub-calls** (new array item `ArrayField.tsx:156`, new key `ObjectField.tsx:607`, `OptionalDataControlsField.tsx:65`, `formDataForNewOption.ts`) start a fresh refPath at their own root, as they do today. A sub-call is not read from an existing subtree, because the subtree under a collapsed node is shallower than a fresh call there.
- **Option choice for defaults** reads the Form state when a selection exists (stage 3). Otherwise it uses the single seeding function (4.6), which scores `data ?? default` as v7 does. The selected option keeps the refPath of the node offering it (4.4).
- **Kept as they are:** `getDefaultFormState`'s signature, its post-processing (`:1068-1093`), and `mergeDefaultsWithFormData`. Fixes for #5515/#5523 (PR #5524) and #5522 land on today's code first, and the fold keeps them.

Every defaults difference from v7 is listed by name in 7.1. The earlier draft also predicted one more level for refs reached only through tuple items, options, `allOf` entries or `then` (probes D8, D9, D10b, D11) and for the outer/inner `allOf` shape (D13, D14b). No prediction adds an entry.

**As landed (stage 3b).** The fold itself is unchanged. The inherited attribute the tree made simpler is the declared default the sanitize judges a value against: a field's own `default`, or else its parent's own `default` object at the field's key, one level, not further up (4.8). That is all the swap rule needed from the defaults, and it replaced the narrowed per-level `getDefaultFormState()` calls the stale-default search made. The fold still picks an option by matching the data (`chooseOption()`) rather than reading the form's selection: the data after a switch is the one `formDataForNewOption()` wrote for the new option, which the matching agrees with, and threading a field path through the fold would key its child memo on the path and lose the sharing 4.5 requires. A `default` declared above a field that holds the options (#5368's second case) was therefore not re-read on a switch; the stage 3 third fix round found that the selection was not what kept it out. The fold already picked the option the switch's data names (`{kind:'obj', note}` matches `Obj`); the default was blocked by the data itself, since the field's defaults that `formDataForNewOption()` writes for a field that held nothing were computed with `excludeObjectChildren`, which writes every property the option gives no default as an explicit `undefined` key, and the fill leaves such a key alone. They are now computed without `undefined` keys (a field that held nothing has no key a user cleared), and the ancestor's default fills the keys they leave: root `default:{w:{p:{kind:'obj', extra:'from-root'}}}`, `w.p` the issue's `oneOf`, None then Obj: 6.11.0 and v7 `{w:{p:{note:'from-option'}}}`, after `{w:{p:{kind:'obj', note:'from-option', extra:'from-root'}}}` (verified, `i9probe/scenarios.mjs` `above5368`). Passing the selection into the fold is therefore not needed for this case and is not done. The residual difference: the form mounts with `{w:{p:{kind:'obj', extra:'from-root'}}}` (6.11.0, v7 and after), because on mount the ancestor's `default` object stands in for the option's own leaf defaults, while the switch writes the option's defaults first and the ancestor's fill the keys left, so `note:'from-option'` is in the data after the round trip and not on mount. The Form-level loop keeps v7's hash guard (`formState.ts`, `deriveFormData()`), and the two reconciliation oracles above are unchanged.

### 4.6 Options as Form state

- **Where it lives.** The selection is Form-level state keyed by `(path, option-list node)`, not by path and index. If a condition swaps the `oneOf` at a path, the selection re-seeds. v7 carries index 1 from A2 over to B2 (verified).
- **How it moves.** Selections follow the array moves Form already announces (`moveOfItems`, `formState.ts:160`) and survive unmount and remount.
- **Seeding.** One function, used only when there is no state for `(path, list)`:
  - a discriminator wins. Two rules exist today: `getOptionMatchingSimpleDiscriminator` matches on `const`/`enum`, while `LayoutMultiSchemaField` and `findSelectedOptionInXxxOf` match on `properties[selector].default ?? const`. Seeding uses the first. `LayoutMultiSchemaField` keeps the second (stage 3 third fix round, rejected with evidence): it holds no selection to seed, its radio shows checked the option whose `default ?? const` (the value `optionsList()` gives it) equals the data's selector value, and `LayoutGridField` renders that option's fields through `findSelectedOptionInXxxOf()`. Moving it to `getClosestMatchingOption(data, options, -1, selector)` made the option it switches from disagree with both where the scoring does not read the `default`: integer selectors (`propertyScore()` compares `type: 'integer'` with `guessType(1)`, `'number'`, and scores 0), with `kind:{type:'integer', default:0|1}` options and data `{kind:1}`, picked option 0 while the radio showed 1; falsy defaults, which are not scored; and a value naming no option, where the grid shows no option and the switch then dropped the closest option's keys (`{name:'c', y:'keep'}`, pick A: 6.11.0 and v7 `{name:'a', x:'X', y:'keep'}`, moved `{name:'a', x:'X'}`; verified, `i9probe/scenarios.mjs` `layoutSwitch`, `i9probe/f.out`). 6.11.0 and v7 agree, so the parity policy keeps it;
  - otherwise `getClosestMatchingOption`, with two fixes: it never returns an option outside the valid set (`getClosestMatchingOption.ts:201-203`), and it never adds a nested *index* as a score (`:75-87`).
  - Seeding is still a prediction when the data matches several options (verified: `{a:'x'}` against `[O1{a}, O2{a,b}]` seeds O1).
- **Memoized matching.** Matching is memoized per `(option-list node, data at path)`. This is required for #4990: the verified `isValid` counts for depths 1-5 are 12, 62, 262, 1062 and 4262.
- **Re-matching.** It happens only when data arrives from outside (a controlled prop push or a reset) or from an edit to a property of the object's own that the options can disagree about (one an option names under `properties` or `required`, or any where an option carries a keyword that reads the object whole, such as `minProperties`, `not` or `additionalProperties`), with the selected option as the tie preference, as 6.11.0 re-matches every data change. Typing inside an option never re-predicts it.
- **Merged plan.** The selected option's entries join the field's plan, so the parent's properties and the option's properties form one property set, and extra keys are stubbed once. This removes the `namesRenderedElsewhere` predictor (`retrieveSchema.ts:1040-1300`).
  - For #5462 this needs an explicit extra-key policy: a key the option *declares* uses the option's schema, and only undeclared keys get the conjunction of parent and option extra-key schemas. Strict conjunction would make `parent additionalProperties:{type:string}` and an option-declared `{type:number}` unsatisfiable (inferred).
- **Option equal to the parent.** An option whose closure adds nothing to the plan (`anyOf:[{$ref self}, ...]`) renders the selector and no extra fields. That ends the self-referencing `anyOf` OOM.
- **Custom `AnyOfField`/`OneOfField`.** These read and write the selection with `useOptionSelection()`, a hook exported from `@rjsf/core` (decided: the accepted API, not a registry member). This is a public-API change for `registry.fields` overrides. The `options` prop stays, derived from the field node.

**As landed (stage 3a).** The selection lives in the `Form` model (`uiState.ts`), keyed by field path and option list, the list named by its options' places in the root (`getValidationTarget()`'s pointers), so a condition that swaps the list starts the choice over and finds the old one again when it swaps back. The array moves `Form` already announces (`AnnouncedMove`) move the selections under the moved keys, and a key an option switch drops takes its selections with it; `reset()` keeps them, and the expansions (4.7), as 6.11.0 and v7 kept both, so the reset data is data from outside. The list is named by its place in the root, the pointer every option's place extends, so a schema that adds an option to the list keeps the selection, as 6.11.0 kept its index. `useOptionSelection(registry, fieldPath, options, formData, discriminator)`, exported from `@rjsf/core`, is the one API and returns `{ selectedOption, selectOption }`: `AnyOfField`/`OneOfField` call it, `SchemaField` calls the internal `useShownOption()` with the same arguments, which adds `keepSelection()`, and a custom `AnyOfField`/`OneOfField` calls it too (the `options` prop stays). `Form` provides its store through `UiStateContext`; outside a `Form` the outermost `SchemaField` creates one and provides it the same way, so the `SchemaField`s, `AnyOfField`/`OneOfField`s and `CyclicSchemaField`s below it share it (`useUiState()`), and only a component with neither above it, such as an `AnyOfField` rendered alone, keeps a store of its own. Its rule:

- No selection for `(path, list)`: the seed, `getClosestMatchingOption(data, options, -1, discriminator)`, which reads the discriminator's `const`/`enum` first. Its two fixes landed in `getClosestMatchingOption()` itself rather than in a second function: a tie goes to the selected option only where it is a candidate, else to the first candidate, so it never returns an option outside the valid set or `-1`, and a nested option list scores what its pick scores, plus one where the data matches it, rather than the pick's index. `LayoutMultiSchemaField` keeps matching by `default ?? const`, its radio's own value (seeding bullet above).

So a parent declining a switch or an edit, which gives back the data rendered before it, keeps the selection, as on 6.11.0, where v7 went back to the option a declined switch's data fits, while a reset or a push that brings that data back after the form rendered the change is re-matched, as on 6.11.0 and v7. Such data is re-matched with the selection as the tie preference, as 6.11.0 re-matched a pushed value, rather than kept while it validates against the option, which hid a pushed value under an option without `additionalProperties: false` that fitted almost any object (stage 3 review). This replaces v7's `proposal` record and the re-match on every data change, so typing never re-predicts.
- Matching is memoized per (validator, `customMergeAllOf`, option list nodes, flags, data object) inside `getClosestMatchingOption()`, weakly on the data object; primitive data is not memoized, since it scores no nested list. #4990's form with data `n` levels deep now validates `25n - 9` times on render (16, 41, 66, 91, 116 for depths 1-5, controlled; 6.11.0: 24, 124, 524, 2124, 8524), verified and pinned by `optionSelection.test.tsx`. - Writing `RJSF_REF_CYCLE_KEY: false` on a schema stops having an effect.

### 4.8 Sanitize, omit and `ui:required` read the tree

- **Sanitize on a schema change** becomes a diff of the previous and next tree by node identity:
  - fields that left the tree are dropped;
  - fields whose plan lost a branch node have their branch-owned default and enum values re-judged.

  This replaces `stalePathsForNewSchema`, the settled-snapshot fields, `isRefillRejected` and the post-loop restore (`formState.ts:1064-1068`, described in its own comment as an untested net). The termination policy in 4.5 still applies.
- **Omit** (Form's own use) becomes "keep data that has a field in the tree". Two policies must be decided explicitly so that this is not a silent change (both inferred): pruning of all-empty optional objects (`omitExtraData.ts:102-128`), and `anyOf` over empty data applying every branch (`:295-313`).
- **`getUiRequiredErrorSchema`** walks the tree, so it sees the selected option and the expanded cycles.
- **Parent-owned forms** still get no defaults and no sanitize (`formState.ts:1285-1376`). Their tree is derived from the parent's data and never rewrites it.
- **The utils functions** `sanitizeDataForNewSchema`, `omitExtraData` and `getUiRequiredErrorSchema` stay exported for standalone callers. `omitExtraData` and `getUiRequiredErrorSchema` are rewritten internally in stage 1, because `resolveAllReferences` is deleted (section 10).

**As landed (stage 3b).** `packages/core/src/components/sanitizeFieldTree.ts` diffs two trees, not a stored `Field` object: each side is walked lazily, field by field, as `SchemaField`, `MultiSchemaField` and `CyclicSchemaField` render it (`layersOf()`: the field's view, then the shown option's at the same path, then that option's own, and nothing below a collapsed cycle that is not expanded). Both sides show the option the new side shows from the same list (the new data's selection or match), so an option switch, by the selector or by a re-match, is no change of constraints: `formDataForNewOption()` owns the data a switch proposes, and a re-match drops no value, as on 6.11.0 and v7. A field is paired with its previous self by path, through the announced `KeyMove` for the change's own array or object (an inserted item has no previous self), and a subtree whose raw schema, value and inherited default are all unchanged is not walked.
- **Identity.** "Plan lost a branch node" is decided by the field's constraints rather than its node set: its `type` (a guessed type counts as none), `const`, `enum` or constant options, `maxItems`, and its declared default (its own `default`, or its parent's own `default` object at its key). A plan change that leaves all of these equal re-judges nothing, so comparing them is the same answer without exposing the plan's node set from `@rjsf/utils`.
- **Re-judging.** A value deep-equal to the old declared default takes the new one, a `structuredClone()`, written in place; there is no key-absent window, so #5480's four containment mechanisms and its residuals do not arise. Otherwise a value of another type is dropped, a value the new `const` rejects becomes it where it held the old one and is dropped otherwise, and a value outside the new `enum` takes the new default where it is one, the only value where there is one, or is dropped; an array item is dropped (filtered) rather than replaced, and an array is cut to a new `maxItems`. A field that left the tree (a key the old side declared and the new does not) is deleted. The value at the edited path and every value holding it are the user's and are not judged; what they hold is.
- **Loop.** Fill, diff against the tree before, and while that changes the data, fill again and diff against the tree of the data the round before judged, so a value a round wrote is judged against the schema it was written for. v7's hash guard ends it.
- **When it runs.** Every non-root edit of a form that is neither `disabled` nor `readonly`, an array or object write included (6.11.0 and v7 skipped those), and, for a self-owned form, every derivation `deriveState()` re-runs for a schema, `ui:emptyValue` or `defaultFormStateBehavior` change, the previous tree then built with the previous schema utilities. A parent-owned form's pushed value is never sanitized, and a later edit judges only what it changes; a reset is not sanitized.
- **Omit policies.** Form's omit is `omitExtraData()` given the form's `FormFieldState`, so a field keeps the data of the option it shows. Both policies keep 6.11.0's answer: an optional object whose filtered content is all empty is pruned, and `anyOf` over empty data applies every branch (verified, 6.11.0's `omitExtraData.js` holds the same two rules).
- **`ui:required`.** `getUiRequiredErrorSchema()` takes the same `FormFieldState`: the option shown at each path and whether the cycle there is expanded.
- **Deleted.** `stalePathsForNewSchema.ts`; the settled snapshot (`formDataSchema`, `settledFormData`, `settledFormDataForPairing`, `settledRetrievedSchema`, `pendingPairingView`/`Data`, `proposedFormData`/`Root`) with `settledFormDataState()`, `moveSettledArrayAtPath()` and their bookkeeping in `formModel.ts`; `isRefillRejected()`, `putBackAt()`, both restores and the refill counting; `getPropertySchemaAt()`, `resolveSchemaAt()` and `isWholeValueSelectAt()`; `hasNestedConditionalSchema` (state) and its use; and `sanitizeDataForNewSchema()`'s `oldData`, `resolvedOldSchema` and `oldDataForPairing` with `constraintMayHaveChanged()` and the pairing chain, which only `Form` passed.

| Live validation (`formState.ts:375`, `retrievedSchema` copy) | unchanged: the retrieved root copy | Decided for stage 2: the live-validation contract is kept, so non-precompiled validators still drop root `if`/`oneOf`/dependency errors until submit |
| Submit / `validateForm` | the root (unchanged) | |

Required alongside:

- **Cache keys.** Stage 2 clears rather than re-keys: AJV removes the subschemas `isValid()` added when `handleSchemaUpdate` replaces the root registered under the same id, and ata rebuilds every validator when the root changes. Without this, a pointer wrapper returns stale results after a schema change (verified P7: `'s'` validated true against `X: number`; regression test in each validator's `validator.test.ts`). cfworker already cleared its cache on a root change.
- **Root id.** AJV, ata and cfworker register the root under its own `$id` when it has one, `ROOT_SCHEMA_PREFIX` otherwise, and prefix a local `$ref` with that id (`withIdRefPrefix(schema, rootId)`). AJV and ata used `ROOT_SCHEMA_PREFIX`, under which a root with an `$id` is not registered: every pointer into such a root failed (verified before the change: `isValid({$ref:'#/definitions/X'}, 's', {$id:..., definitions})` was `false` in AJV and ata, `true` in cfworker). cfworker registered such a root under `ROOT_SCHEMA_PREFIX` in place of its `$id`, which holds for a local `$ref` but not for the absolute ones `makeAllReferencesAbsolute()` writes into a 2020-12 root with an `$id`: with `$id: 'https://example.com/root.json'`, `$defs: { A, B, isB }`, `properties: { k, v: { oneOf: [{ $ref: '#/$defs/A' }, { $ref: '#/$defs/B' }] } }`, `if: { $ref: '#/$defs/isB' }` and data `{ k: 'b', v: { k: 'b' } }`, stage 2 before the review picked option 0 and logged `Unresolved $ref "https://example.com/root.json#/$defs/A"` where v7, handed the option inline, picked option 1, and the condition took `else` on 6.11.0, v7 and stage 2 alike. Registered under its `$id`, cfworker picks option 1 and takes `then`: defaults `{ k: 'b', v: { k: 'b', y: 'Y' }, e: 'ELSE' }` on 6.11.0 and v7, `{ k: 'b', v: { k: 'b', y: 'Y' }, t: 'THEN' }` after (verified; the shared `pointerValidationTests.ts` runs it against each live validator, since a precompiled validator rejects the absolute-ref root as one it was not compiled from, on v7 too). An `$id` ending in an empty fragment (`http://e.com/r.json#`, the form of the draft-06/07 meta-schemas' own `$id`s) names the same document, so `withIdRefPrefix()` drops that `#` from the prefix, and AJV precompile drops it from the export names (`<rootId>#/ptr`); left in, every pointer read `...json##/if`, Ajv threw `MissingRefError` and every condition took `else`, where 6.11.0 and v7 took `then` (verified, AJV and ata, live and precompiled). AJV registers such a root under its `$id` without the `#` as well, which is how Ajv keys it: registered under the `#`-ending key, `replaceRootSchema()` removed nothing when the root was edited under the same `$id`, re-adding it threw `schema with key or id "http://example.com/root.json" already exists`, and every condition took `else` (`{ k: 'x', e: 'e' }` where the edited root gives `{ k: 'x', t: 't' }`); 6.11.0 and v7 behaved the same (verified, stage 2 review; regression test in `validator.test.ts`).
- **Pointer encoding.** A pointer's tokens are encoded as `encodeURI()` encodes them, leaving the characters a fragment may hold (`$ : @ + , ;` ...) as they are, and a `#` as `%23`. With `encodeURIComponent`, `$defs` became `%24defs`, which cfworker never decodes, so every `if` and option under `$defs`, or under a property named with one of those characters, was unresolved (verified). A `#` left as it is resolved everywhere except where it ended the `$ref`: Ajv drops a trailing `#` as an empty fragment, so a dependency named `Phone #` lost its `oneOf` under AJV and threw under AJV precompiled (verified; v7 and 6.11.0 handed the subschema itself). cfworker keys its lookup by `encodeURI()`'s spelling (its `encodePointer()`), which keeps `#`, so the cfworker validator spells a `%23` in a `$ref` fragment back as `#` before handing the schema over. Regression tests in each validator and the shared precompiled suite: `$defs` and `a$b`, `a:b`, `a+b`, `a@b`, `a#b`, `a b`, `a%b`, `a/b`, `a~b`, a name ending in `#`, and a dependency `Phone #`.
- **Boolean subschemas.** A boolean subschema is handed over as what it stands for, `{}` or `{ not: {} }`, never by pointer: it holds no `$ref` for a pointer to keep in reach, and ata live reads a `$ref` that names a boolean as `true`, so `if: false` took `then`, and a dependency `oneOf` option with `properties: { a: false }` matched, where 6.11.0, v7 and the other validators took `else` and matched the other option (verified). `SchemaField` retrieves a boolean option as a fresh `{}` too; the compile list includes `{}` and `{ not: {} }` wherever the root holds a boolean option, or a precompiled form throws while rendering it (verified: v7 rendered it, stage 2 before this threw `No precompiled validator function was found ... "f62"`).
- **cfworker.** Its dereferencer reads draft-07 `dependencies` as one subschema, so an entry named like a keyword it ignores (`type`, `required`, `enum`) is not indexed and a pointer into it was unresolved (verified with a dependency named `type`). `createCfworkerInstance()` indexes those entries after registering the root. This reads two engine internals, the private `lookup` and the `__absolute_uri__` stamp, which the "no workarounds" rule would reject if a public contract existed; none does (the engine exports `dereference()` but no way to reach a validator's lookup), and the alternative, handing cfworker an inline copy for a pointer into such an entry, would be a second validation path for one validator. The cost is an engine upgrade renaming either field: `validator.test.ts` asserts both exist, besides the regression test that stops resolving. The public route was tried and rejected (stage 2 review): `Validator.addSchema(entry, '<root>#/dependencies/type')` does index the entry under that fragment, but `dereference()` then registers it again under the engine's default base URI (`https://github.com/cfworker`), so a second such entry throws `Duplicate schema URI`, and the `$ref`s inside the entry resolve against that base rather than the root. Both the private `lookup` and the `%23` spelling (below) are engine limits to report upstream (a public way to index a subschema under its pointer, and `encodePointer()` escaping `#`); `refTo()` cannot pick one spelling that both engines accept, since Ajv drops a `#` ending a `$ref` and cfworker keys its lookup with a literal `#`.
- **AJV precompile.** The compile list is the root plus the graph-named pointers and derived schemas, a discriminator property listed for every option under every `discriminator.propertyName` the root declares (see the table). A pointer is exported with `standaloneCode(ajv, { [key]: rootId + '#/ptr' })` as the function Ajv compiles for that subschema of the root; every other schema is compiled under its key with its local refs prefixed by the root id. This removes the compile failure "can't resolve reference #/definitions/node" for a recursive node used as an option and the runtime miss for retrieved options with stubbed keys (#5454), verified against 6.11.0.
- **ata precompile (decided: carry what a document reaches).** `bundleStandalone` resolves a `$ref` only to an entry of `definitions`/`$defs` in the document it compiles, returns `null` otherwise, compiles no `$ref` beside keywords that assert something, and compiles no schema holding no assertion it knows (`{}`, `{ title: 'By email' }`, a document of `definitions` alone), so every compiled schema without a `not` or a `$ref` gets `not: { not: {} }`, which always holds. Each listed schema is compiled as a document carrying what it reaches of the root: every subschema of the root it names through a `$ref`, a definition or not (a definition, a property, an option, the root itself as `#`, at any depth), as an entry of its own (`rjsf:<n>`) in a single container, `$defs` when the root has one and `definitions` otherwise, the `$ref` renamed to it, and the document's own `definitions` and `$defs` dropped, since only renamed `$ref`s could name them; each carried entry is rewritten the same way, so a recursion resolves through the renamed entry exactly. One container, because ata compiles nothing for a document holding both (`{ $defs, definitions }`, verified); generated names, because ata does not percent-decode a `$ref` (`#/definitions/c%20d` names nothing in it, verified). Stage 2 before its review carried a definition under its own name in its own container, which left the root, and every document reaching a definition, uncompiled for a root holding both containers or a definition named with a character a `$ref` percent-encodes (`'c d'`, `'c%d'`): the form threw `was not compiled to a standalone validator` on render where 6.11.0 and v7 rendered `[Option 2] root_v_k root_v_y` (verified; the shared `pointerValidationTests.ts`). A `$ref` the root names nothing at is read against the document itself, where the copy of an option with an `$id` of its own, listed without that `$id`, holds the definitions its `$ref`s name. A `$ref` beside other keywords becomes an `allOf` entry beside them, as 2019-09, 2020-12 and Ajv read it. Stage 2 first inlined a copy of each non-definition subschema and hoisted the root's whole `definitions`/`$defs` beside every document (stage 2 review): a `$ref` met again inside its own copy was left as it was, so an option `{ $ref: '#' }` named the document itself and the form threw on render where v7 rendered, a `$ref: '#'` below a copy resolved to the copy rather than the root (option `{ properties: { me: { $ref: '#' } } }` with data `{ me: { name: 5 } }`: live ata `false`, precompiled `true`), and one uncompilable definition such as 2020-12 `Ext: { $ref: '#/$defs/Base', properties }` left every document uncompiled, so any option threw on render. After: the tree, the recursive property `tree: { ..., kids: { items: { $ref: '#/properties/tree' } } }` and `Ext` all compile and validate as live ata does; 6.11.0 validated the tree, `v: { $ref: '#/properties/base' }`, `Ext` and a draft-07 `$ref` beside `properties` too (as a conjunction), and overflowed the stack on the recursive property; v7 threw `was not compiled` or `Cannot read properties of undefined` on all of them (verified, 6.11.0 from npm, v7 at `c8856747e`). A `$ref` that names nothing in the root, or one into another document, is left as it is and throws `was not compiled to a standalone validator` when first used; no build-time error was added. Unrelated ata limitation found on the way: `bundleStandalone` with `verbose` emits a reference to an undefined `_cpLen` helper for `minLength` in a non-root position (the shared #5454 test uses `pattern` instead).
- **`schemaParser`** stays as a deprecated export that returns `getValidationSchemas()`, the compile list. The `SchemaMap` keys and contents change, so precompiled code must be regenerated (section 7.2). The list does not depend on `customMergeAllOf`, so `schemaParser()` takes the root alone, and the compile functions take `CustomValidatorOptionsType`, as in 6.11.0. `SchemaParserOptions` and `CompileValidatorOptionsType`, which v7 added to carry a `customMergeAllOf` into the parse, are removed: they were never released. A schema a merge makes (an option a `customMergeAllOf` rewrites, the product json-schema-merge makes of two `patternProperties`' `oneOf`s) has no node in the root and is not listed, so a precompiled validator throws on it; 6.11.0 throws on the same shapes (verified), and v7 before stage 2 covered them only by enumerating merges, which stage 2 deletes.
- **Ajv dialects.** A pointer is compiled as part of the root, so under `Ajv2020` a condition inside a draft-07 tuple `items` fails as validating that root does; 6.11.0 gives the same defaults (verified), v7 stage 1 filled the `then`.
- **`rawValidation`** has no `rootSchema` parameter, and the precompiled `rawValidation` ignores its schema argument. The "validate by pointer and filter errors" scoring alternative therefore has no supported entry point, and this RFC does not use it.
- **Third-party `ValidatorType`s** that ignore `rootSchema` would break on `{ $ref }` schemas. The `isValid()` JSDoc says `schema` is often a `$ref` local to `rootSchema` that has to be resolved against it, and the upgrade guide's `ValidatorType` note links the pointer section, but this is still a compatibility risk and is listed in the changelog.

Why lazy rather than eager: an eager walk inherits v7's path-sensitive blow-up (2.1), and keeping per-call unrolling for copies is the mechanism behind v7's `K4` render OOM (2.2). A lazy call costs `O(|plan(F)| + Σ |plan(child)|)` plus an `O(1)` guard lookup if the chain keeps a set-hash map, which is polynomial in schema size (inferred). It bounds the cost per call, not the size of the rendered form (section 8).

The lookahead builds each property child's plan from the child's own data, which the parent already holds, so it covers the first-entered ref through `allOf`/`then`/dependencies and the guard. The exception is children whose seeds come from a user-selected option: stage 1 has no Form state for the selection (it lives in `MultiSchemaField`'s `useState`), so the decision happens when `SchemaField.tsx:552` retrieves the option copy, using the option's stamp. The self-referencing `anyOf` fix in stage 1 depends on that stamp (inferred).

### 4.11 Named fields and options per target (stage 4, as landed)

**One named-field slot (#5391).** A field is named by one slot, read in order: the field's own `ui:field` (`ui:field` or `ui:options.field`), else `ui:globalOptions.field`, else a field registered under the schema's `$id` (`resolveNamedField()` in `SchemaField.tsx`). Each is a component or the name of a registered one, checked with `isComponentType()`. An empty own `ui:field` still shadows the global one, and an own one naming nothing falls through, as before; a `$id` naming nothing is not warned about, since it is an identifier first. The order is 6.11.0's: there, as on v7, a `ui:field` of either spelling beat the `$id`. The policy decision #5391 asked for: the three are spellings of one request, so a named field renders the same way whichever spelling named it, beside the `anyOf`/`oneOf` option selector, and in place of the options under `ui:fieldReplacesAnyOrOneOf`. 6.11.0 and v7 dropped a `$id` field for a non-select union and rendered the options alone; that answer, a field registered for the schema that never renders, was inconsistent with the `ui:field` spelling and silent, so it is not kept. A named `FallbackField` keeps its exception (it never renders beside the options it would replace). `getFieldComponent()` loses its own `$id` lookup.

**Once per data path (#5377).** A `SchemaField` that resolved a named field, rendered or declined, provides its `fieldPath` through a core-private `NamedFieldContext`. A `SchemaField` below it at the same path renders as though no field were named: its resolved `uiSchema` has the field shadowed in every spelling (`withoutNamedField()`, the shadow `optionsReplaceNamedField` applied to the options before), and its `$id` is not looked up. `Form` provides `undefined` around its root, so a `Form` rendered inside a custom field starts with no path named. The selected option renders at the same path inside the context, so it renders the default field for its schema: a `ui:field` beside a union no longer renders a second time inside the option, which is the `ui:field` half of #5358, a `ui:globalOptions.field` no longer reaches an option that carries a per-option `uiSchema`, and an option's own `ui:field` (from `uiSchema.anyOf`/`oneOf`) or `$id` is not applied below a named field either, where 6.11.0 and v7 rendered it (an option `$id` there rendered the parent's `ui:field` again, which it inherited). That last one is the rule's own answer, kept rather than special-cased: applying an option's own name while shadowing the inherited one would need the global field shadowed in each per-option `uiSchema` as well, a second mechanism for what the context does once. The `XxxOfField` is handed the field's `uiSchema` unshadowed; the shadow is computed only for the option-label check that decides whether the field's description is left to the option. The rule is keyed on the path alone, not on the component: a component check would let two wrappers naming each other at one path alternate without end, and a component written inline is a new identity on every render. Its consequence is the documented one: a custom field that renders `registry.fields.SchemaField` for its own data gets the default field there, whatever `ui:field` the `uiSchema` it passes names; to render another custom field for the same data it renders that component directly. A path below (a property, an item) applies its own named field, so the guard never hides a nested directive. `FallbackField`'s `field` shadow for its value field is deleted: a named `FallbackField` provides its path, so the value field, rendered at that path, is shadowed by the context, and one reached by the type has no field named that resolves (a `ui:field` naming a field would have rendered that field instead). It keeps its type selector's shadow, since the selector is a field of its own path with a `uiSchema` it builds, and its `help` shadow.

**Options per target (#5527 items 1 and 2).** `getUiOptions()` takes `globalOptions` beneath the field's own options without their `required`, and skips the root's `ui:definitions` and `ui:globalOptions` keys, so no widget's `options` carry a form-wide `required`, `definitions` or `globalOptions`. `ui:required` stays a field's own option, as `SchemaField`, `LayoutGridField` and `getUiRequiredErrorSchema()` already read it. Rejected: separate field, widget and template option bags. Every field would hand its widget a different `options` object, an API change for custom widgets with no defect it fixes beyond these two, and the per-target question (which component draws which part) is #5490's declaration. Item 3, the selector's missing `required` prop, is a one-line fix independent of this RFC and is not part of stage 4. `LayoutGridField` still copies `ui:globalOptions` into each field's `uiSchema`, since a nested grid reads it there; it no longer reaches a widget.

**Resolution per field, and where #5491 joins it.** `SchemaFieldRender` resolves once per render, in this order: the `uiSchema` (`resolveUiSchema()`, shadowed below a named field), the retrieved schema and its select info, the named field, the component and its option flags (`getFieldComponent()`), and from them the label, description, help and `displayLabel`. The levels that render the same data path below it (the selected option, the fallback UI's value field, a re-entered `SchemaField`) still resolve their own, and `getDisplayLabel()` still runs two to four times per field: what each such level shows is the presentation plan's question, not this stage's. #5491's `resolveFieldPresentation()` is designed to be that step: it takes the decisions above as inputs (the resolved component's key for its declaration, the widget, the label text, `showLabel`, description, help, errors, `required`) and the plan of the level above rendering the same id as `inherited`. The integration point is `NamedFieldContext`: it is already the per-path context that tells a level what was decided above it at the same data path, and #5490 calls for exactly such a core-private context for `inherited`. Its value grows from the path to `{ fieldPath, presentation }` when the plan lands, a level reading `inherited` only where the path matches, and the plan is computed in `SchemaFieldRender` right after `getFieldComponent()`. The once-per-path rule then also answers #5490's "custom fields draw their own label" for a named field at the same path. Nothing here copies #5491's code.

## 7. Behaviour changes and compatibility

Each item below goes into `CHANGELOG-v7.md`, the v7 upgrade guide and the harness allowlist. "Before" is verified v7 output unless marked; "after" is prototype output unless marked inferred. The harness compares with the v7 branch (`c8856747e`), which is unreleased; the changelog and the upgrade guide compare with 6.11.0, the last release (verified against the npm packages). Where 6.11.0 overflowed the stack or ran out of memory, the guide says so as the "before" (items 4, 8, 19, 13 and the lcm family); where 6.11.0 equals stage 1, as for item 14, there is no entry.

**Parity policy.** 6.11.0 is the reference users see. Stage 1 matches it where v7 matches it. Where v7 already differs from 6.11.0, crashes, runs out of memory, or is inconsistent with itself (root against property, a first call against a second, an option written in place against one written as a `$ref`), the rule's own consistent answer wins and the difference is listed here, rather than reproduced with special-case code. A special case whose only purpose is to reproduce such a quirk stays only when its user-visible importance is argued here; none is at present (the `allOf` reading of a chained `$ref` under 2019-09/2020-12 in 4.2 is no quirk: it is the dialect's meaning, 6.11.0 and v7 both give it, and the OpenAPI 3.1 inheritance pattern depends on it). Applying this removed, from stage 1's first cut, the narrow "target `default` wins" reading of a `$ref` with its per-field flag (item 12), the composition walk for `ui:definitions` (item 14), the set-equality guard and its answer-keyed memo in the defaults view (4.4, 4.5), the `refsFollowed` bookkeeping in option scoring (7.2), and a root that `getDefaultFormState()` took to be the schema itself only while there was no form data (item 25). The check of an option's own `$ref` against the ref path it was offered under stays, moved into the rule's first-entered check: without it a recursion through an option list behind a `$ref` stopped one level deeper than the same recursion with the list written in place.

- **Stage 2:** a dependency's `oneOf` option is applied by the `properties[<key>]` its scope declares (its own, its `$ref` target's, its `allOf` entries', its `then`/`else`'s and its `dependencies` schemas'), the scope option scoring reads, where 6.11.0 and v7 read only its own `properties` or its `$ref` target's. With `properties: { k: { type: 'string', enum: ['a', 'b'] } }`, `dependencies: { k: { oneOf: [{ allOf: [{ properties: { k: { enum: ['a'] } } }], properties: { ka: { type: 'string', default: 'A' } } }, { allOf: [{ properties: { k: { enum: ['b'] } } }], properties: { kb: { type: 'string', default: 'B' } } }] } }` and data `{ k: 'b' }`: 6.11.0 and v7 give the defaults `{ k: 'b' }`, retrieve `k` alone and warn `ignoring oneOf in dependencies`; after, `{ k: 'b', kb: 'B' }`, and the form renders `root_k root_kb` (verified; `getDefaultFormStateTest.ts`). The same reading can make two options apply where one did, and the exactly-one rule then applies neither: with `oneOf: [{ allOf: [{ properties: { k: { enum: ['a', 'b'] } } }], properties: { ka: { type: 'string', default: 'A' } } }, { properties: { k: { enum: ['b'] }, kb: { type: 'string', default: 'B' } } }]` and data `{ k: 'b' }`, 6.11.0 and v7 skipped the first option and applied the second, defaults `{ k: 'b', kb: 'B' }` and render `root_k root_kb`; after, both match, the defaults are `{ k: 'b' }`, the form renders `root_k` alone and warns `ignoring oneOf in dependencies` (verified, AJV; the stage 2 review saw the same render under all five validators; the shared `pointerValidationTests.ts`). Kept rather than special-cased back: one scope reader serves scoring, discriminators and dependencies.
- **Stage 2, precompiled:** a discriminator in an `allOf` entry beside the `oneOf` (`s: { allOf: [{ discriminator }], oneOf }`), or beside an `allOf` holding it (`s: { discriminator, allOf: [{ oneOf }] }`), with data lacking the discriminator (`{ b: 'q' }`): 6.11.0 threw `No precompiled validator function was found` scoring the options, v7 and after give option 1; a discriminator beside a `$ref` to the options gives option 1 on all three (verified, shared precompiled suite).
- Live validation against the root was not adopted (decision for stage 2): the contract in the v7 upgrade guide stands.
- `schemaParser` output changes in format and keys. Precompiled code generated by `compileSchemaValidatorsCode` must be regenerated, and old output throws "No precompiled validator function was found".
- validator-ata precompile compiles each listed schema as a document carrying the root's definitions it reaches and every other subschema it reaches through a `$ref` as an entry of its own, a `$ref` beside other keywords read as an `allOf` entry (4.9). A property that refers back to itself (`tree: { ..., kids: { type: 'array', items: { $ref: '#/properties/tree' } } }`) reports `.tree.kids.0.kids.0.name` for a `name` of `5` two levels down, where 6.11.0 overflowed the stack (verified). A `$ref` that names nothing in the root, or one into another document, has no function.
- **Stage 2:** `AJV8Validator` registers a root whose `$id` ends in an empty fragment under that `$id` without the `#`, so a root edited under the same `$id` replaces the one before it: with `C = { $id: 'http://example.com/root.json#', properties: { k: { type: 'string', default: 'x' } }, if: { properties: { k: { const: 'x' } } }, then: { properties: { t: { default: 't' } } }, else: { properties: { e: { default: 'e' } } } }` and then `{ ...C, title: 'edited' }` on one `customizeValidator()` instance, the second gave `{ k: 'x', e: 'e' }` on 6.11.0 and v7 and gives `{ k: 'x', t: 't' }` (verified).
- **Stage 2:** `CFWorkerValidator` registers a root with an `$id` under that `$id`, so the absolute `$ref`s `createSchemaUtils()` writes into a 2020-12 root resolve, a condition holding a `$ref` included: with `{ $schema: 2020-12, $id: 'https://example.com/root.json', $defs: { isB: { properties: { k: { const: 'b' } }, required: ['k'] }, ... }, properties: { k: { type: 'string' }, ... }, if: { $ref: '#/$defs/isB' }, then: { properties: { t: { type: 'string', default: 'THEN' } } }, else: { properties: { e: { type: 'string', default: 'ELSE' } } } }` and data `{ k: 'b' }`, the defaults held `e: 'ELSE'` on 6.11.0 and v7 and hold `t: 'THEN'` (verified, 4.9 Root id). Options read from such a root match the same way: with `oneOf: [{ $ref: '#/$defs/isA' }, { $ref: '#/$defs/isB' }]`, `isA`/`isB` requiring `k` `'a'`/`'b'`, `getFirstMatchingOption({ k: 'b' }, schemaUtils.getRootSchema().oneOf)` gives `0` on 6.11.0 and v7 and `1` after (`getClosestMatchingOption()` gave `1` already; verified, `i9probe/opt.mjs`).

Before: under `Ajv2020`, `isValid({properties:{animal:{const:'Cat'}}}, {animal:'Cat'}, {type:'array', items:[{type:'string'}]})` gave `false`, and so did the next call with any other root; with the default draft-07 validator, `isValid({$ref:'#/$defs/n'}, {}, {$schema:2020-12, $defs:{n:{type:'object'}}, type:'object'})` gave `false`, then `true` on every later call. After: `true` on every call, and the next root registers (verified; `validator.test.ts`). So an `if: {$ref}` under a 2019-09 or 2020-12 root picks its branch on the first call too: `{$schema:2020-12, $defs:{I:{properties:{k:{const:'x'}}}}, properties:{k:{default:'x'}}, if:{$ref:'#/$defs/I'}, then:{properties:{t:{default:'t'}}}, else:{properties:{e:{default:'e'}}}}` with data `{k:'x'}` gave the defaults `{k:'x', e:'e'}` on a fresh validator (6.11.0 and v7) and gives `{k:'x', t:'t'}` (verified); the form rendered `root_k root_t` on all three. `Ajv2019` or `Ajv2020` through `customizeValidator({ AjvClass })` remains the way to validate such a root under its own dialect. This is what lets `getDefaultFormState()` drop its empty root (7.1, item 25). Corpus: `R 2020 if ref default validator`, `R 2020 chained ref option default validator`.
- **Stage 1:** option scoring reads a property written as a `$ref` as the definition it names, with the keywords beside it, as far as the form data reaches, whether or not the `$ref` is recursive. 6.11.0 inlined a non-recursive `$ref` before scoring, and retrieved a recursive one, without the point an object value gets, overflowing the stack once the data ran out; the v7 branch stopped at the data but kept the two readings. With `Node={type:'object', properties:{next:{$ref Node}}}`, options `[{properties:{a:{$ref Node}}}, {properties:{a:{type:'object', properties:{next:{type:'object'}, z:{type:'string'}}}}}]` and data `{a:{next:{next:{}}}}`: 6.11.0 overflows, the v7 branch picks option 1, after picks option 0 (verified). `calculateIndexScore()` called directly reads a `$ref` property the same way: `{properties:{a:{$ref O}}}` with `O={type:'object', properties:{x:{type:'string'}}}` and data `{a:{x:'y'}}` scores 1 on 6.11.0 and 2 after, the score the same option gets inside `getClosestMatchingOption()` on both (verified).

### 7.3 Markers

- `ADDITIONAL_PROPERTY_FLAG` and `GUESSED_TYPE_FLAG` are unchanged on per-field merged schemas. They are read by `WrapIfAdditionalTemplate` in core and eight themes, `SchemaField.tsx:313,696`, `ObjectField.tsx:118`, `FallbackField`, and the docs example at `custom-templates.md:1262`.
- `RJSF_REF_KEY` is still emitted (`resolveUiSchema.ts:48`, `schemaParser.ts:109` and `FallbackField.tsx:169` depend on it). After an `allOf` merge it names the field's own `$ref`, as 6.11.0 does and the v7 branch did not (7.1, item 14).
- `RJSF_REF_CYCLE_KEY` is emitted at the positions chosen by 4.4 (`SchemaField.tsx:458` and `getUiRequiredErrorSchema.ts:135` read it). Writing `false` expanded one level in stages 1-2; from stage 3a `retrieveSchema()` reads such a copy as a plain copy of the field, and `expandRefCycle()` is the expansion (7.1 item 33). The constant stays exported.
- `RJSF_REF_SIBLING_BRANCHES_KEY` and `PATTERN_MERGE_LEFT_UNDONE` are no longer emitted from stage 1. Stage 2 removes the first: v7 added it and never released it, so no released code reads it. The released public symbols (`utils/src/index.ts:170`) wait for v8 to be removed.
- A new private symbol (4.1) is stamped on every subschema `retrieveSchema` returns in stages 1-2. It is not exported, and code that strips symbols from a schema turns it back into a call root.
- **The stamp stays after stage 3.** Rendering still retrieves one level at a time: `SchemaField` retrieves the subschema its parent's view handed out (`SchemaField.tsx`, `retrievedSchema`), `ObjectField` and `ArrayField` hand their children the subschemas of that view, `MultiSchemaField` renders the option `SchemaField` retrieved through `getRenderedOptionSchema()`, a copy that `retrieveSchema()` plans from its keywords with the copied field's provenance (`fieldOf()`, `adoptCopy()`), and `CyclicSchemaField` expands through `expandRefCycle()`, which reads it. The sanitize diff, the `ui:required` walk and `getFromSchema()`/`isSelect()` do the same. What each of those retrieves is a handed-out copy, and the stamp is what carries the field's seeds, its ref path and the guard chain the recursion rule (4.4) checks the field against, and the offering field's plan for an option (`addsNothing()`). It goes only when a field is rendered from a `Field` node the form builds once for the whole tree (4.3), which stage 3 did not build: the selection, the expansion and the sanitize read the form's state per path instead.

## 8. Risks and open questions

- **Dense definition graphs (`K_n`).** The rule's rendered tree is `O(e·(n-1)!)` fields on a complete definition graph, even without conditionals: `K4` 16 inputs / 33 buttons, `K5` 65 / 196, `K6` 326 / 1305, `K7` 1957 / 9786 (prototype; stage 1 renders the same inputs and Expand buttons on `K3`-`K5`, verified). The **defaults are much larger than the render**: the fold fills data at every position the rule reaches, including the ones the render collapses behind Expand buttons, so `K3` has 35 default leaves against 5 inputs, `K4` 544 against 16 and `K5` 12 805 against 65 (verified on stage 1; 12 740 of `K5`'s values have no rendered field, e.g. `root_p1_p0_v`). That is v7's order of size too (v7's `K4` defaults hold 3 304 `"v"` occurrences, stage 1's 3 274), so it is not a regression, but the defaults, not the render, are the binding cost: `K5` defaults take about 0.2 s, and `K6` defaults take 7.7-10 s per call and 6.4 million characters of JSON (verified), so a `K6` form cannot mount within any budget. v7 itself runs out of memory rendering `K4` and takes 10.7 s for `getDefaultFormState` on `K5`. A lazy `retrieveSchema` bounds the cost per call, not the size of the form, so `K10` and above stay unrenderable, as they are on v7 today, and FHIR- or OpenAPI-style cross-referencing definitions are at risk. Open: is a structural bound wanted, for example collapsing a property child whose target is already expanded as a sibling-subtree root on the path? It would be a further allowlisted change, and the place to bound it is the defaults, for example filling defaults only at positions the render reaches. The harness carries `K3`-`K5` with time and heap budgets, and `K6`/`K7` as pending surfaces past the budget (their `retrieveSchema` output is recorded; their defaults and render are not).
- **`$data` in conditions.** Unsupported and documented as such. Proper support would need validation by (root data, instance pointer), which `isValid` cannot express.
- **`$ref` siblings: override or conjunction?** Override is today's rendering, so this RFC keeps it. Conjunction is JSON Schema's meaning and what root validation already does. Changing it alters rendered schemas and option choice.
- **Live validation against the root.** Decided: not adopted; `formState.ts:356-366` keeps dropping root `if`/`oneOf` errors until submit.
- **Form-level reconciliation termination.** Keep v7's hash guard or adopt a named rule. Must `{b:'z'}` and `{a:'y'}` stay exactly as they are?
- **Idempotence of defaults.** Accept the three known flip shapes as documented exceptions (proposed), or define `getDefaultFormState` as an iteration to a fixed point, which changes v7 semantics.
- **Split I2.** If one level per click for `properties` recursion turns out to be unpopular, the split variant (4.4) needs prototyping before it can be considered.
- **validator-ata:** decided in stage 2: inline every bare `$ref` outside `definitions`/`$defs` and hoist those beside each schema (4.9).
- **Custom `AnyOfField` API.** Decided: the hook `useOptionSelection()` exported from `@rjsf/core` is the API for reading and writing the selection (4.6), not a registry member. How it interacts with Heath's presentation work (#5490) is open.
- **Dangling `$ref` as a field error (future work).** Decided to keep 6.11.0's and v7's behaviour in this series: `retrieveSchema()`, `getDefaultFormState()` and the form throw `Could not find a definition for <ref>.` (or `Definition for <ref> is a circular reference` for an alias loop). Rendering the error on the field alone needs every walk of the form (the parent's one-level collapse lookahead, the defaults fold, the sanitize diff, the `ui:required` walk, omit's `$ref` resolution, the validator's compile) to read an `invalid` node as a field of its own, so the contract has to be decided first: an `invalid` view handed out for the field (a new marker), or a documented throw that `SchemaField` catches.
- **Downstream use of the `lib/schema/*` deep imports** that the guide currently promises: unknown.
- **Standalone `retrieveSchema` callers** that read nested subschemas from one result (7.1, item 2): unknown how many exist outside this repo.
- **`omitExtraData` divergence from "keep fields in the tree"**: decided in stage 3b (4.8, as landed). Form passes its selection, so the option omit keeps is the one shown; the all-empty optional object and `anyOf` over empty data keep 6.11.0's answers. Standalone callers still get the relaxed best match.
- **Performance.** The graph is parsed once per root. A plan whose build read no data (no condition, dependency or option) is memoized for any data, and a view of a field is memoized per field and plan with the values of the keys its children's plans read, so an edit, which hands the form a new data object whose untouched keys keep their values, returns the same view for every field the edit does not reach. A property whose node merges nothing (no `$ref`, `allOf`, `if`, `dependencies` or options) can never collapse and is handed out without a plan. A caller's spread copy of a handed-out schema is parsed once while its keywords stay those of the last copy (`adoptCopy()`). Measured per edit on 200 string fields beside a `$ref`/`if` child, stub validator (verified): `getDefaultFormState` 331 µs against v7's 297 µs, root `retrieveSchema` 0.8 µs against 93 µs, a handed-out schema 0.6 µs against 41 µs, a spread copy 1.5 µs against 43 µs. `retrieveSchemaCost.test.ts` guards these by what is rebuilt rather than by time. A schema that merges nothing and holds no subschemas (no `$ref`, `allOf`, `if`, `dependencies`, options, `properties`, patterns, extra-property keywords or items) is retrieved once per root and handed back on every later call, since its view reads neither the data nor the context: `isSelect()` and `sanitizeDataForNewSchema()` retrieve every property on every edit. The defaults of a field seeded by such a schema are kept per schema with the props they were computed from, when they are not an object, so an edit folds again only the fields whose props it changed. Seed lists are keyed once. Measured on 800 string fields (stage 1 review, stub validator, sequential runs, verified): `getDefaultFormState` per edit 1 335 µs against v7's 1 749 µs (with a `$ref`/`if` child and an option list, 1 626 µs against 2 068 µs; 200 fields, 245 µs against 327 µs); `retrieveSchema` of a raw property 0.2 µs against 0.3–0.4 µs; `sanitizeDataForNewSchema` of the root 590 µs against 718 µs. Typing with user-event into a mounted `Form` of the same 800 fields plus a `$ref`/`if` child and an array of it, 60 keystrokes: 741–762 ms against 705–709 ms at the top level and 752–770 ms against 738–743 ms in the nested child, a remaining 1–8% that the root view accounts for: it is not memoized when a nested object's plan reads its data (a condition or `dependencies` under it), so it is rebuilt on every edit, as v7 rebuilds it. Mounting takes 191–193 ms against 163–165 ms. `Form.renderCost` and `renderStability` must not regress. The defaults memo in 4.5 is required; without it the fold is exponential in depth (verified on the prototype).
- **Prototype limits.** It caps the dependency fixed point at six passes and re-folds every child (both replaced in 4.5); it ignores `prefixItems` and skips boolean `true` seeds (inferred: no termination impact, since they are containment edges with no refs of their own); it resolves percent-encoded aliases but not `$id` or anchors; it returns empty on alias cycles and missing refs instead of throwing; it emitted inputs only for typed fields until enum/const leaves were added; it does not default a required array to `[]`; it seeds options with `getClosestMatchingOption` and forces the self-referencing option's selection; it does not model parent-owned forms. Stage 1 replaces it with the real implementation under the harness.
