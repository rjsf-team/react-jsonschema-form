# 7.0.0

## @rjsf/antd

- **BREAKING CHANGE** Dropped support for `antd` version 5; the peer dependency range is now `^6.3.6`. `ErrorList` and `CyclicSchemaExpandTemplate` use of `Alert` always passing `title` prop now. The `6.3.6` floor isn't arbitrary: antd 6.0.0-6.3.5 crash `@rjsf/antd` forms on first render (`getRealHeight` destructuring a `null` node), fixed upstream in [ant-design/ant-design#57636](https://github.com/ant-design/ant-design/pull/57636)
- `DateWidget`/`DateTimeWidget` format a `format: "iso-date-time"` value as a naive local date-time string instead of converting it to a UTC ISO string, since that format's timezone is optional. A stored value that happens to carry an offset anyway is stripped before being parsed, so it displays as the naive wall-clock time it represents instead of being converted to the browser's local zone ([#3930](https://github.com/rjsf-team/react-jsonschema-form/issues/3930))
- **BREAKING CHANGE** Fixed `BaseInputTemplate` never calling `onChangeOverride` for a numeric field: its `InputNumber` branch was wired straight to `onChange` and reports only the parsed value, never an event. A numeric field with an `onChangeOverride` now renders the `Input` branch (still `type="number"`) so the override receives the `ChangeEvent`, as it does in every other theme
- Added `<optgroup>`-equivalent support to `SelectWidget` via `ui:options.optgroups`, grouping options using rc-select's nested `options` shape
- `WrapIfAdditionalTemplate` renders an additional property's key as a `SelectWidget` of the names the parent schema's `propertyNames.enum` allows, instead of a free-text input, and takes the key from the new `keyName` prop rather than from the decorated `label`, so a `deprecated` additional property no longer offers its decoration as a key name, nor renames itself to it ([#4682](https://github.com/rjsf-team/react-jsonschema-form/issues/4682))
- **BREAKING CHANGE:** The default `Form` export is a `ThemedForm` (see `@rjsf/core`): generic over the form data, so `<Form formData={data} />` infers `T` and `<Form<MyData> />` names it. The `Theme`, `Templates` and `Widgets` exports keep each component's own generic type instead of being instantiated at the default `T` (`any` in 6.x), so `withTheme<MyData>(Theme)` and `{ ...Templates, FieldTemplate: MyFieldTemplate }` typecheck for any `T`. `generateForm()` returns a `ThemedForm<T, S, F>`; `generateTheme()`, `generateTemplates()` and `generateWidgets()` keep their signatures, apart from the new `unknown`/`FormContextType` defaults, and still build a fresh object on every call

## @rjsf/chakra-ui

- Converted the internal `forwardRef`-wrapped UI primitives (`Field`, `Slider`, `Alert`, `NumberInputRoot`, `Checkbox`, `Radio`, `CloseButton`, and the `Select` family) to plain function components that accept `ref` as a regular prop, now that React 19 supports this natively
- `SelectRoot` is now a plain generic function (`function SelectRoot<T extends CollectionItem>(...)`) instead of a non-generic arrow function cast to `ChakraSelect.RootComponent`, removing the cast and the wrapping parens it required
- Fixed `getChakra()` deleting the non-forwardable keys straight out of `uiSchema['ui:options'].chakra`, mutating the caller's own uiSchema as a side effect of rendering. It now returns a filtered copy
- Fixed `ChakraUiSchema`, which used `Omit<UiSchema, 'ui:options'>`. `UiSchema` has a string index signature, so `keyof UiSchema` includes `string` and `Omit` erased every named member, leaving a type that accepted anything. It now intersects instead
- `BaseInputTemplate` renders a `number`/`integer` field as `<input type="text" inputMode="decimal|numeric" pattern="..." title="...">` instead of `<input type="number">`, and no longer puts `step`, `min` or `max` on it, so the rendered markup and any snapshot of a numeric field change; see the `getInputProps()` entry under `@rjsf/utils` for the reasoning and the ways back to a native number input ([#4038](https://github.com/rjsf-team/react-jsonschema-form/issues/4038))
- Added `<optgroup>`-equivalent support to `SelectWidget` via `ui:options.optgroups`, using `Select.ItemGroup`/`Select.ItemGroupLabel`
- **BREAKING CHANGE:** Removed `chakra-react-select` from `peerDependencies`; the package no longer uses it, so it no longer needs to be installed alongside `@rjsf/chakra-ui`
- Fixed `NativeSelectWidget` ignoring `ui:enumDisabled`: it computed each option's disabled state but never applied it to the rendered `<option>`, so every listed option stayed selectable
- `WrapIfAdditionalTemplate` renders an additional property's key as a `SelectWidget` of the names the parent schema's `propertyNames.enum` allows, instead of a free-text input, and takes the key from the new `keyName` prop rather than from the decorated `label`, so a `deprecated` additional property no longer offers its decoration as a key name, nor renames itself to it ([#4682](https://github.com/rjsf-team/react-jsonschema-form/issues/4682))
- **BREAKING CHANGE:** Fixed `BaseInputTemplate`, `CheckboxesWidget`, `NativeSelectWidget`, `SelectWidget`, `TextareaWidget` and `UpDownWidget` marking themselves `invalid` from `rawErrors` alone, so a field stayed flagged as invalid under `ui:hideError` ([#3684](https://github.com/rjsf-team/react-jsonschema-form/issues/3684))
- **BREAKING CHANGE:** Fixed `CheckboxesWidget` marking its inner `CheckboxGroup` `invalid` whenever the field was required and empty, which flagged it before validation had found anything wrong and could not be suppressed by `ui:hideError`. It now derives that state from the field's visible errors, the same as the surrounding `FieldsetRoot`. A required, empty field is no longer flagged until validation reports an error for it, and a field with visible errors now marks every checkbox `aria-invalid`, where a non-required one used to mark only the fieldset ([#3684](https://github.com/rjsf-team/react-jsonschema-form/issues/3684))
- **BREAKING CHANGE:** The default `Form` export is a `ThemedForm` (see `@rjsf/core`): generic over the form data, so `<Form formData={data} />` infers `T` and `<Form<MyData> />` names it. The `Theme`, `Templates` and `Widgets` exports keep each component's own generic type instead of being instantiated at the default `T` (`any` in 6.x), so `withTheme<MyData>(Theme)` and `{ ...Templates, FieldTemplate: MyFieldTemplate }` typecheck for any `T`. `generateForm()` returns a `ThemedForm<T, S, F>`; `generateTheme()`, `generateTemplates()` and `generateWidgets()` keep their signatures, apart from the new `unknown`/`FormContextType` defaults, and still build a fresh object on every call

- `FallbackField`'s type selector offers `integer` and `null` alongside the five types it already did, and casts the form data into the chosen type for all seven: an `object` or `array` starts empty rather than keeping a value of the type it replaces, which the field then rendered as if it belonged, and a value with no text form of its own (`null`, an object, an array) clears instead of putting the literal `null` or `[object Object]` into the input. It starts on the type the current form data has, `null` included, rather than showing `object` for a `null` value, and on the schema's own first type when there is no data to match, except that a schema listing `null` first starts on the first type that can hold a value, since starting on `null` would write a `null` into the form data for a field nobody has touched. Text is read as a number only in the notation the number field itself accepts, so `0x10`, `0b11` and `0o17` leave the field empty rather than coming back as the `16`, `3` and `15` nobody typed, as does text naming an infinity — `Infinity`, or a `1e999` that overflows to one — which is no JSON number at all and which `JSON.stringify()` writes out as `null`. This part applies whether or not `useFallbackUiForUnsupportedType` is set, so a property described by, say, `additionalProperties: { enum: ['a', 'b'] }` now renders as a select over that enum for every form, and data of another type than the enum allows is as invisible in it as it would be in a select the schema asked for by naming a type. It leaves out the subschema keywords, which could name a type that cannot merge with the guessed one, the identifiers, which every stubbed property would otherwise share, and a `default` of another type than the data. `sanitizeDataForNewSchema()` reads the flag and treats such a type as no type at all when both schemas it compares are equally unconstrained, so a value whose type changes is kept instead of being discarded as data belonging to an old schema. A new schema that declares a type of its own is still the type the data has to satisfy, so switching from a free-form option to one that requires a number of the same key clears a string rather than leaving it in a number field ([#5238](https://github.com/rjsf-team/react-jsonschema-form/issues/5238))
- **BREAKING CHANGE:** The generic defaults changed from `any`: `T` (the form data) now defaults to `unknown` and `F` (the form context) to `FormContextType`. Every field, widget and template inherits them, so a component or callback written without a type argument now receives `unknown` form data and must narrow it or name its type (`FieldProps<MyData>`, `IChangeEvent<MyData>`). Code that passes its own `T` keeps its types, and a value annotated with the bare default still fits a typed `Form`: component slots (the `TemplatesType` entries, `Widget`, `Field` and the `ui:` template overrides) are typed with the new `SlotComponent<P>`, which checks a component's props bivariantly, and `FieldProps.onChange`, `WidgetProps.onChange` and the `items` function of a `UiSchema` take their `T` the same way, so a `UiSchema`, `CustomValidator` or `ErrorTransformer`, a handler taking a bare `IChangeEvent`, and a component written against the bare props all fit a typed `Form<MyData>`. A component annotated as a React `ComponentType` or `FunctionComponent` still fits every slot, but a `Widget`, `Field` or template value is no longer assignable to a `ComponentType` annotation; annotate it with the RJSF type instead. The `F` default is a rename with no narrowing effect yet: `FormContextType` still aliases `GenericObjectType` (`Record<string, any>`), so `formContext.foo` is still `any` until `FormContextType` is retyped in a follow-up. `Registry.schemaUtils` is now `SchemaUtilsType<T, S, F>` rather than `SchemaUtilsType<T, S>`, which the old `any` default had been hiding
- **BREAKING CHANGE:** `ValidatorType` has no `T` parameter: it is `ValidatorType<S, F>`, `validateFormData<T>()` takes the form data type per call, and `isValid()` and `rawValidation()` take `unknown` form data. A validator checks data of any shape against a schema, so one instance serves every `Form` whatever `T` it renders, and a validator package's default export fits a typed `Form<MyData>` again. `SchemaUtilsType.getValidator()` and `doesSchemaUtilsDiffer()`, `createSchemaUtils()` and every `schema/` utility take a `ValidatorType<S, F>`; `schemaParser()` and `DefaultFormStateBehavior.arrayMinItems.computeSkipPopulate` drop the `T` they never used. `createSchemaUtils()` no longer picks `T` up from the validator, so pass it (`createSchemaUtils<MyData>(validator, schema)`) when the `SchemaUtilsType` should be typed. A `ValidatorType<MyData>` annotation or an `implements ValidatorType<T, S, F>` needs the `T` removed
- The `help` option of `ui:options` (and `ui:help`) accepts `string | ReactElement`, matching `FieldHelpProps.help` and the element `SchemaField` already renders; it was typed `string`, which a typed `UiSchema<MyData>` now enforces
