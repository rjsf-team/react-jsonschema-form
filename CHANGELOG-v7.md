# 7.0.0

## @rjsf/antd

- **BREAKING CHANGE** Dropped support for `antd` version 5; the peer dependency range is now `^6.3.6`. `ErrorList` and `CyclicSchemaExpandTemplate` use of `Alert` always passing `title` prop now. The `6.3.6` floor isn't arbitrary: antd 6.0.0-6.3.5 crash `@rjsf/antd` forms on first render (`getRealHeight` destructuring a `null` node), fixed upstream in [ant-design/ant-design#57636](https://github.com/ant-design/ant-design/pull/57636)
- `DateWidget`/`DateTimeWidget` format a `format: "iso-date-time"` value as a naive local date-time string instead of converting it to a UTC ISO string, since that format's timezone is optional. A stored value that happens to carry an offset anyway is stripped before being parsed, so it displays as the naive wall-clock time it represents instead of being converted to the browser's local zone ([#3930](https://github.com/rjsf-team/react-jsonschema-form/issues/3930))
- **BREAKING CHANGE** Fixed `BaseInputTemplate` never calling `onChangeOverride` for a numeric field: its `InputNumber` branch was wired straight to `onChange` and reports only the parsed value, never an event. A numeric field with an `onChangeOverride` now renders the `Input` branch (still `type="number"`) so the override receives the `ChangeEvent`, as it does in every other theme
- Added `<optgroup>`-equivalent support to `SelectWidget` via `ui:options.optgroups`, grouping options using rc-select's nested `options` shape
- `WrapIfAdditionalTemplate` renders an additional property's key as a `SelectWidget` of the names the parent schema's `propertyNames.enum` allows, instead of a free-text input, and takes the key from the new `keyName` prop rather than from the decorated `label`, so a `deprecated` additional property no longer offers its decoration as a key name, nor renames itself to it ([#4682](https://github.com/rjsf-team/react-jsonschema-form/issues/4682))
- **BREAKING CHANGE:** The default `Form` export is a `ThemedForm` (see `@rjsf/core`): generic over the form data, so `<Form formData={data} />` infers `T` and `<Form<MyData> />` names it. The `Theme`, `Templates` and `Widgets` exports keep each component's own generic type instead of being instantiated at the default `T` (`any` in 6.x), so `withTheme<MyData>(Theme)` and `{ ...Templates, FieldTemplate: MyFieldTemplate }` typecheck for any `T`. `generateForm()` returns a `ThemedForm<T, S, F>`; `generateTheme()`, `generateTemplates()` and `generateWidgets()` keep their signatures, apart from the new `unknown`/`FormContextType` defaults, and still build a fresh object on every call
- `FieldTemplate` renders a field's validation errors alongside its `ui:help` text instead of replacing them with it. `Form.Item`'s `help` prop is antd's only slot for either, and the old precedence meant a field with `ui:help` showed no error message at all ([#5326](https://github.com/rjsf-team/react-jsonschema-form/issues/5326))
- `FieldTemplate` renders a `ui:help` passed as a React element, which it previously dropped along with the field's errors, since it gated both on the string-only `rawHelp` (see `rawHelp` under `@rjsf/utils`). A string `ui:help` was never affected, from the field's uiSchema or from `ui:globalOptions` ([#5326](https://github.com/rjsf-team/react-jsonschema-form/issues/5326))
- `FieldHelpTemplate` is registered in the theme's templates and restates antd's description color on help text when the field has errors. antd tints its whole `help` slot as an error in that case, and help shares the very element that carries the error text, so the tint would render help as a second error message. This is deliberately the opposite of the `hasErrors`-keyed danger tint `@rjsf/react-bootstrap` and `@rjsf/shadcn` apply, where help is its own element below the field. It is an inline style because it has to beat the inherited tint, so a consumer restyling `.help-block`'s color needs `!important` to take the error case back ([#5326](https://github.com/rjsf-team/react-jsonschema-form/issues/5326))
- Fixed object options in `RadioWidget` and object/array selects in `FieldTemplate`, and `SelectWidget` reports its form data value on focus and blur ([#5309](https://github.com/rjsf-team/react-jsonschema-form/issues/5309), [#5317](https://github.com/rjsf-team/react-jsonschema-form/issues/5317))
- Fixed `realValue` options whose `String()` matches, such as `1` and `'1'`, sharing a DOM value ([#5315](https://github.com/rjsf-team/react-jsonschema-form/issues/5315))
- Fixed `AltDateWidget` never passing `time`, `disabled` and `readonly` to `useAltDateWidgetProps()`, so `alt-datetime` rendered no hour, minute or second selects and emitted a date-only value, and the Now and Clear buttons still changed a `readonly` or `disabled` field ([#5410](https://github.com/rjsf-team/react-jsonschema-form/pull/5410))
- `TextareaWidget` no longer replaces a `ui:options.rows` of `0` with the default of 4 rows. React leaves a `rows` of `0` off the textarea, so it gets the browser's default height of 2 rows, as with `@rjsf/core`'s `TextareaWidget` ([#5387](https://github.com/rjsf-team/react-jsonschema-form/pull/5387))
- `FieldErrorTemplate` keys a React element error by its own `key` and any other error by its position, rather than giving every element error the same `...-[object Object]` key and a repeated string error the same key twice ([#5382](https://github.com/rjsf-team/react-jsonschema-form/pull/5382))
- Fixed `ObjectFieldTemplate` rendering a property with no column span when the `colSpan` map in `formContext` has no usable entry for its widget or field name. The lookup now falls through to the schema type and then to the default span, skipping entries that are not a whole number of columns from 0 to 24 and a `ui:field` that names no registered component. The keys are the ones `SchemaField` renders the property by, after resolving a `$ref` with its `ui:definitions` entry and merging an `allOf`, except for the type `SchemaField` infers from the constants of a `oneOf`/`anyOf` with no `type`, and the select it infers for a boolean with labelled options ([#5516](https://github.com/rjsf-team/react-jsonschema-form/issues/5516)). The type is read with `getFieldTypeForWidget()`, so a nullable type, a type inferred from `const`, `enum` or `properties`, or a type list whose `ui:widget` picks its field, matches its entry in the map, and an object declared without `type` gets the full-width default. A `ui:field` that names no field falls back to the field in `ui:globalOptions`. A widget in `ui:globalOptions` is looked up for a boolean, a multi-select array and a files array, whose fields render it, but not for a string or a number, whose fields don't. The default span counts only visible properties. A string entry such as `{ string: '8' }`, outside the declared `Record<string, number>`, is now ignored, and a plain `colSpan` number that is not a whole number from 0 to 24, such as `25` or `12.5`, gets the default span instead of being passed to `Col` ([#5450](https://github.com/rjsf-team/react-jsonschema-form/pull/5450))
- **BREAKING CHANGE:** Fixed `AltDateWidget`'s date parts having no accessible name: each select is named by the field's label and the translated part, such as `When, year`, even when the label is hidden, and described by the field's description, help and errors. `SelectWidget` gives the `aria-label` and `aria-describedby` it is passed to its control through `widgetAriaProps()` ([#5355](https://github.com/rjsf-team/react-jsonschema-form/issues/5355), [#5357](https://github.com/rjsf-team/react-jsonschema-form/issues/5357))
- Fixed `CheckboxesWidget` and `RadioWidget` rendering options enabled on a field whose group is disabled: every checkbox of a `disabled` field, where a click still changed the form data, and every checkbox and radio of a `readonly` one under `readonlyAsDisabled`. An option's own `disabled` overrides its group's in antd, and each option passed `false` unless `ui:enumDisabled` listed it ([#5487](https://github.com/rjsf-team/react-jsonschema-form/pull/5487))
- Fixed `CheckboxesWidget` and `RadioWidget` staying enabled, and still changing the form data, under an antd `DisabledContext` such as `<ConfigProvider componentDisabled>`. The group and each option passed `disabled={false}` for an enabled field, which antd reads ahead of the context; they now leave `disabled` unset ([#5487](https://github.com/rjsf-team/react-jsonschema-form/pull/5487))

## @rjsf/chakra-ui

- Converted the internal `forwardRef`-wrapped UI primitives (`Field`, `Slider`, `Alert`, `NumberInputRoot`, `Checkbox`, `Radio`, `CloseButton`, and the `Select` family) to plain function components that accept `ref` as a regular prop, now that React 19 supports this natively
- `SelectRoot` is now a plain generic function (`function SelectRoot<T extends CollectionItem>(...)`) instead of a non-generic arrow function cast to `ChakraSelect.RootComponent`, removing the cast and the wrapping parens it required
- Fixed `getChakra()` deleting the non-forwardable keys straight out of `uiSchema['ui:options'].chakra`, mutating the caller's own uiSchema as a side effect of rendering. It now returns a filtered copy
- Fixed `ChakraUiSchema`, which used `Omit<UiSchema, 'ui:options'>`. `UiSchema` has a string index signature, so `keyof UiSchema` includes `string` and `Omit` erased every named member, leaving a type that accepted anything. It now intersects instead
- `BaseInputTemplate` renders a `number`/`integer` field as `<input type="text" inputMode="decimal|numeric" pattern="..." title="...">` instead of `<input type="number">`, and no longer puts `step`, `min` or `max` on it, so the rendered markup and any snapshot of a numeric field change; see the `getInputProps()` entry under `@rjsf/utils` for the reasoning and the ways back to a native number input ([#4038](https://github.com/rjsf-team/react-jsonschema-form/issues/4038))
- Added `<optgroup>`-equivalent support to `SelectWidget` via `ui:options.optgroups`, using `Select.ItemGroup`/`Select.ItemGroupLabel`
- **BREAKING CHANGE:** Removed `chakra-react-select` from `peerDependencies`; the package no longer uses it, so it no longer needs to be installed alongside `@rjsf/chakra-ui`
- Fixed `NativeSelectWidget` ignoring `ui:enumDisabled`: it computed each option's disabled state but never applied it to the rendered `<option>`, so every listed option stayed selectable
- `WrapIfAdditionalTemplate` renders an additional property's key as a `SelectWidget` of the names the parent schema's `propertyNames.enum` allows, instead of a free-text input, and takes the key from the new `keyName` prop rather than from the decorated `label`, so a `deprecated` additional property no longer offers its decoration as a key name, nor renames itself to it ([#4682](https://github.com/rjsf-team/react-jsonschema-form/issues/4682))
- **BREAKING CHANGE:** Fixed `BaseInputTemplate`, `CheckboxesWidget`, `NativeSelectWidget`, `SelectWidget`, `TextareaWidget` and `UpDownWidget` marking themselves `invalid` from `rawErrors` alone, so a field stayed flagged as invalid under `ui:hideError` ([#3684](https://github.com/rjsf-team/react-jsonschema-form/issues/3684))
- **BREAKING CHANGE:** Fixed `CheckboxesWidget` marking its inner `CheckboxGroup` `invalid` whenever the field was required and empty, which flagged it before validation had found anything wrong and could not be suppressed by `ui:hideError`. It now derives that state from the field's visible errors, the same as the surrounding `FieldsetRoot`. A required, empty field is no longer flagged until validation reports an error for it, and a field with visible errors now marks every checkbox `aria-invalid`, where a non-required one used to mark only the fieldset ([#3684](https://github.com/rjsf-team/react-jsonschema-form/issues/3684))
- **BREAKING CHANGE:** The default `Form` export is a `ThemedForm` (see `@rjsf/core`): generic over the form data, so `<Form formData={data} />` infers `T` and `<Form<MyData> />` names it. The `Theme`, `Templates` and `Widgets` exports keep each component's own generic type instead of being instantiated at the default `T` (`any` in 6.x), so `withTheme<MyData>(Theme)` and `{ ...Templates, FieldTemplate: MyFieldTemplate }` typecheck for any `T`. `generateForm()` returns a `ThemedForm<T, S, F>`; `generateTheme()`, `generateTemplates()` and `generateWidgets()` keep their signatures, apart from the new `unknown`/`FormContextType` defaults, and still build a fresh object on every call
- Fixed object options in `RadioWidget` and `CheckboxesWidget`, and `SelectWidget` reports its form data value on focus and blur and offers an empty string option in the `realValue` format ([#5317](https://github.com/rjsf-team/react-jsonschema-form/issues/5317))
- Fixed `realValue` options whose `String()` matches, such as `1` and `'1'`, sharing a DOM value ([#5315](https://github.com/rjsf-team/react-jsonschema-form/issues/5315))
- Fixed `AltDateWidget` never passing `time`, `disabled` and `readonly` to `useAltDateWidgetProps()`, so `alt-datetime` rendered no hour, minute or second selects and emitted a date-only value, and the Now and Clear buttons still changed a `readonly` field, or a `disabled` one rendered by a custom `FieldTemplate` ([#5410](https://github.com/rjsf-team/react-jsonschema-form/pull/5410))
- `UpDownWidget` reports `undefined` to `onFocus`/`onBlur` when the focused element is an increment or decrement trigger, where it reported the trigger's `''` ([#5379](https://github.com/rjsf-team/react-jsonschema-form/pull/5379))
- **BREAKING CHANGE:** Fixed `AltDateWidget`'s date parts having no accessible name: each select is named by the field's label and the translated part, such as `When, year`, even when the label is hidden, and described by the field's description, help and errors. `SelectWidget` gives the `aria-label` and `aria-describedby` it is passed, or its own `aria-describedby`, to its trigger rather than its root, through `widgetAriaProps()` ([#5355](https://github.com/rjsf-team/react-jsonschema-form/issues/5355), [#5357](https://github.com/rjsf-team/react-jsonschema-form/issues/5357))
- `getChakra()` returns `JsxStyleProps`, the style props its filter keeps, instead of `Field.RootProps`, so `Fieldset.Root` and `Field.Root` both accept its result without a cast. Only a read of a non-style `Field.RootProps` member off the result, which was always `undefined`, stops compiling ([#5488](https://github.com/rjsf-team/react-jsonschema-form/pull/5488))
- **BREAKING CHANGE** Fixed the `chakra` option never reaching a widget: every widget handed `getChakra()` its `uiSchema` wrapped as `{ uiSchema }`, which holds no `ui:options`, so the style props were dropped. `getChakra()` now takes the widget's merged `options` instead of a `uiSchema`, so a `chakra` set through `ui:globalOptions` or the `ui:chakra` shorthand applies as one in `ui:options` does. A form whose uiSchema carries a `chakra` option is now styled by it. See the upgrade guide ([#5488](https://github.com/rjsf-team/react-jsonschema-form/pull/5488))
- **BREAKING CHANGE** The `chakra` option of the theme's `UiSchema` type is `JsxStyleProps` instead of `Field.RootProps`. A non-style prop such as `invalid`, `required`, `label` or `onClick`, which `getChakra()` has always filtered out, is now a compile error in the `ui:options` of the uiSchema's root. A nested field's `ui:options`, `ui:chakra` and `ui:globalOptions` are not typed for it, so it still compiles there and is dropped ([#5488](https://github.com/rjsf-team/react-jsonschema-form/pull/5488))
- `getChakra()` keeps every Chakra style prop, where it dropped the ones that share a name with an HTML attribute, such as `color`, `width`, `height` and `display`, and `@emotion/is-prop-valid` is no longer a dependency ([#5488](https://github.com/rjsf-team/react-jsonschema-form/pull/5488))

## @rjsf/core

- **BREAKING CHANGE:** `GridType` and `Operators` are now `as const` objects with same-named union types instead of `enum`s, so the source is valid under Node's type stripping. Values and `GridType.ROW`-style member access are unchanged; code that used a member as a type must write `typeof GridType.ROW` instead of `GridType.ROW` ([#5244](https://github.com/rjsf-team/react-jsonschema-form/pull/5244))
- **BREAKING CHANGE** `withTheme()` now returns a plain function component instead of a `forwardRef`-wrapped one, and `FormProps['onSubmit']`'s event parameter is now typed as `SubmitEvent<HTMLFormElement>` instead of the deprecated `FormEvent<any>`
- **BREAKING CHANGE:** Removed deprecated `Form` APIs: the `getUsedFormData()` and `getFieldNames()` instance methods (no direct replacement), the `omitExtraData()` instance method (use `SchemaUtils.omitExtraData(schema, formData)` instead), the `removeEmptyOptionalObjects` prop (already a no-op; use `omitExtraData`, which now prunes empty optional objects itself), and `boolean` values for the `liveValidate`/`liveOmit` props (use `'onChange'` in place of `true`, or omit the prop in place of `false`). Also removed the `ui:rootFieldId` uiSchema directive; use the `Form.idPrefix` prop instead
- **BREAKING CHANGE** Replaced the `extraErrorsBlockSubmit` prop with `extraErrorsAreWarnings`, inverting the default: `extraErrors` now block form submission unless `extraErrorsAreWarnings` is set to `true`, fixing [#4964](https://github.com/rjsf-team/react-jsonschema-form/issues/4964)
- Fixed `validateFormWithFormData()` (used by form submission and `validateForm()`) silently dropping a `customError` raised by a field/widget's `onChange` on submit; it's now merged in and blocks submission the same way schema and (non-warning) `extraErrors` do
- **BREAKING CHANGE:** Removed the private `_internalFormWrapper` prop from `FormProps` and `ThemeProps`; its only consumer was the removed `@rjsf/semantic-ui` theme. Use `tagName` to render a different element in place of `<form>`
- **BREAKING CHANGE** Dropped the `experimental_` prefix from `FormProps`, now that these features are no longer experimental: `experimental_defaultFormStateBehavior` → `defaultFormStateBehavior`, `experimental_customMergeAllOf` → `customMergeAllOf`
- **BREAKING CHANGE:** `getTestRegistry()` moved to `@rjsf/core/testing` as a named export; `@rjsf/validator-ajv8`, which it needs, is an optional peer dependency that only this entry point requires. Its positional arguments remain supported. Fixed three theme test helpers that previously passed an options object instead of positional arguments
- **BREAKING CHANGE** `TimeWidget`/`DateTimeWidget` pad missing seconds and append the browser's local UTC offset to a `format: "time"`/`format: "date-time"` value whenever it's changed (e.g. `14:30:00-04:00` instead of `14:30`), so the value is compliant with those JSON Schema formats per RFC 3339 — both require seconds, and a timezone offset is required for `time`/`date-time` specifically, matching the stricter `ajv-formats` 3 upgrade in `@rjsf/validator-ajv8`. The offset is always stripped back off for display in the native time/datetime-local input, since it can't render one. `format: "iso-time"`/`"iso-date-time"` are mapped to the same widgets and still get seconds padded, but no offset added, since their timezone is optional ([#3930](https://github.com/rjsf-team/react-jsonschema-form/issues/3930))
- Added `generateTheme()`, `generateFields()`, `generateWidgets()`, `generateTemplates()`, `generateButtonTemplates()` and individual component exports. **BREAKING CHANGE:** `getDefaultRegistry()` has been removed; use `generateTheme()`, one of the individual generators, or a direct component import instead ([#5266](https://github.com/rjsf-team/react-jsonschema-form/pull/5266))
- **BREAKING CHANGE:** The `Form.getRegistry()` static is now a standalone `buildRegistry()` export from `@rjsf/core`, taking the same arguments; most callers should use the `registry` prop they already receive, or `getTestRegistry()` from `@rjsf/core/testing` ([#5266](https://github.com/rjsf-team/react-jsonschema-form/pull/5266))
- `submit()` and `focusOnError()` reach the form-only members (`requestSubmit`, `elements`) behind an `instanceof HTMLFormElement` check, so they no longer throw when `tagName` renders something other than a `<form>` ([#5266](https://github.com/rjsf-team/react-jsonschema-form/pull/5266))
- **BREAKING CHANGE:** The `data` parameter of the `onBlur` and `onFocus` props is now typed as `unknown` instead of `any`, since a field's value can be any shape. Handlers that used the value without narrowing it (e.g. `(id, value: string) => ...`) need a type guard or an explicit cast ([#5266](https://github.com/rjsf-team/react-jsonschema-form/pull/5266))
- **BREAKING CHANGE:** Markdown requires an explicitly registered `templates.MarkdownTemplate`; core defaults to plain text. Import the renderer from `@rjsf/core/markdown`; `markdown-to-jsx` is now an optional peer dependency that only that entry point needs. Existing description/help flags remain independent and default to false. Raw HTML parsing is disabled, including file information. `FileWidget`'s file information rendered markdown unconditionally before, which is what made the file name bold; it now respects `ui:enableMarkdownInDescription` like every other translatable string, and the English `FilesInfo` string is plain text. ([#5263](https://github.com/rjsf-team/react-jsonschema-form/pull/5263))
- **BREAKING CHANGE:** Removed `RichDescription.TEST_IDS` and `RichHelp.TEST_IDS`, since neither component renders markdown itself any more; use `MarkdownTemplate.TEST_IDS.markdown` from `@rjsf/core/markdown` instead. Added the default `MarkdownTemplate` to the individual component exports, so it can be imported from `@rjsf/core` like every other template ([#5263](https://github.com/rjsf-team/react-jsonschema-form/pull/5263))
- Fixed `ui:placeholder` being dropped for multi-select arrays, file arrays, custom array widgets and boolean fields. They read `placeholder` from props, which nothing passes, so it stayed `undefined` while the value sat unused in `options`. They now read it from `getUiOptions()`, as `StringField` does
- Fixed a `ui:FieldTemplate` or `ui:FieldErrorTemplate` override being ignored on a `LayoutMultiSchemaField`, which resolved both templates by passing `options` — the anyOf/oneOf option schemas — where `getTemplate()` expects the UI options
- `FileWidget` ignores a `change` event whose `FileList` is empty instead of forwarding it to `useFileWidgetProps`, which now reads an empty selection as a cleared value. Some pickers re-fire `change` with an empty list when the dialog is cancelled, which would have wiped the existing selection
- **BREAKING CHANGE:** Fields, widgets and templates identify a field by two strings instead of the `fieldPathId` object: `fieldPath` (a `FieldPath` such as `friends[0].firstName`, where the data lives) and `id` (the DOM id). `FieldProps`/`FieldTemplateProps` receive both; the other templates receive `id`. `FieldProps['onChange']` carries the `FieldPath` string instead of a `FieldPathList`, and the `childFieldPathId` compensation prop is gone. Ids are unchanged from v6, except in two cases where v6 produced a duplicate: the optional-data controls of an object or array that is itself an `oneOf`/`anyOf` schema now carry the `XxxOf`-suffixed id of the field rendering them, where v6 gave the outer and the selected option's controls the same id; and a schema property named `''`, which v6 gave its parent's id, now has one of its own at every level — directly under the root included, where v6 wrote its value over the whole `formData`. `IChangeEvent` and `FormState` no longer carry `fieldPathId` either, so an `onChange(e)` handler reading `e.fieldPathId` must be updated. Primitive props are reference-stable across renders, so `React.memo` boundaries work without deep comparison ([#5217](https://github.com/rjsf-team/react-jsonschema-form/issues/5217))
- **BREAKING CHANGE:** `IChangeEvent` is a standalone interface rather than a `Pick` of `FormState`, so the form's state can change shape without changing the public event, and every member is `readonly`. Members and types are unchanged apart from `formData`, which is now `EventFormData<T>` (see below); assign the event's `formData` into your own state rather than assigning into the event
- `Form` passes its `uiSchema` through to `getDefaultFormState()` so `ui:emptyValue` and `ui:initialValue` are applied — including to a new array row added via `ArrayField`'s "Add" button (using `uiSchema.additionalItems` for a row added past a fixed/tuple `items` schema, and `uiSchema.additionalProperties` for an object's dynamically-added property, matching the uiSchema each already renders with) — and merges a `ui:required: true` field's validation into the result via `@rjsf/utils`'s new `getUiRequiredErrorSchema()`, rather than rewriting the schema handed to the validator. That utility walks the form the same way it's rendered — resolving each node's schema (`$ref`, `allOf`, `dependencies`, `if`/`then`/`else`, the selected `oneOf`/`anyOf` branch) and uiSchema (including a `ui:definitions` fragment) against the current `formData` — so `ui:required` is enforced everywhere a field can appear, identically on the submit and `liveValidate` paths, and by precompiled validators, since the schema they were built from is never touched ([#4983](https://github.com/rjsf-team/react-jsonschema-form/issues/4983))
- `SchemaField` and `LayoutGridField` resolve a field's effective required state from `ui:required` when present, falling back to the schema otherwise. `ui:required` is resolved from a field's own uiSchema only: it is not honored via `ui:globalOptions` or a `LayoutGridField` grid cell's own config object for a schema-backed field, since a form-wide or grid-level default would make the required indicator and schema validation disagree; a grid cell that instead renders an arbitrary custom `render` component is unaffected by this, since its `uiProps` (including any `required`) are plain component props passed through untouched, not schema-connected uiSchema. `SchemaField` warns when `ui:required: false` is set on a schema-required field with neither `ui:initialValue` nor `ui:emptyValue` set on that same field's own uiSchema, since the UI would show it as optional while validation still rejects an empty value. The warning is logged once per page for a given field id, through `logOnce()` (see the `@rjsf/core` entry below) ([#4983](https://github.com/rjsf-team/react-jsonschema-form/issues/4983))
- Added `CoreUiOptionsChecks`, the `UiOptionsCheck` union describing `@rjsf/core`'s own built-in widgets, fields and `ui:options`. Pass it as the `Checks` type argument of `@rjsf/utils`'s new `StrictUiSchema` type (see the `@rjsf/utils` entry below) to type-check a uiSchema against `@rjsf/core`'s real vocabulary ([#4916](https://github.com/rjsf-team/react-jsonschema-form/issues/4916))
- **BREAKING CHANGE:** Removed the `experimental_componentUpdateStrategy` prop. `Form` and `SchemaField` are memoized with the default shallow comparison, so props holding functions (`customValidate`, `transformErrors`, templates, widgets, fields, `formContext`, ...) must be stable references; a changed one now takes effect at once, where v6 ignored it until another prop changed ([#5217](https://github.com/rjsf-team/react-jsonschema-form/issues/5217))

- `isValid()` and `rawValidation()` key a schema whose `$id` is the empty string by its hash, so two such schemas no longer evict each other from the cache of built validators ([#5338](https://github.com/rjsf-team/react-jsonschema-form/issues/5338))
- The `errors` a validation returns keep an error whose `message` a `transformErrors` cleared whenever a `customValidate` is passed, as they do without one, since `validationDataMerge()` no longer drops the existing errors when their `errorSchema` is empty. A form whose `transformErrors` clears every `message` therefore reports those errors through `onError` instead of submitting when it also has a `customValidate`, as it already did without one ([#5034](https://github.com/rjsf-team/react-jsonschema-form/issues/5034))
- `validateFormData()` lists the errors of a `customValidate` that returns an array for the items of an array field and keys them by index in the `errorSchema`, where it left them out of `errors` and let that array replace the validator's own errors for the array field. See the `@rjsf/utils` entry for `validationDataMerge()` and `unwrapErrorHandler()` ([#3827](https://github.com/rjsf-team/react-jsonschema-form/issues/3827))
